## Architecture: contact groups (phase 2, 2026-10-20) — "send to the whole crew"

**A group is a named list of address-keyed members** (`{ id, name, color, members:[member], note, createdAt, updatedAt, sharedFrom }`, `sanitizeGroup` normalizes everything). Two homes, one service — **`scripts/services/ContactGroupService.js`** (`game.nightcity.contactGroupService`, BaseApplication getter):
- **Player groups** live on the character — actor flag **`contactGroups`** (the player owns the actor, so `saveActorGroup`/`deleteActorGroup` are their own writes; `isOwner` is checked). **GM groups** live in the world setting **`masterContactGroups`** (`saveMasterGroup`/`deleteMasterGroup`, GM-only). `groupsFor({actorId, isGM})` is what the composer searches: the from-character's own groups + the GM's when the GM composes. Factory Reset / the id migration need nothing (flag block + registered setting).
- **Members are built by `memberFromPlayerContact` / `memberFromMasterContact` / `memberFromActor`** and resolved live by `recipientsFor(group)` → `{recipients, unresolved}` (participants.js `resolveMember`): a dead id hint with no address is REPORTED by name, a bare address still goes as a raw recipient, duplicates collapse. `groupFromTag(actorId, tag)` is the "make a group from this tag" shortcut (unsaved).
- **Push (GM → player) — `pushGroupToPlayer(groupId, targetActorId)`:** every member the player lacks is shared first (directory entries via `pushToPlayer`, bare actors via `pushActorToPlayer`, both duplicate-safe; the target never receives itself), then the group lands on the character **as a COPY with its own id, tagged `sharedFrom:{groupId, at}`**; re-pushing REPLACES that copy. `sharedWith(groupId)` reads who holds one (via `getPlayerCharacters()` — rows are `{actorId, actorName, playerName, actor}`, NOT `{id, name}`; that shape bit this build once).
- **Export/import:** Admin → Contacts export now writes **`{ ncmMasterContacts: 1, exportedAt, contacts, groups }`**; both importers (Admin tab + GM Contact Manager) accept that envelope OR the old bare array. `importMaster` de-dupes groups by name, strips `sharedFrom`, and lists members that resolve to nothing in THIS world (reported, never dropped). The sim round-trips a group into a mocked world where every id differs and asserts every member comes back by address.
- **Composer:** group hits lead the To autocomplete (`_groupResult`, `.ncm-autocomplete-item--group`); picking one adds ONE chip (`isGroup`, `×N`, hover = member names, `.ncm-composer__chip--group`, colour as `--g`) whose members were resolved at pick time (unresolved named once, up front). `_onSend` flattens group chips into `sendList` (de-duped) and sends `recipients` whenever a group chip is present, even for one member. `recipientKey` includes `groupId` so the chip removes as one; drafts persist `groupId` and re-add via `_addGroupById`. `composeMessage({ groupId })` opens the composer with the group (launcher forwards it). `MessageService._normalizeRecipients` also expands `data.groupId` (macro API / scripts).
- **Player UI:** the Contact Manager's **Groups panel** (`templates/contact-manager/partials/contact-groups-panel.hbs` = `TEMPLATES.CONTACT_GROUPS_PANEL`, hidden while a form is open). **Rebuilt 2026-10-21 as a RAIL + TRAY (`.ncm-cgr-*`, dev-approved mock `dev/mockups/contact-groups-rail-mock.html`; the row list with hover-only names is gone):** a group is a **chip** (colour bar · name · a stack of up to 3 member avatars · count · GM-shared shield) on a wrapping rail that scrolls past three rows; clicking a chip (`cgOpen`) opens ONE **tray** under the rail — every member as a card (portrait/initials, name, role · address; `cgMember` opens that contact in the detail pane; a member matching none of this character's contacts is a dashed "address only" card) with Message all / Edit / Delete / close (`cgMessage`/`cgEdit`/`cgDelete`/`cgClose`) in the tray header once. **Recently messaged groups sort first**: `sanitizeGroup` keeps `lastUsedAt`, `ContactGroupService.touchActorGroup(actorId, groupId)` stamps it silently (never throws, no event) from the composer's success path for every actor-scope group chip; never-used groups follow A→Z. Past **`ContactManagerApp.GROUP_RAIL_LIMIT`** (6, ≈ one row) the rest fold behind a dashed **"+N more"** chip (`cgMore` toggles `_groupsExpanded`); the open group is always shown. The view-model is `_contactGroupsContext()` → `{ total, expanded, hiddenCount, list, open }` and members resolve to the character's OWN contacts through `_findGroupMemberContact` (master id → address → linked actor → name). New / `cgNew` is the dashed chip at the rail's end. **GM UI:** Admin → Contacts **Groups card** (`.ncm-cg-*`, above the search): New / Push / Edit / Delete (`cgAdmin*` → `ContactsTab.onGroup*`); Push opens the multi picker over player characters. **The card shipped permanently EMPTY (testers 2026-10-22: "saved, can be messaged, never appears in the admin UI; players never get it")** — `AdminPanelApp._prepareContext` lifted two NAMED keys (`contactSummary`, `pushLog`) out of the Contacts tab context instead of spreading it, so `masterGroups` never reached the template and Push was unreachable (the composer reads the setting directly, which is why sending still worked). Now `...contactContext` is spread like every other tab, and `test-contact-groups` asserts the spread AND that every key the tab returns is read by the template. **A tab's context must be SPREAD into the panel context, never cherry-picked.** **Both use `scripts/ui/ContactGroups/GroupEditorDialog.js`** (`editGroupDialog(group, {memberSource})` → name, colour swatches (`GROUP_COLORS`), member list, "Add members" = **`showNamePicker({ multi: true })`** — the shared picker gained a multi-select mode: check rows, Done button, resolves an ARRAY; members already in the group are greyed `in group`). The dialog returns the edited group UNSAVED; the caller owns the write. All CSS in `styles/components/contact-groups.css`, every colour a token (player panel/composer follow the player theme; dialog/card the admin preset).
- **Group pictures (2026-10-29, dev: "group image uploads — it'll appear in groups and when you send them messages").** `group.img` (kept by `sanitizeGroup` through `sanitizeGroupImg`: a path, an http(s) URL or a `data:image/` URI; `javascript:` / other `data:` / anything with a quote or `<>` is dropped). The group editor (`GroupEditorDialog`) has a Picture row — a live preview tile in the group colour, a path box, Browse (FilePicker; a player without file-browser rights is told to paste a path), Clear. Drawn on: the player Contact Manager chip (replaces the colour bar, keeps the colour as an edge) + tray head, the composer's group chip AND its autocomplete row, Admin → Contacts → Groups (list + detail head; a picture gets its own 84px / 44px column), Players → Groups they hold (rack tiles + tray), and every GROUP PICKER: Players → **Push a group to …** (the name picker — it now draws an `icon` in the entry's `color` for a row with no picture instead of the item bag), the map's Group highlight and Messages' Who / Send-to scope pickers. It is part of `groupSig`, so changing it marks pushed copies out of date; pushes, export and import carry it. Not on received mail (a fan-out copy does not know which group it came from). Sim `dev/tools/sims/test-group-images.mjs` (32, also covers the Players → Edit redesign). Not live-tested.
- **Macro API:** `getContactGroups(actorIdOrName?)`, `addContactGroup(group)`, `pushGroupToPlayer(groupId, actorIdOrName)`; `sendMessage({ groupId })`.
- **Phase 3 (same day) — GM tooling.** (1) **Mass Broadcast** (Admin → Messages) has a **Send to** select — every player character, or one of the GM's groups — and sends ONE fan-out (`sendMessage({ from, subject, body, isBroadcast:true, recipients })`) instead of a per-player loop, so refused recipients are NAMED; a bare sender name writes no sent copy (no inbox for it). (3) **Orphan Audit** lists **group members that resolve to nothing** (no address AND dead id hints — a raw address is never an orphan) across GM and player groups, and prunes them (`_pruneGroupMembers`; a group left empty is deleted). ## Player Contact Manager — last interaction (2026-08-14)

The detail panel's **Last Interaction** card and the **Recent** sort are live (they were TODO placeholders for years). `MessageRepository.getLastMessagesByCounterparty(actorId)` scans the actor's mailbox ONCE and indexes the newest message per counterparty three ways (`byEmail` lowercased / `byActorId` / `byContactId`) — the counterparty is always the OTHER side (sender on received mail, recipient on a `-sent` copy). `MessageRepository.pickLatestFor(index, {email, actorId, masterContactId})` (static) resolves one contact against it, newest across the three keys. `ContactManagerApp._prepareContext` builds the index per render (`_lastMsgIndex`), `_lastMessageFor(contact)` feeds both the `recent` sort (no-history contacts last, A→Z) and the selected contact's card (`{subject, timeAgo}` via the shared `_relativeTime` pattern). Also usable one-off: `getLastMessageWith(actorId, contact)`. Sim coverage in `dev/tools/sims/test-footprints.mjs`.

## Architecture: IDENTITIES — one character, several contacts (2026-10-26)

Tester: "can one actor have multiple email addresses / aliases?" Not a second address system: an **identity is a GM master contact LINKED to the character** (`contact.actorId`). Mail to any of them already lands in the character's inbox (`_resolveRecipient` → linked actor). The contact field `alias` is the unrelated display subtitle — in code these are IDENTITIES; the UI says "main" / "alias of …". Sim `dev/tools/sims/test-identities.mjs` (73). **Not live-tested, no mock was made (dev: "do all those things").**
- **Rules = pure `scripts/utils/identities.js`**: `identitiesOf(contacts, actorId)` (main first), `primaryOf`, `identityRole(contacts, c)` → `{isPrimary, isAlias, primary, count}` (null for an unlinked or lone contact), `aliasLabel`, `identityUsage(messages, identities)` (a message counts for the identity it names — `toContactId` received / `fromContactId` sent — else the main), `replyIdentity(contacts, original, replierActorId)`. **Main = `contact.primaryIdentity`** (whitelisted in add/update), else the first linked. **`MasterContactService.getByActorId` now returns the MAIN identity** (unchanged when none is flagged); `identitiesFor`, `identityRoleOf`, `setPrimaryIdentity` (one per character), `addIdentity(actorId, {name, email})` (GM).
- **The exact identity now survives a send** — before, the composer collapsed a character-linked contact to the character and the mail recorded the MAIN address: `_addRecipient(actorId, locked, ident)` keeps `{contactId, email, name}`; autocomplete passes it; GM/player search dedupe by contact/address (not by character) so every identity is its own row; a sole recipient sends its `toContactId`. **Send-as** keeps BOTH `fromActorId` and the picked identity (`fromContact`, list type ALIAS); `_fromEmail` and `MessageService._senderEmailFor` let an explicitly picked identity OF THAT CHARACTER win over the registered address. **Replies**: `buildReply` answers the identity the mail came FROM (`toContactId` + `to`) and sends AS the identity it reached (`fromContactId`/`from` via `replyIdentity`); the composer adopts both.
- **GM tracking**: GM Contact Manager **Identities card** (`_identitiesContext` — every linked contact, ★ main [`identSetPrimary`], open [`identOpen`], counts + last use from the character's inbox, the registered address when no identity carries it, **+ Add alias** [`identAdd` → `addIdentity`, address + duplicate checks]); Admin → Contacts (alias rows nested + indented under their main with "alias of X", main row "main · N identities", an **Aliases** filter pill, a search hit brings the whole group); Admin → Messages (feed rows + NPC Inbox show "`alias` · alias of X" via `_aliasNote`; filtering by a character includes all its identities). CSS `.ncm-gm-ident*`, `.ncm-ct-row--alias`/`.ncm-ct-badge--alias|--main`, `.ncm-msg-alias`. Export/import carry `actorId` + `primaryIdentity` as part of the contact.
- **NPCs with NO actor have identities too** (dev, same day). Groups are keyed by `groupKeyOf(contacts, c)`: `a:<actorId>` for a character's linked contacts, `c:<rootContactId>` for a contact-only NPC whose aliases carry **`identityOf: <the NPC contact id>`** (whitelisted; an alias of an alias stores the ROOT; an `identityOf` pointing at a character's contact joins the character). Main = flagged `primaryIdentity`, else the root / first linked. **Routing**: `_resolveRecipient` sends an actor-less alias's mail into its group's inbox (the character, or the root NPC's contact inbox — `identityInboxId`) while `toContactId` stays the alias; `_createSentCopy` files mail sent AS such an alias in the same inbox. `MasterContactService.addContactIdentity(contactId, data)` / `identitiesForContact`; `setPrimaryIdentity` works per group. `buildReply(…, {fromContactId})` + `replyIdentity(contacts, orig, {actorId, contactId})` so the NPC answers AS the alias the mail reached. The GM card shows for EVERY contact (a lone one gets just itself + **+ Add alias**). Sim now 73.
- **Portraits: an alias NEVER borrows its character's face** (a burner showing Lucky Lin's portrait unmasks it). `resolveDisplayPortrait` and `PortraitService.resolvePortrait` (incl. a player's copy via `masterContactId`) return initials for an alias with no picture of its own; its own `portrait` still wins; the main identity falls back to the character as before. **+ Add alias** takes a picture (text + FilePicker via the prompt's `render`).

## Architecture: address directory export / import (Admin → Tools → Email Domains & Addresses, 2026-10-24)

Tester ask: "mass import a csv or json of emails." Master contacts already had JSON import/export; **actor addresses (the `email` flag) had neither**. The Tools-tab domain dialog (`ToolsTab.onManageDomains`) now carries two tool rows: **Export / Import domains** (JSON envelope `{ncmEmailDomains:1, default, domains, allowCustom}`, or one domain per line; the import fills the OPEN dialog's rows and Save persists) and **Addresses: Export CSV / Export JSON / Import…**.
- **The rules are the pure module `scripts/utils/emailDirectory.js`** (no Foundry globals; sim `dev/tools/sims/test-email-import.mjs`, 46 checks). `buildDirectoryRows(world)` = every person-actor with an address + every master contact with one (`kind: actor|contact`, both ids; a linked contact exports as its own row because the two addresses CAN differ). `parseDirectoryImport(text)` reads CSV/TSV (header by alias in any order — `Character`/`Address`/`Contact ID`… — or positional `name,email[,kind]`; a header is only a header when NO cell is an address and it is mostly alias words, because `Judy Alvarez,judy@mox.nc,contact` has one alias hit and is data) and JSON (the envelope, a bare array, a `{name: address}` map, or a master-contacts export). **`planDirectoryImport(rows, world)` writes nothing**: per row → `update-actor` | `update-contact` | `create-contact` | `skip` with a reason. Order: explicit actorId → explicit contactId → character by name (space/punct-insensitive) → contact by name → (a name, no `kind`) new contact. `kind:'actor'` never touches/creates a contact; `kind:'contact'` never touches a character. **A blank address never clears one. An unchanged row is a skip even when its linked twin differs** (re-importing an export plans ZERO writes — the sim asserts it). When the primary changes, the character↔master-contact **twin is kept in step (`also`)** and is never reported as a stranger holding the address; a true stranger is a WARNING, as is a duplicate address in the file and a player character (the GM is overriding what the player chose). Same target twice → the second row is skipped naming the first. Ambiguous names (two actors) → skip asking for the id column. ICE/demon/container actors are never targets.
- **The world adapter + writes live in ToolsTab** (`_directoryWorld`, `_exportDirectory`, `_importDirectory` → the plan PREVIEW dialog (`.ncm-dirimp-*`, admin-themed, table `margin:0`) → Apply → `_applyDirectoryPlan`): characters through **`EmailService.forceSetEmail`** (the one writer; it warns on a taken address), contacts through `MasterContactService.updateContact({email})` / `addContact` (new contacts are `type:'npc'`, not send-only, with a provenance note). Failures are collected and toasted, never thrown mid-list. **`scripts/utils/csv.js` is now THE CSV parser/writer** — `DataShardComposer._parseCsv` delegates to it (the sim asserts the inline copy is gone). Mail already sent keeps the `from` it was stamped with (standing rule). **Not live-tested.**

## Group push: never yourself; numbers ride along (tester round 2026-11-09)
- **`ContactGroupService.selfTest(actorId)`**: a member is the character itself by sheet link, by one of its directory identities (`identitiesFor`), or by address (its email flag or an identity's). The old check only matched `resolved.actorId`, but a member resolves through the directory FIRST and a character's directory entry is often not linked to the sheet → everyone got themselves.
- **`copyFor(group, actorId)`** = the group less the character: the push writes it, and BOTH "Out of date" checks (Players tab `_heldGroupsContext`, Groups tab) compare a held copy with `copyFor(master, thatActor)`, never the raw group (it would always differ for a member).
- A push also removes a contact an earlier push left that stands for the character itself (`_removeSelfContacts`, matched to this group's self-members only).
- `pushActorToPlayer` now carries the character's main number (`callService.numberOf`), like `pushToPlayer` already did for directory contacts; a saved copy without one gets it.
- `characterIdsOf(group)` (sheet link, else a character whose address a member carries) feeds the name picker's new **`sets`** option (multi only: "Tick a group" chips that tick/untick rows, never filter) in Phone → Share and Contacts → Push to players.
