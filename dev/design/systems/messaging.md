## Architecture: player send feedback — the relay ACK (2026-10-20)

Tester report: "sometimes my player failed to send a message, but we don't know if it's the signal, bad email or other thing." Root cause: the player path was **fire-and-forget** — `MessageService._relayMessage` emitted `MESSAGE_RELAY` and returned `success:true` immediately, so the composer played "Delivered" and closed; a GM-side failure (orphaned inbox, unresolvable anon reply) came back as a stray `ui.notifications.warn` with repository text, broadcast to **every** client. Rules now:
- **`_relayMessage` awaits the GM's `MESSAGE_DELIVERED`** for its `messageId` (`_awaitDeliveryAck`, `_pendingRelays` map, `RELAY_ACK_TIMEOUT_MS` 8s → `errorCode:'RELAY_TIMEOUT'`). The composer therefore shows the REAL outcome in its existing failure overlay (Retry / Queue / Save Draft) and stays open. The GM handler (`handleMessageRelay(data, senderUserId)`) stamps **`forUserId`** on the ack (SocketHandlers passes the socket `sender`), and `handleDeliveryConfirmation` ignores acks for other users; a late/unsolicited ack for ME falls back to a toast.
- **Errors are translated for the player in ONE place — `MessageService.playerFacingError(raw)`** ("Could not access inbox journal" → "…ask your GM to check Admin → Tools → Orphan Audit"); the raw text rides `rawError` + the console. **The GM is toasted too** (permanent warn naming sender → recipient + raw reason) — they are the only one who can fix it.
- **Queued ≠ Delivered.** `_relayMessage` returns `{success:true, queued:true, reason:'gm_offline'|'dead_zone'}`; the composer shows an amber **Message Queued** panel with the reason (`_playSendAnimation('success', {queued, reason})`) instead of "Delivered to X". **Dead zones now actually queue** (the Send button already read "Queue" but nothing enforced it, so the message relayed at once and arrived garbled at signal 0); the existing `NETWORK_CONNECTED` listener flushes the queue when signal returns. GM sends are unaffected (the GM composes from anywhere, incl. "send via").
- **`errors.general` is rendered** (block line under SUBJ, `.ncm-composer__field-error--general`) — the composer had set it for years for "needs a subject or body" and the template only printed `errors.to`, so an empty Send looked like a dead button.
- **Every `{ success:false }` return in MessageService / MessageRepository carries an `error`** — the sim asserts it, and asserts every `_errors.<key>` the composer sets has a `{{errors.<key>}}` in the template. Sim: `dev/tools/sims/test-send-feedback.mjs` (35 checks, real methods via prototype + a scripted two-client socket). **Not yet live-tested two-client.**

## Architecture: multi-recipient mail — fan-out, participants, Reply All (contact groups phase 1, 2026-10-20)

Groundwork for contact groups ("send to the whole crew"). **Before this the module had never delivered one message to two people**: the composer packed 2+ chips into an ARRAY `toActorId`, the service resolved a single recipient, and the send died with "Recipient not found".
- **Members are keyed by ADDRESS, ids are hints — `scripts/utils/participants.js`** (pure): `makeMember({email, name, kind, hint:{actorId, contactId}, role:'from'|'to'})`, `dedupeMembers`, `othersFor`, `selfKeys`, `memberKeys`, and the 4-step `resolveMember(member, world)`: **hint by id** (precise inside one world; reports `stale` when the document's address moved) → **address** (`verifyContact`-shaped: directory entry + linked actor, or an actor's email flag) → **name** (space/punctuation-insensitive) → unresolved (still sendable as a raw address). Why address-first: master-contact export is a bare JSON array re-imported with FRESH ids and de-duped by email, so an id-keyed member breaks the moment a group crosses worlds. `worldAdapter()` builds the adapter from Foundry globals; the sim drives it with two mocked worlds and proves an exported member re-resolves by address when every id differs.
- **`MessageService.sendMessage` is now: validate → sender → `_normalizeRecipients` → one or many.** `data.recipients` (array of `{actorId, contactId, email, name}`) wins; the legacy single fields and the legacy array `toActorId` still normalize. ONE → `_resolveRecipient` (the lifted recipient-resolution + send-only + verification block, async because of the correspondent rule) → `_stampOutgoing` (addresses, NPC auto-register, names, ids, thread, GM overrides, network/signal/timestamp) → deliver/relay, unchanged behaviour. MANY → **`_sendToMany`**: each recipient resolved + gated on its own (a refusal is REPORTED in `results`/`failed`, never a silent drop; all refused → `ALL_RECIPIENTS_FAILED` and nothing is written), the base stamped once (`to`/`toName` = the whole party), **`participants`** = sender (role `from`) + every recipient that passed, then N copies `{...base, toActorId, to, toName, _recipientInboxId}`. GM → `_deliverMany` (each copy through the normal `_deliverMessage(copy, {sentCopy:false})`, so spam filter / anon mask / terminal mirror / NPC toast / MESSAGE_NOTIFY all run **per copy**; then **ONE** sent copy via `_createSentCopy(base)`). Player → ONE relay carrying `_fanout: copies`; `handleMessageRelay` fans out and acks once with `delivered`/`failed`/`results`; the composer reports "Not delivered to 2 of 4 — who: why" and refunds the failed share of attached eddies (**eddies are debited × recipients** — every copy carries the amount). **Never add a second sent-copy writer.**
- **`participants` persists through all three flag builders** (`createMessage`, `_pageToMessage`, `_buildMessageFlags`) — the field-by-field rule. `_maskAnonForRecipient` strips the `role:'from'` member (truly hidden). `_recipientEmailFor` orders registered-flag → **directory address** → synthesized `name@nightcity.net` (the directory used to lose to the synthesized address when the linked actor had never run Email Setup).
- **Threading needed no redesign.** `counterparties(msg, viewingActorId, viewingKeys)` adds every participant's keys minus the viewer's own (actor id + address + directory id — `MessageViewerApp._threadOpts` passes `viewingKeys` via `selfKeys`), so two group threads with the same subject merge only when they share someone OTHER than me; a sent copy's joined `to` is split on commas. Pre-fan-out mail (no participants) threads exactly as before.
- **Reply All**: `buildReply(orig, fromActorId, body, {all:true})` → `reply.recipients` = `replyAllRecipients` (participants minus self by id/address/directory id/name; **empty on anonymous mail — the mask would leak — and on legacy mail**). Viewer: `reply-all-message` action + button beside Reply (both branches), gated by `canReplyAll` (≥2 others, not masked, not send-only); the compose launcher forwards `replyAll` (it whitelists options — add new ones there). Composer adds the recipients as removable chips. A `.ncm-viewer__detail-party` chip beside the To line shows the party size (hover = names).
- Sim: `dev/tools/sims/test-group-send.mjs` (56 checks — member record, the 4 steps + cross-world round trip, normalization, GM fan-out shape, partial failure, all-refused, the relay/ack round trip, anon strip, Reply All, threading over the party, validator, and the persistence/launcher/template drift guards). **Not live-tested.** Phases 2–3 (groups as data, GM push, admin + import/export) are designed in the `contact-groups` memory note.

## Architecture: incoming-message notifications

The recipient's "New Message" toast is driven by a **single** path: `EVENTS.MESSAGE_RECEIVED` → the listener in `registerMessagingSystem.js` → `NotificationService.showMessageNotification`. That method owns the toast **and** the receive sound, and **dedups by `messageId`** (a `_recentMsgToasts` map, ~4s window) because the same delivery emits `MESSAGE_RECEIVED` from two sources: the socket path (`MessageService.handleMessageNotification`, recipient online) and the document-sync path (`DocumentSyncBridge._onJournalPageCreated`, when the journal page appears).

**Scene-control unread badge sits INSIDE the button** (`.ncm-unread-badge`, notifications.css, top/right 1px + z-index) — it used to hang outside at −4px and Foundry's controls toolbar clips overflow, so the circle/count rendered cut off. Don't move it back outside the button bounds. **Mark all as read (2026-08-14):** `MessageRepository.markAllAsRead(actorId)` flips every unread non-sent non-deleted message (spam included — the exact set `getUnreadCount` counts) in ONE `updateEmbeddedDocuments` batch; `MessageService.markAllAsRead` wraps it with a single `MESSAGE_READ` emit + `MESSAGE_STATUS_UPDATE` socket (`messageId: null, all: true` — every listener only reads `actorId`). UI = the `.ncm-pill--action` "Mark all read" pill at the right edge of the viewer's category-pills track (`data-action="mark-all-read"`, renders only when `counts.unread`, dashed border so it doesn't read as a filter).

Rules so the toast doesn't duplicate or render "Unknown — (no subject)":
- **Never** call `showMessageNotification` directly from a delivery handler, and never add a second toast/sound trigger on `MESSAGE_RECEIVED` — emit the event and let the one listener handle it.
- **Every** `MESSAGE_RECEIVED` emitter must carry the display payload: `from`, `fromName`, `fromActorId`, `fromContactId`, `subject`, `preview`, `priority`. The thin `{messageId, toActorId, fromActorId, priority}` shape was the original duplicate-toast bug. `showMessageNotification` resolves the sender as `fromName → linked actor name → master-contact name → from(email) → "Unknown"`.
- Stored message flags have **no** `fromName`/`senderName` field — only `from` (email) + `fromActorId`/`fromContactId`. Resolve names at read time.
- The document-sync emitter (`DocumentSyncBridge._onJournalPageCreated`) detects inboxes via `MessageRepository.identifyInbox` (flag-based — it previously keyed on a stale `isInbox`/`[NCM]` check and never fired). It **skips `-sent` copies and `status.spam`** and gates the toast on the recipient `actor.isOwner`, mirroring the socket path so a player never gets toasts for NPC or other-player mail. All four `DocumentSyncBridge` journal/page handlers use `identifyInbox`.
- Player→NPC mail never hits a player toast path; the **GM** gets its own toast via `MessageService._notifyGmOfNpcMail` (in `_deliverMessage`, gated by setting `notifyGmNpcMail`, default on). Spam-filtered mail (see spam filter section) is delivered **silently** — the socket notify is skipped and the doc-sync path bails on `status.spam`.

## Architecture: eddies (money) transfer

Eddies attached to a message transfer in **one** place — the recipient clicks **Claim** in the viewer (`MessageViewerApp._claimEddies`), which credits `actor.system.wealth` (CPR `value` + `transactions[]` ledger) and sets `status.eddiesClaimed`. The sender is debited at send (`MessageComposerApp._deductEddies`); the amount rides the message via the `eddies` flag until claimed. **Never auto-credit the recipient in the composer** — doing so caused a double transfer / duplicate ledger entry. `_creditEddies` survives only as the **sender refund** on send failure. `_claimEddies` guards re-claim (sent copy, already-claimed, a per-`messageId` re-entrancy lock) and resolves the target message by id from `_cachedMessages` (so thread-transcript entries claim correctly).

## Architecture: self-destruct messages

Composed via `selfDestruct = { mode, expiresAt, duration }` (modes `after_read` | `1h` | `6h` | `24h`; `_computeExpiry` returns null for `after_read`), persisted in flags. Triggered in `MessageViewerApp`:
- **`after_read`** — erased when the reader *leaves* the opened message: `_destroyAfterReadIfNeeded()` from `_selectMessage` (opening another) and `close()`.
- **Timed** — `_setupDestructFill` runs the countdown bar and fires `_playDestructExpiration` at 0, **and** fires immediately if a message is opened after it already expired. A GM-side **reaper** (`MessageService.reapSelfDestruct`, 60s interval registered in `registerMessagingSystem` postReady) erases timed messages whose expiry passed even if never opened (skips `after_read` + sent copies).

Both paths **hard-delete** (`permanentDelete`, not soft/trash) — self-destruct must be non-recoverable. **GMs never trigger self-destruct** (all three viewer paths early-return when `game.user.isGM`) so they can audit inboxes; timed cleanup still happens via the reaper.

## Architecture: unknown-sender spam filter

Opt-in (`spamUnknownSenderEnabled`, default **off**). At delivery, `MessageService._shouldSpamFilter(data)` may route mail to a **player's Spam folder** (sets `status.spam`) when the sender isn't in the recipient's contacts (`_isSenderInRecipientContacts` checks email / linkedActorId / masterContactId). Player-recipient only; skips sent/broadcast/already-spam. Tuners (Module Settings): `spamUnknownSenderChance` (%), `spamUnknownSenderScope` (`known` = sender is a real contact — a master-directory entry **by `fromContactId` or email**, or a registered character — but the player hasn't added them | `all` = also unknown addresses), `spamUnknownSenderExcludePlayers` (keep party comms out). Delivery is silent (see notifications rules). The viewer's `inbox` filter excludes `status.spam`; the `spam` filter shows it.

**`status.spam` must survive persistence.** `MessageRepository.createMessage` builds the stored status field-by-field; it must read `spam: messageData.status?.spam || false` (it was once hardcoded `false`, which silently dropped **every** spam route — the unknown-sender filter AND the Spam tab blast/templates/auto-spam — into the normal inbox). If spam "isn't landing" and the route decision logged true, check that block first. (`saved`/`deleted`/`scheduled` stay hardcoded `false` for new mail — only `spam` honors the caller.) Also note `_shouldSpamFilter`'s recipient gate is `toActor?.hasPlayerOwner` only — narrower than `SpamService.getPlayerActors` (`hasPlayerOwner` **or** an NCM `email` flag) — so it no-ops when the recipient isn't owned by a logged-in non-GM player (the solo-GM-testing trap). Left intentionally narrow: the only extra actors it'd catch are email-only NPCs, which don't check a spam folder.

**Scope `'known'` is the most common "100% chance but still in inbox" gotcha:** a completely unknown sender (a typed-in address not in the directory) is *intentionally skipped* under `'known'` — switch the scope setting to `'all'` to catch those. `_shouldSpamFilter` emits a `log.debug` at **every** early-return with the reason (recipient-not-player, excludePlayers, already-a-contact, scope-skip, chance-0, etc.) plus the final route/pass decision — turn on `debugMode` to see exactly why any message did or didn't land in Spam. The `'known'` check qualifies a sender via `fromActor` **or** a truthy `data.fromContactId` **or** `verifyContact(data.from).verified`, so a message from a real master contact filters even when its email is blank/synthesized (previously it only checked the email path).

## Architecture: Spam tab (generator, auto-spam, import/export)

The Admin → Spam tab (`SpamTab.js` + `templates/admin-panel/tab-spam.hbs`) is backed by `scripts/services/SpamService.js`. Spam templates are pure content (`fromName`/`fromEmail`/`category`/`subject`/`body`/`networkFilter`) — **recipients are chosen at send-time** via the chip UI, never stored on a template. Both the Quick Blast bar and each template's "Send to →" row render the same `spamPlayerActors` list.

- **Recipient list = `SpamService.getPlayerActors()`.** It returns every actor that is `actor.hasPlayerOwner` **or** carries an NCM `email` flag — the same "messageable character" definition used elsewhere (e.g. `OverviewTab`). **Do not** narrow this back to an explicit per-user `OWNER` entry: that silently returns empty for actors owned via *default* ownership or registered NPCs, which is the bug that made the chip lists show only the "All" chip and no players. The per-user owner lookup survives only to pick a chip color.
- **Auto-Spam by Network** config lives in the `spamAutoConfig` world setting (`{ [networkId]: { enabled, volume, categories } }`; volumes low/med/high/flood → count ranges via `getVolumeRange`). It is **wired but easy to mistake for broken**: `registerNetworkSystem.js` (ready, priority 109) listens for `EVENTS.NETWORK_CHANGED` and calls `SpamService.onNetworkConnect(networkId, actorId)` **only when** the event is `source: 'socket'`, **not** `isGMAction`, and carries an `actorId`. That means it fires when a **player with an assigned character** switches networks (their client broadcasts `NETWORK_STATE_CHANGED` with `game.user.character.id`) — **not** on the GM's own switches and **not** for a player without an assigned character. Delivered spam is pre-flagged `status.spam` (goes to the Spam folder, silent — no toast). Both the listener and `onNetworkConnect` emit `log.debug` with the skip/deliver reason (`debugMode`).
- **New / Edit template renders IN the preview pane** (2026-10-28, dev: "put that in the template preview section on the right") — the first branch of `.ncm-spam-lib__detail` (`spamShowCreator` → the form, else the selected template, else the empty state); the old §3 section under the library is gone. **Top row (2026-10-28):** Quick Blast · a **Category** dropdown (`<select data-spam-category>`, change listener in `SpamTab.onRender`; it replaced the row of category pills — the blast still draws from the picked category) · a **Templates** card (New + icon-only Import / Export) share the top (`.ncm-spam-top`, a container query: one line from 900px, else Quick Blast on its own slim line and Category + Templates on the next). **Recipients are ONE searchable multi ScopePicker** (`spamToPicker` in Quick Blast, `spamToPicker2` in the template Send bar, both over the same `_recipients`; a pinned "Every player" row selects all) — the chip-per-character lists are gone (dev: "I have a lot of characters"). `onToggleAll`/`onToggleRecipient` stay for other callers. Sim `test-spam-layout.mjs` (29, a real Handlebars render).
- **Import / Export templates** (`spamImportTemplates`/`spamExportTemplates` actions → `SpamTab.onImport/ExportTemplates` → `SpamService.importTemplates`/`exportTemplates`). Export downloads **only custom** templates (built-ins ship with the module) as `{ ncmSpamTemplates: 1, exportedAt, templates[] }`. Import accepts that envelope **or** a bare array, assigns fresh ids, validates the category, and de-dupes against existing customs by `fromName + subject` (case-insensitive) so re-importing is safe. Follows the ContactsTab blob-download / hidden-`<input type=file>` pattern.

## Architecture: GM awareness of player→NPC mail

`MessageService._notifyGmOfNpcMail` (called in `_deliverMessage`, GM client) toasts the GM when a **player-owned sender → non-player recipient** (gated by `notifyGmNpcMail`). The **NPC Inbox** triage panel in Admin → Messages (`MessagesTab._gatherNpcInbox`, actions `toggleNpcInbox`/`npcInboxFilter`/`npcInboxReply`) groups player→NPC mail by NPC.

## Architecture: anonymous send (GM)

A GM-only composer option (`anonymousEnabled`) that masks the sender: the recipient sees a masked avatar + alias and **cannot resolve the real identity** (it's stored GM-side only — *truly hidden*, not cosmetic). Gated by `game.user.isGM && anonSendEnabled`. Six world settings under "Anonymous Send": `anonSendEnabled`, `anonDefaultStyle` (default **scrambled**), `anonAllowRepliesDefault`, `anonTraceEnabled`, `anonTraceDV` (15), `anonTraceSkill` (a CPR-skill dropdown from `SKILL_MAP`). The message carries an `anonymous` block `{ enabled, role?, style, alias, maskedEmail, allowReplies, traceable, traceDV, traced }`.

**Truly-hidden data model — the masking policy lives in `MessageService`, not the repository.** `MessageRepository` only persists/reads the `anonymous` block (createMessage flags + `_pageToMessage`) and uses the alias for the page name (`_resolveSenderName`). In `_deliverMessage`, `_maskAnonForRecipient(data)` builds a clone with the real identity stripped (`from`=masked email, `fromActorId`/`fromContactId`=''); that clone is used for **both** the recipient inbox copy **and** the recipient `MESSAGE_NOTIFY`/toast. The **real sender survives only on the GM-owned `-sent` copy** (the original `data`). So the recipient's player-readable page never contains the real id. Anonymous mail is **spam-filter exempt** (`_shouldSpamFilter` bails — an "unknown" sender would otherwise always match).

**Masked display is one shared resolver + one CSS component.** `resolveAnonSender(message,{isGM})` (helpers.js) returns the masked view for non-GM (and for a GM reading the scrubbed copy — a known limitation; GMs audit via the `-sent` copy, which reveals + tags **SENT ANON**). All read paths call it: `MessageViewerApp._enrichMessageDisplay` (detail/list/thread — exposes `isAnonMasked`/`isAnonRevealed`/`anonStyle`), `NotificationService.showMessageNotification` (alias), `DocumentSyncBridge._onJournalPageCreated` (carries `anonymous` + alias in the MESSAGE_RECEIVED payload — the doc-sync toast path reads the already-scrubbed page). Avatars render via the `ncm-anon-avatar` Handlebars helper (registerTemplates.js) → pure-CSS layers in `styles/components/anon-mask.css` keyed by `data-anon-style`. **The mask never uses a real photo** — Filtered/Scrambled obscure a neutral silhouette, so nothing leaks. Four styles: `filtered` / `scrambled` (default; heavy static + jitter + tear + RGB) / `ghost` (blobby silhouette) / `monolith` (SEELE "SOUND ONLY" slab). Add-to-Contacts is hidden on masked mail; the `.ncm-anon-badge` shows ANON / SENT ANON / TRACED.

**Reply routing (masked both ways).** `buildReply` detects `originalMessage.anonymous` (role≠recipient, not traced) and returns an `anonReply` descriptor `{ parentMessageId, alias, style, maskedEmail }` with **no** real target — the player can't know it. `sendMessage` and `DataValidator.validateMessage` both skip the recipient-required + verification gates when `data.anonReply`. GM-side `_deliverMessage` calls `_resolveAnonReplyTarget(parentMessageId)` (scans journals for the `<id>-sent` page → real sender), sets the true `toActorId`, and delivers; the replier's **own** sent copy is re-masked via `_maskAnonReplyForSender` → an `anonymous` block with **`role: 'recipient'`** so their outbox can't reveal who they answered (`resolveAnonRecipient` masks the TO; `resolveAnonSender` skips role `'recipient'`). The composer shows a locked masked recipient chip (`anonReplyTo`). One-way mode (`allowReplies` false) → `anonRepliesBlocked` hides Reply/Quick-Reply and shows a "No Reply" chip.

**GM reply within an anon thread pre-ticks Anonymous Send (toggleable).** When a **GM** opens a reply, the composer calls `MessageService.getThreadAnonConfig(originalMessage)` (scans journals for the thread's original GM-owned anon copy — `anonymous.enabled && role !== 'recipient'`, matched by base `messageId`/`inReplyTo`/`references`/`threadId`, preferring the thread-root) and, if found, **pre-enables** `anonymousEnabled` + seeds `anonStyle`/`anonAlias`/`anonAllowReplies`/`anonTraceDV` from that block (`_anonConfigFromBlock`). It's only pre-filled — the GM can untick it per reply (deliberately not forced). Gated `game.user.isGM && _isAnonFeatureEnabled()`, so players never get it (all anon **sending** UI — toggle, options strip, masked identity — is behind `isGM`; a player only ever sees the locked `anonReplyTo` chip).

**Composer Send button must be re-enabled on every `_onSend` exit path.** `MessageComposerApp._onSend` disables the send button (`disabled=true` + `--disabled`, which is `pointer-events:none`) at the top; it must be restored in the `finally` block. It previously only restored on the eddies-deduction early-return, so a single failed/exception send (the anon-reply path is prone — the GM resolves the hidden target) left the button dead to mouse clicks while Ctrl+Enter still worked (the keydown handler calls `_onSend` directly, bypassing the dead button). That's the "keyboard sends but the button won't click" signature.

**Trace-to-unmask (GM-mediated).** A "Trace" button (`canTraceAnon`) runs `MessageViewerApp._traceAnonSender` → skill dialog + `skillService.performCheck(actor, anonTraceSkill, {dc: anonymous.traceDV})`. Result is reported to the GM via `SOCKET_OPS.ANON_TRACE_REQUEST` (player→GM; the client reports success — trust model matches the existing relay). `MessageService.handleAnonTraceRequest` → `revealAnonSender(messageId, inboxActorId)` resolves the real sender (`_resolveAnonReplyTarget`) and **patches the player's page** with real `fromActorId`/`from`/`fromContactId` + `anonymous.traced=true`; the update syncs back (`DocumentSyncBridge._onJournalPageUpdated` → `MESSAGE_STATUS_CHANGED` → viewer re-render) and the mask resolves to the real identity. `resolveAnonSender` and `buildReply` both bail when `traced` (so a traced sender shows normally and replies directly). GM clicking Trace force-reveals (no roll). Sounds: `trace-fire` (attempt), `shard-decrypt` (reveal), `hack-fail` (miss).
- **Two trace bugs that bit and how they were fixed (don't reintroduce):** (1) `revealAnonSender` must rewrite the **whole** `anonymous` block (`{...current, traced:true}`), NOT a nested `anonymous.traced` dot-path via `updateMessage` — the nested-flag update is unreliable (the standing CLAUDE.md gotcha) and the **player-side unmask hinges entirely on `traced` landing** (the player masks whenever `enabled && !traced`, regardless of `fromActorId`; only the GM-reveal path keys off `fromActorId`, so the GM saw it "work" while players stayed masked). (2) `handleAnonTraceRequest` must **check `revealAnonSender`'s result** before toasting "identity revealed" — it used to toast success unconditionally, so a failed reveal (e.g. missing `-sent` copy) looked like it worked while nothing changed. On failure it now warns the GM with the reason.

**CSS gotchas this hit:** new composer buttons (`ncm-composer__anon-pill`/`anon-reply`) MUST be added to the composer button-reset lists in `message-composer.css` or they render as Foundry's full-width native buttons; viewer avatar hosts (`.ncm-viewer__avatar--anon`) need `overflow:hidden` because they set `border-radius` but rely on a rounded `<img>` (the absolutely-positioned mask isn't otherwise clipped); the `.ncm-anon-badge` needs `vertical-align:middle`+`align-self:center`+`line-height:1` or it rides high on the text baseline.

## Architecture: inbox window title + theme extras

The inbox window title is **personalized and diegetic**: `MessageViewerApp.get title()` → `{handle} // {agentName}` (handle = NET email local-part, else actor name; `agentName` from `playerTheme.agentName`, default "Agent"). The singleton viewer switches characters, so `_onRender` re-syncs the `.window-title` element (AppV2 builds the frame once). Boot splash + Character Select keep the "Night City Messenger" brand. The Theme Customizer **Text panel** (tab labeled "Text" — formerly "Fonts"; the internal `data-tc-tab`/`activeTab` key is still `fonts`) holds the **Agent Name** field, the font selectors, text size, and a **contrast** slider (70–140%, step 5, default 100). The Agent Name row is wrapped in `.ncm-tc__font-section` so it shares the panel's 16px indent (it's the only `.ncm-tc__srow` outside that section otherwise, which left it flush-left). Contrast — `ThemeService.applyTheme` tone-maps the bg/text/border palette by spreading their **OKLCH lightness** around a pivot of **0.42** (`CONTRAST_SPREAD` in constants.js; `adjustLightness` in helpers.js), **not** a CSS `filter: contrast()`. The filter approach distorted images/wallpaper and drifted saturation; the palette spread leaves images untouched and preserves hue/chroma (neon stays neon), and accents (`primary/secondary/accent`) are deliberately excluded. It always recomputes from base prefs/preset, so dragging can't compound. `textMuted`/`border` aren't user-overridable or in any preset, so `CONTRAST_SPREAD` carries their variables.css defaults as the `base` fallback. Range is deliberate: `text-primary` whites out ~110% and `bg-deep` blacks out ~142%, so 140 is a clean high-contrast ceiling without crushing the bg depth layers (don't exceed ~150); the 70 floor is a soft/dim mode for glare sensitivity. No JS clamps the value — the slider `min`/`max` in `theme-customizer.hbs` are the only gates. The old `--ncm-contrast` var + reset.css filter rule are gone. ## Architecture: message threading / conversation view

Clicking the **`Thread · N`** pill in the message detail (a `<button data-action="toggle-thread">` in the subject strip) swaps the single-message detail pane for a **conversation transcript** — every message in the thread, oldest→newest, on a timeline rail, with the message you came from highlighted and auto-centered. Back returns to the single message. This is the only "Option C" full-transcript view; it lives entirely inside `message-detail.hbs` as an `{{else if message.threadExpanded}}` branch of the locked/encrypted/normal conditional chain (no separate template/part).

**Thread state is a single instance flag.** `MessageViewerApp._threadExpanded` (default false) is flipped by `_toggleThread()` and **reset to false in `_selectMessage`** so opening any message — including an entry's "open" button inside the transcript — returns to the single-message view. `_getEnrichedMessage` attaches `threadInfo` (badge count), `threadExpanded`, and `threadEntries` (only built when expanded). `_onRender` centers `.ncm-viewer__thread-entry--current` in `.ncm-viewer__thread-scroll`. Per-entry bodies are independently access-checked via `messageAccessService.checkAccess` so encrypted/network-locked messages stay redacted *inside* the transcript, exactly as in the single view.

**Thread membership is resolved, not a raw `threadId` filter.** `scripts/utils/threading.js` (pure, no Foundry globals) merges a flat message list into conversations with a union-find over **four signals**, any one of which links two messages:
1. `threadId` — canonical group id
2. `inReplyTo` — points at the parent's id
3. `references[]` — full ancestor chain (survives forward-of-forward, reconstructs even if `threadId` is lost)
4. **subject + shared counterparty** — fuzzy fallback: identical `normalizeSubject()` (strips `RE:`/`FWD:`/`FW:`) **and** an overlapping `counterparties()` (the *other* party from the viewing actor's perspective — the actor's own ids are excluded, since they're in every message). Rescues forwards-to-strangers, hand-composed same-subject mail, and legacy pre-`references` messages.

Signal 4 is the only one that can over-merge (two unrelated "FWD: invoice" chains from the same fixer). It's gated by the world setting **`subjectThreading`** ("Smart Conversation Grouping", default on; strings in `en.json`). Off = strict reply/forward-link threading only. Both `_getThreadInfo` and `_buildThreadEntries` route through the resolver via the shared `_threadOpts()` helper. IDs are compared on their **base** form — `baseId()` strips a trailing `-sent` so a sent copy and its received twin count as one identity. Within a single actor's mailbox each logical message appears once (the twin lives in the other actor's inbox), so no dedup is needed.

**Forwards now connect by design.** `MessageService.buildForward` carries `threadId` + `inReplyTo` + `references` (the new recipient simply sees a single-message thread until they reply); `buildReply` carries `references` too. Both build the chain via `_buildReferences(originalMessage)` (appends the base parent id to the de-duped ancestor list). `sendMessage` never leaves `threadId` undefined — it falls back `references[0] → inReplyTo → messageId`. `references` is persisted/read by `MessageRepository` (`createMessage` flags + `_pageToMessage`), defaulting to `[]` for old messages. **Note:** `MessageRepository.getThread()` (used by the macro API) still keys purely on `threadId` — it was left for back-compat and is *not* the resolver; the transcript UI does not use it.

## Architecture: responsive message viewer

The Message Viewer adapts to the viewer's **own width** via CSS **container queries** — `.ncm-viewer { container-type: inline-size }` (message-viewer.css §23), not viewport `@media`. Breakpoints: wide >860 (full two-pane), medium ≤860 (icon-only header buttons, avatar-only identity, HUD drops Location), narrow ≤520 (single column; pill→dot+%; primary tabs + category pills icon-only via the `font-size:0` collapse trick; denser rows). The single-column switch is the only JS: `_onRender` sets `data-pane` on `.ncm-viewer` (`selectedMessageId ? 'detail':'list'`); narrow CSS shows one pane and the `.ncm-viewer__mobile-back` button (action `mobile-back`). Window min-size clamped in a `setPosition()` override. When narrow, the list-panel inline `width` is overridden with `width:100% !important` (placed after the `--list-collapsed` rule to win on specificity/order).

The header-condense breakpoint is **860, not 720** (raised): the full header layout (identity name+email, net pill, clock, scene, 4 action buttons) needs ~860px, so between 720–850 the flexible parts (identity name, scene) collapsed to zero and the **fixed** parts (avatar, divider, net-dot, action icons) overlapped — the expand-chevron painting over the net pill's dot, buttons spilling off the right. Condensing at 860 skips that dead band. (The single-column switch stays at 520.) Verified by rendering the header at a range of widths via headless Chrome — the reliable way to debug these container-query bands without launching Foundry.

**Network selector shows only reachable networks.** `MessageViewerApp._buildSelectorNetworks()` still computes each network's `state` ('active'|'available'|'locked'|'unavailable') but then `.filter()`s out `unavailable` and 0% signal — like real life, you don't see networks you can't reach. `locked` (in range, needs auth) stays visible. `availableCount` derives from the shown list. Dead zones return `[]` (jammed state); a scene with networks configured but none reachable shows a "No Networks in Range" empty state (distinct from the dead-zone state) in `network-selector.hbs`.

**Network selector dropdown rows (the "Available Networks" popup).** Redesigned for legibility (`network-selector.css` / `network-selector.hbs`): each row carries `--net-c` (its configured color) inline; the **left accent stripe + active-row tint + 4-bar signal meter** all use that color (active row glows, locked rows mute the bars to grey). ## Architecture: paste hygiene + Import from Journal (2026-10-23)

Tester: pasting a journal page into a shard **Document** gave black text on the dark theme and white blocks, typing afterwards stayed black, the light theme was no better, and "one paragraph per box" made bringing journals over impractical (PDF copies arrive hard-wrapped on top). **Root cause: a browser's default paste writes the SOURCE's computed styles inline** (a journal is `#191813` on parchment → every span lands with its own `color`/`background-color`), and a container's `color … !important` can never beat a child's inline declaration; the block was saved as raw `innerHTML` and rendered raw, so players got it too. Typing "stayed black" because the caret was inside the pasted span.

- **`scripts/utils/richText.js` is the ONE pure module** (no Foundry/DOM; sim `dev/tools/sims/test-rich-paste.mjs`, 96 checks). `cleanHtml(html, {mode, colors})` is a tokenizer + tolerant tree whitelist cleaner. Modes: `inline` (a list item/caption), `block` (a Document text block: inline + `p`/`br`/lists; `div`→`p`, headings→bold line, blockquote/pre→p, img/hr/tables dropped), `rich`/`mail` (a message body: + headings/blockquote/pre/hr/img/tables). **Colour policy: a colour survives ONLY if it is the module's** — a `var(--ncm-*)` value or a hex in `RICH_TEXT_PALETTE` (the shard RTE's swatches; `RTE_COLORS` now aliases it). At PASTE time even palette colours are dropped (`colors:'none'`). Also kept: `font-weight/style`, `text-decoration`, margins/paddings, relative `font-size` ≤ 2em, `ncm-*` classes, `data-label`, safe `href`/`src` (no `javascript:`/`data:`). The Google Docs `<b style="font-weight:normal">` wrapper is unwrapped, Word's `o:p`/comments dropped. **Block contract: a one-paragraph block is bare inline HTML, a multi-paragraph block is a `<p>…</p>` sequence** (Enter in the editor writes `<div>`s → normalised to `<p>` at save).
- **Three layers, never just one:** PASTE (the editor's `paste` listener: shard Document blocks via a delegated listener on `.ncm-docpage` → `_onDocPaste`; the shard message RTE → `_onRtePaste`; the Agent mail editor in `MessageComposerApp._setupEditorSync`), SAVE (`DataShardComposer._collectDocRow` cleans `block`, `_collectEntryData` cleans the body `rich`), RENDER (`ContentRenderers` document enricher cleans text `block` + list items `inline`; a plain message body `rich`; `MessageViewerApp._renderMessageBody` cleans `mail` BEFORE the encrypted-block regex — attribute order is preserved so it still matches; `TerminalViewerApp._sanitizeBody` now routes through it, so a bold line/list no longer flattens to plain text on the machine). Render-time cleaning heals shards and mail saved before this shipped with no migration. **A new contenteditable surface = a paste listener + a save clean + a render clean**; the sim counts them.
- **Paste → blocks (`pasteToBlocks` / `htmlToBlocks`)**: headings start a section and become the heading of whatever follows (text, a list, a figure); consecutive paragraphs stay in ONE text block (a block is a SECTION, not a sentence); lists/figures/quotes are their own blocks; a table becomes one paragraph of rows; `@UUID[…]{Label}` enrichers flatten to the label (`enrichers:true`, the journal-import path). **Plain text (a PDF viewer puts only text on the clipboard) is REFLOWED** (`reflowText`): hard-wrapped lines rejoin (a non-sentence-ending line ≥55% of the paragraph's longest line, or a lowercase successor), `word-` + lowercase dehyphenates, ligature glyphs (ﬁ ﬂ ﬀ) expand, NBSP/soft-hyphens normalise, bullet runs become list blocks, a block whose longest line is under 40 chars keeps every break (an address, verse), and a bare page number (`12`, `Page 3 of 9`) is dropped only when the paste has ≥3 paragraphs. The reflow GUESSES, so **an after-paste strip (`.ncm-docpaste`) offers Undo and, when several paragraphs landed in one block, "Split into N blocks"**; a per-block `docSplitBlock` tool (`has-paras` class, shown only where it applies) does the same later. Undo rebuilds the list from a `_collectDocBlocks()` snapshot — the native undo stack cannot restore blocks that live outside the contenteditable.
- **Import from Journal** (`docImportJournal`, the Body fieldset's actions row): the shared name picker over every journal TEXT page (sub-line = journal · folder path, chip = top folder), `fromUuid` → `page.text.content` → `htmlToBlocks(…, {enrichers:true})`; Replace/Append dialog when blocks already exist; an empty Title takes the page name.
- **Viewer/editor fixes that rode along:** the text block renders as `<div class="ncm-ct-doc__p">` (a `<p>` cannot hold paragraphs; CSS + the declassified tint cover both); `.ncm-docpage` background is `--sp-bg-deep` (was a literal `#14141c` — near-black under clean-light); the editor's heading input wears the viewer's accent mono look (it was bright display text, so "white while typing, orange displayed" read as a bug); `.ncm-docpara__t *` inherits colour/background so a legacy pasted block reads correctly in the editor before its first save; the Agent viewer gained rules for h1–h6/blockquote/code/pre/hr/ul/ol/img/table in mail bodies (they rendered in Foundry/CPR defaults); the Agent composer's monospace tool writes a bare `<code>` (its inline literal hex ignored the theme). List items used to render raw `{{{this}}}` with no escaping (a typed `<3` broke the list) — cleaned `inline` now.
- Probe: `dev/mockups/doc-paste-probe.html?t=clean-dark|clean-light|high-contrast&raw=1&strip=1&pdf=1` lifts the REAL `_docBlockHtml` out of the composer source (CRLF-safe regex — the repo is CRLF on Windows), renders the real `content-body.hbs`, and reports worst text contrast in `<title>`: the raw paste measures **1.06:1** (the tester's screen), cleaned **8.81:1** dark / **6.79:1** light. **Not live-tested in Foundry.**

## Architecture: embedded media (audio/video)

`resolveMediaEmbed(rawUrl, mediaType)` in `helpers.js` is the **single** source resolver, shared by shards and normal messages. It returns `{ kind: 'none'|'native'|'embed', src, isVideo }`: YouTube/Vimeo links → `embed` (iframe, `src` rebuilt from the parsed video ID — never raw user HTML); direct file/URL → `native` (`<video>`/`<audio>`, audio-vs-video inferred from extension, else `mediaType`); non-`http(s)` schemes (`javascript:`/`data:`) → `none`. Two surfaces:
- **Shard AV Log** content type — `mediaUrl` field added to the composer (`DataShardComposer`, with a `browseMedia` FilePicker) and the player wizard. `ItemInboxApp._enrichEntry` resolves it; `item-inbox.hbs` renders player-or-waveform.
- **Normal messages** — a new media **attachment** (`{ isMedia: true, mediaUrl, mediaType }`) via the composer's "Embed Audio/Video" toolbar action (`_onAttachMedia`). Reuses the existing `attachments[]` persistence (no repo/service change). `MessageViewerApp` splits `isMedia` attachments out of the cards/encrypted-classifier and `_buildMediaEmbeds` renders inline players in `message-detail.hbs` (normal/unlocked branch only — locked/encrypted messages don't leak the player).

## Architecture: every NPC has an inbox — the GM's roster (2026-11-02)

**A sheetless NPC's inbox is keyed by its directory id**, and `viewer.actorId` holds that id, so **`viewer.actorId` is not always an actor**. An alias shares its main's inbox (`identityInboxId`). `scripts/utils/inboxRoster.js` is the one list: `buildInboxRoster` (pure; one row per MAILBOX, aliases only make a row searchable) + `gmInboxRoster` (reads every journal once for the mail counts). Identity drawer → **Switch inbox** (`_paintInboxSwitch`, GM only, built when the drawer opens because the viewer redraws on every click; search filters in place, Enter opens the first; Recent in localStorage `ncm.inbox.gmRecent`). Character Select → **NPCs** section (`_buildNpcList`; a GM's unowned `character` actors moved there). `composeMessage` turns a contact id passed as `fromActorId` into `fromContactId`; it read "Unknown" before. `ConversationService._identity` / `joinChoices` accept a contact id. Players' lists are unchanged. Sim `test-inbox-roster.mjs`. Not live-tested; the Calls tab from a sheetless NPC's inbox is unchecked.
