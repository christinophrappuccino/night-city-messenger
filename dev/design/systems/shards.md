## Architecture: who may author shards (the encoder gate)

**There is ONE answer — `canEncode(actor)` (helpers.js) — and every door reads it.** The Agent's Encode pill (`MessageViewerApp` context flag), the item right-click + convert button + unconvert (`ShardSheetOverride.canAuthor`), the Program Deck's blank cartridge, the `game.nightcity.openEncoder` funnel, and `ShardEncoderApp._permissionProblem()` (which runs on open AND again before the roll, because the operator is switchable from inside the window). A character who does not qualify sees **no button**, never a button that opens and refuses.

It returns `{ok, reason, off}` — `off` distinguishes "the GM has not switched player authoring on" (a world setting) from "this character does not qualify" (a gate the GM wrote), because the fixes differ.

**The gate is `encoderConfig.gate`, byte-for-byte the shape of `DEFAULTS.OPERATOR_GATE`, evaluated by the same `canOperate`** — mode / logic / roles+roleLogic / skill+min / itemGroups (OR-of-ANDs) / actors allowlist / allowGM. No second gating dialect. It is a **separate object** from the terminal operator gate on purpose, so "anyone may operate a terminal, only a Tech may forge a shard" is sayable.
- **`canOperate` gained `{ standalone: true }` for exactly this.** Its normal path merges `DEFAULTS ← the operatorGate SETTING ← override`, so passing the shard gate as a plain override would silently import the terminal's rule for every field the shard gate omits — two gates that look independent in the UI but are not. It also takes `label` (default `'Operator tools require'`); the encoder passes `'Encoding a shard requires'`.
- **Gated with nothing configured is INERT and says so.** `gateSummary()` reports `{gated, inert, parts}` and the GM card prints the live answer ("Right now a character qualifies by: **Tech / Netrunner OR Interface 4+**"). No accidental lockout.
- Sanitising lives in `sanitizeGate` inside the pure `EncoderModel.js` (sim-testable): unknown mode → `anyone`, empty groups and nameless entries **dropped** (an unsatisfiable gate reads as a broken button), rank coerced to a non-negative integer.
- GM card: **Admin → Shards → Player Authoring → "Who can make them"** tab. Role/gear/character choosers are the searchable **`showNamePicker`** dialog, not `<select>`s.

**`ShardConversionFlow` is RETIRED (2026-09-22)** — the file, `templates/dialogs/shard-conversion.hbs`, and both `shard-conversion.css` copies (the admin-panel one was already an orphan, never imported) are deleted, along with `TEMPLATES.SHARD_CONVERSION`. The three settings only it read — **`playerShardFloor`, `playerShardSkill`, `playerBlackICE`** — are no longer registered: a `config: true` setting nothing reads is a knob in Module Settings that silently does nothing. Their Setting documents stay on disk, inert (the namespace-migration precedent). `playerBlackICE` had already been orphaned; the Encoder asks `encoderConfig.lock.blackIce`. The old two-route statics (`encoderEnabled` / `playerAuthoringOn`) are gone with it — one route, one question.

**`scripts/utils/namePicker.js` is THE searchable world picker — every dropdown over a world collection goes through it (2026-10-20).** `showNamePicker({title, hint, entries, allowNone, selected, chips, placeholder, taken})` + `documentEntries(docs, {group:'folder'|'type'|fn, sub, note, fallbackImg})` + `folderPathOf(doc)` + the pure `matchesPicker(entry, q, group)`. ## Architecture: shard theming

**The shard palette is DATA, not CSS.** Each `SHARD_PRESETS` entry carries an 11-key `palette` (the `COLOR_VAR_MAP` keys); `buildShardThemePrefs(theme, presetKey, {textScale, contrast})` (helpers.js, the twin of `buildTerminalThemePrefs`) layers the shard's own overrides on top; `ItemInboxApp._applyShardTheme` applies it element-scoped through `ThemeService.applyTheme`. The twenty `--sp-*` tokens are **derived from `--ncm-*` in ONE place** (the block at the top of item-inbox.css, shared with `.ncm-data-shard-composer` and `.ncm-malware-workshop`).

This replaced `styles/themes/shard-presets.css` (deleted), which hardcoded all twenty tokens for each of eight presets. Three things that fixed:
1. **The per-shard contrast slider did nothing on 8 of the 9 presets.** Contrast writes `--ncm-*`; a preset's hardcoded `--sp-*` never read them.
2. **`--sp-accent` read `var(--ncm-color-secondary, #19f3f7)` — a variable that does not exist**, so even the blank preset ignored the player's accent and fell through to literal brand cyan (same for `--sp-bar`, `--sp-chip-active-text`).
3. **Typed content could never follow the shard's theme** — the 18 content types render on `--ncm-*` by design.

Verified by `dev/mockups/shard-theme-probe.html` (renders all nine presets through the real ThemeService into the real cascade, diffs every token against the old stylesheet, reports worst drift in `<title>`): **10 of 11 mapped tokens reproduce EXACTLY**; the only drift is `--sp-text-muted`, now a `color-mix` of textMuted toward the accent so one formula reproduces each preset's tinted footer (Δ29–78, same hue family). Small drift for a clearer derivation was the agreed trade.

**`COLOR_VAR_MAP` gained `border` + `textMuted`** — shard presets carry a tinted border and footer as identity. `CONTRAST_SPREAD` had already tone-mapped both under those exact key names, so this closed a half-built contract. No THEME_PRESET defines them, so the player theme is unchanged until someone sets an override, and `variables.css` keeps the `:root` defaults. Adding a key here grows the player Theme Customizer grid and the terminal Theme tab automatically — they all iterate the map.

**Where things are written, and why:**
- The **palette goes on the APP ROOT**, not `.ncm-item-inbox`: the window FRAME sits outside the viewer element and must follow the shard (`.ncm-app.ncm-item-inbox > .window-header` — **compound**, because this window's app root carries both classes while the template root repeats `ncm-item-inbox`; the descendant form is the inner element), and `.ncm-item-inbox` owns `--ncm-text-scale` as a calc of two knobs that `applyTheme` would stomp with a single number. Text scale is passed as the **composed** player×shard product so the header matches the body.
- **Contrast is applied separately, onto the inbox, with `{ baseFrom: appRoot }`** so the tone-map spreads THIS shard's colours (or the player's, when the shard has none) rather than the brand constants `applyTheme`'s own contrast pass falls back to. The viewer therefore passes `contrast: 100` into `buildShardThemePrefs`.
- `config.theme` has **three legal shapes** and the builder tolerates all of them with no migration: the palette object (`{colors, fonts, wallpaper, wallpaperStrength}`), the dead `'classic'`/preset-key **string** `_onSaveConfig` used to write, and the preset **CHROME block** (`accent`/`headerBg`/`watermarkIcon`/`colorTemp`) the Encoder writes — which has no `colors` key, so they coexist.

**Config → Theme tab** (`item-inbox-config.hbs` `data-panel="theme"`, wired by `ItemInboxConfig._wireThemeTab`). Live preview strip, preset cards, an 11-key colour grid with per-key reset, font selects, Text Size + Contrast (moved here from Identity), wallpaper + strength, and the two libraries.
- **The draft contract: theme controls are UNNAMED and data-keyed (`data-stc`), mutate `this._themeDraft`, and NEVER re-render.** `_prepareContext` reads the STORED config, so a `render()` would discard unsaved edits in Identity/Security/Network/Systems/Boot. Everything repaints by hand (`_repaintThemeTab`, `_rebuildSavedThemeList`, `_rebuildFullPresetList`). The one exception is `fullApply`, which writes immediately after a confirm that says so.
- **A cleared override is stored as `''`, never deleted.** `updateConfig` merges through `mergeObject`, which would keep a removed key's old value; `''` is falsy so the builder falls through to the preset exactly as an absent key would.
- The preset **cards drive a hidden `<input name="preset">`** — that is what `_onSaveConfig` and `_onApplyPreset` read.
- Only the borrowed `.ncm-tc__*` widgets are reused; their **button/select resets are root-scoped per host**, so `.ncm-item-inbox-config` had to join those selector lists in theme-customizer.css. Keep them in step.

**Two libraries, and the security rule that separates them:**
- **`shardThemePresets` — saved LOOKS.** Palette, fonts, wallpaper, plus a `basePreset`. Carries **no security block by construction**.
- **`shardPresetLibrary` — full shard presets.** Look + startup + identity, and the **security block ONLY if the GM ticked the box when saving** (unticked by default). An entry that carries one is chipped `SECURITY` on its row and the apply confirm names it. `SHARD_SECURITY_KEYS` is an explicit list, so a config field added later does not silently start travelling inside a preset. Import never auto-applies.
- The reason for all of it: several shipped presets ship Black ICE at DV 20, and reaching for "make another one like this" must never arm a shard without saying so. Same rule as the Encoder never handing `convertToDataShard` a preset KEY.

**Players can wear the GM's looks.** The Encoder's Look row offers the built-in presets and the saved looks (`encoderConfig.look = { presets, savedThemes }`, both default on, each gating its own source). A saved look and a preset are **mutually exclusive picks** — two lit chips claiming to set the same thing reads as a bug. `_lookConfig` layers the saved palette onto the preset chrome (`{...out.theme, ...t}` — no shared keys) and still carries **no security**.

**Optional depth — three real rules (2026-09-22).** `encoderConfig.optional` was four bare booleans that nothing read. It is now `{gear, time, assist}`, each an object with a rule behind it; **`signature` was REMOVED** rather than left as a dead switch (dev: "lets just remove that"). `sanitizeOptional` **lifts a legacy boolean into `{on: <bool>}`** over the defaults, so a world that stored the placeholder shape upgrades with no migration.
- **gear** — `gearBonusFor(cfg, carriedNames)`. Matched by item name the space/punctuation-insensitive SkillService way. `stack: 'best'` (default) counts only the most useful item; `'sum'` adds them, which is how a +9 happens by accident. It returns `from[]` so the readout can NAME what helped — a silent bonus is one the player cannot check, argue with or learn from.
- **time** — `timeCostFor(cfg, dv)` = base + perDV × DV, rendered by `formatMinutes`. Charged whatever the outcome: a rejected forgery still took the afternoon. Advancing the clock is a GM-only write, so `_spendTime()` moves it when it can and **always reports the cost**, whispering the GM when a player cannot move it themselves. Both the clock write and the report are try/caught — running out of permission must never cost a player the shard they just rolled for.
- **assist** — `assistBonusFor(cfg, {helperRank})`. Candidates come from `getPlayerCharacters()`; a helper who fails `requireSkill` is still OFFERED but chipped "no help" and refused on click, so the rule teaches itself instead of leaving the player wondering why the number did not move.

**Every bonus reaches the roll through ONE accessor — `ShardEncoderApp._bonuses()`** (perk + gear + assist). `_base()`, both ladder previews and the roll's `modifier:` all read it. A bonus added at a call site is exactly how the readout and the roll end up quoting different numbers; the sim asserts no preview still adds `_blank().perk` by hand.

**The shard viewer's window title is the shard's own name** — no `DATA SHARD:` prefix (dev, 2026-09-22). It prefers `config.shardName`, then the item name.

**The Player Authoring window's copy is PLAIN, per the standing rule that GM tools use plain language** (in-world vocabulary belongs on player-facing immersive surfaces). Every section subtitle says what the control does, not why it is interesting — the aphoristic first pass read as confusing to the dev. Two lines were also factually stale, claiming the Lock and Content stages were "not built yet" after they shipped; when a stage lands, grep this window for its copy.

## Architecture: data shard conversion + entries

Two convert paths, both gated through `ShardSheetOverride._launchConversionFlow(item, actor)` (the right-click "Convert to Data Shard" on actor sheets and the Items directory):
- **GM** converts **instantly with the default config** — `DataShardService.convertToDataShard(item)` (no overrides) — mirroring the Admin → Shards tab "Convert" button. **No wizard.** The GM customizes afterward via the "Configure Shard" context option. (Pre-change the GM also got the player wizard; that was deliberately removed.)
- **Players** get the **Shard Encoder**, gated by `canEncode(actor)` (see the encoder-gate section). It opens on the BLANK stage with the item seeded — deliberately NOT `stage: 'program'`, which used to force every item right-click into the Program branch, so a player who wanted to forge a dossier landed on a page asking which program to build. (The tier-gated `ShardConversionFlow` wizard that used to live here is retired.)

**Admin → Shards → "New Blank Shard" CREATES a fresh world Item** (`ShardsTab._createBlankShard`: CPR `gear` type when offered, name auto-numbered, default icon), converts it with the blank preset, and opens Configure — it used to open the same pick-an-item dialog as the preset quick-create buttons, so it read as a duplicate of "Convert Item" (dev, 2026-09-10). The preset buttons still convert an EXISTING item.

**Shard entries must be written through `DataShardService.addMessage(item, entryData)`** — never by hand-writing a journal page. The reader `DataShardService._pageToShardMessage` (used by `getShardMessages`/`getVisibleEntries`, which the `ItemInboxApp` viewer renders) **discards any page whose flag `type !== 'shard-message'`** and keys on `messageId`/`contentType`. `addMessage` stamps exactly that shape — as does the Encoder, via `programToEntry` / the composer's collected `entryData`. (A prior bug in the retired conversion wizard wrote a raw page with `entryType`/no `messageId` and the entry was silently invisible; that is the failure mode to watch for in any new writer.) **Per-entry `icon`/`accentColor` are NOT stored** — the viewer derives icon/accent from `CONTENT_TYPE_INFO[contentType]`.

**Players can't write to the GM-owned shard journal** (created `OBSERVER`). So the wizard's initial entry **rides along in the conversion socket relay**: `_requestPlayerConversion(item, config, entryData)` → `SHARD_CONVERT_REQUEST` carries `entryData` → the GM handler in `SocketHandlers.js` runs `convertToDataShard` then `addMessage` in one round-trip (entry failure is non-fatal). Eddies debited up-front in the wizard are **refunded on any conversion failure** (`_refundActorWealth`).

**Integrity is opt-in per shard, not a regression.** It renders only when `config.integrity.enabled` is true. `DEFAULTS.SHARD_CONFIG.integrity.enabled` is **`false`** and **no preset enables it** (an Encoder blank tier can, via its `integrity` checkbox), so default-converted shards show no bar until the GM ticks Integrity in Configure Shard → Systems.

**Shard integrity (rebuilt 2026-10-18, tester report "nothing ever looks corrupted") — design + as-built in `dev/design/SHARD-INTEGRITY.md`.** Three root causes it fixed: cosmetic mode had NO visuals at all (the tier only coloured the bar); mechanical corruption silently failed for players (the page write on the GM-owned journal threw inside a swallowed `.catch`); corruption was all-or-nothing. Standing rules:
- **Two layers.** Shard integrity (one number, the bar) drives the visuals + death at 0. Each entry's `corruption` page flag (0..1, quarter steps; legacy `corrupted:true` reads as 1) drives what is lost (mechanical mode). **Which units are lost is DERIVED, never stored** — `IntegrityModel.isUnitLost` gives each unit a fixed seeded threshold, so loss is monotonic and reconstruct returns the newest losses first.
- **All rules live in the pure `IntegrityModel.js`** (`resolveIntegrity` layers any stored block over `INTEGRITY_DEFAULTS`, 0-safe — no migration); DOM paint in `IntegrityFX.js`. **Lost data is removed BEFORE `enrichContent`** (`applyLoss`), never hidden with CSS — the leak rule.
- **Cosmetic garble is PAINT-OVER**: the real character stays in the DOM (`-webkit-text-fill-color: transparent` + a `::before` glyph), so copy/paste and screen readers get the truth. Capped at 1,200 glyphs per entry. Motion is vetoed by OS reduced-motion or the animation pref; the garble stays.
- **Every integrity write is GM-side; players relay** via `SOCKET_OPS.SHARD_INTEGRITY_REQUEST` (ops degrade/entry/repair/salvage). `degradeIntegrity` writes **pages first, then the item** — the viewer re-renders off the item update. The threshold is a **percent** (it used to compare raw points). **The config save carries `currentIntegrity`/`history`/`salvaged` over** (`_collectIntegrity`) — it used to reset to Max, healing the shard on every save.
- Protected money (eddies/banking never lose eb), programs turn **unstable** (`programInstability` → `unstable` on `runPayloadExecute`/`runMalwareDeploy`: +DV and a misfire chance) — both GM toggles. Uploads bake the damage into the copy (`exportEntry`; a fully lost entry can't be uploaded).
- The ShardsTab **Integrity** box has a Damage button (+ `game.nightcity.messenger.damageShard`, GM macro "Damage Selected Shard") and an **Entry damage** list; the network access-mode picker's card-clearing is now scoped to its own group because the Integrity section reuses `.ncm-cfg-am-card`.
- **The index strip never says more than the cards** (`_applyIntegrityToChips`): chips take their title from the ENRICHED entry (garbled at 75%+ for players, "Sector lost" when gone — it used to print the real stored subject), carry a 4-segment damage bar, and give the GM the exact % as a tooltip. Chip titles get the paint-over garble at half rate from Unstable down; the chip itself is a `data-action`, so its title is garbled with a narrower skip list than card bodies.
- Sim `dev/tools/sims/test-integrity.mjs` (40); probe `dev/mockups/shard-integrity-probe.html` (real viewer code); design mock `shard-integrity-mock.html`. **Test setup:** `dev/tools/test-integrity-setup.macro.js` (GM Script macro) builds four shards on a carrier actor — Breach Me / Pre-damaged / Visual Only / Bricked — and lists what to try.

**Shard text size (2026-09-10, tester "old eyes") — two knobs, multiplied.** `item-inbox.css` and the shared `content-types.css` had **zero** `--ncm-text-scale` plumbing (226 + 218 fixed-px font-sizes), so the player's Theme Customizer Text Size did nothing in the shard viewer and only partly in typed content anywhere. Both are now fully swept to `calc(Npx * var(--ncm-text-scale, 1))` (mechanical; the sweep skips `font-size: 0` and comments). On top of that a **per-shard Text Size slider** (80–150, step 5) sits in the shard config's Preset & Theme section → `config.textScale` (default 100, `DEFAULTS.SHARD_CONFIG`). The composition is pure CSS: `ThemeService.applyTheme` publishes the player scale on `:root` a second time as **`--ncm-text-scale-base`** (root only — a custom property can't read its own inherited value), the viewer template stamps `--ncm-shard-text-scale` inline on `.ncm-item-inbox` (from `shardTextScale` in `_prepareContext`), and the item-inbox.css root block defines `--ncm-text-scale: calc(base × shard)`. So a player at 130% reading a shard the GM set to 120% gets 1.56×, live from either slider. The config slider previews DOM-only onto every open viewer of that item (`_previewShardTextScale` sets the var, no render) and `close()` reverts an unsaved drag. **Admin-tagged windows now force `--ncm-text-scale: 1`** (admin-theme.css root rule): GM tools size text with the admin *zoom*, and before this the player scale stacked on top of it for every calc'd surface inside a tagged window (GM-view viewer/composer, the entry composer's live preview — and, post-sweep, the entry composer's own form). Terminals are untouched: they set `--ncm-text-scale` on their own root and never read the base. **`malware-workshop.css` is swept too (2026-09-12, all 77 sizes)** — inert inside the GM Workshop (admin-tagged → scale forced to 1, the admin zoom sizes it) but required because the player-facing Shard Encoder (designed, not built — `dev/mockups/shard-encoder-fui-mock.html`) is hosted in the Workshop frame and reuses its `.ncm-fw-*` classes; the dev's rule is that the Workshop's type tiers are the Encoder's model. The FUI modals (security-console / upload-console / bank-heist / operator-select) still have no scale plumbing. Verified in headless Chrome against the real core+CPR+module cascade (shard 1.2×1.5 → 23.4px from 13px; default stamp → player scale only; admin-tagged → 13px; terminal → its own 1.1×).

**Shard contrast (same day) — a per-shard Contrast slider (70–140) beside Text Size → `config.contrast`.** Same OKLCH tone-map as the Theme Customizer (`adjustLightness` around `CONTRAST_SPREAD.pivot`, accents excluded, images untouched), packaged as **`applyContrastToElement(el, pct, {baseFrom})`** (helpers.js): for each `CONTRAST_SPREAD` token it reads the base colour from **`:root`'s computed value** (i.e. the player's own already-contrast-adjusted palette, via `cssColorToHex`; the constants' hex when :root has nothing), pushes it from the pivot, and writes it **inline on the viewer root** — where the shard's `--sp-*` aliases (which read `--ncm-*` on the SAME element) and the shared content-types CSS pick it up. A slider drag or re-render can't compound, because the base is always re-read rather than accumulated; **100% removes the inline overrides** so an untouched shard keeps following the player theme live. Applied in `ItemInboxApp._applyShardTheme` right after the preset class (`shardContrast` in context); the config previews live on open viewers through the same helper and `close()` reverts an unsaved drag (`_displayPreviewed`/`_displaySaved` cover both sliders). Terminals already had contrast through `buildTerminalThemePrefs` → `ThemeService.applyTheme` and are untouched.

> **CORRECTED 2026-09-22.** This paragraph used to claim "shard presets never override the `--sp-*` palette in CSS … presets only carry accent/headerBg/icon". **That was wrong**, and the error was load-bearing: `styles/themes/shard-presets.css` hardcoded all **twenty** `--sp-*` tokens for each of the eight themed presets, and since the contrast tone-map writes `--ncm-*`, those presets' `--sp-*` never read it — **the contrast slider silently did nothing on 8 of the 9 presets.** The fix is the palette move described in the Shard theming section: presets now carry a JS `palette`, the `--sp-*` tokens derive from `--ncm-*` in ONE place (item-inbox.css), and `applyContrastToElement` is called with `{ baseFrom: <app root> }` so it tone-maps *this shard's* colours rather than the player's. The `baseFrom`-less form still reads `:root`, which is what the Encoder and other callers want.

## Architecture: the Shard Encoder (player-facing authoring) + the legibility layer

The player's answer to the GM's Malware Workshop: a blank chip → something on it → one roll. Design is signed off (the seven decisions are in the `shard-encoder-design` memory note); the approved mock is `dev/mockups/shard-encoder-fui-mock.html`. **Built 2026-09-21: BLANK → BUILD (content **or** program) → LOCK → ENCODE, plus the GM card, the accessibility layer and the Market.** Nothing of the flow is left stubbed; what remains is retiring the old wizard and a live test.

**`STAGES` is the ONE list** the spine, the footer count and the navigation read, and its **middle row is a BRANCH**: the same slot is CONTENT (forge a file) or PROGRAM (build a tool), chosen by `S.mode`, which is why its `title`/`sub` are `{content, program}` maps read through `stageText()`. A new stage slots in by adding a row plus a `_rail<Stage>()` / `_patch<Stage>()` pair. Entry defaults to CONTENT; the **Payload / Malware tiles switch the branch** (the mock's "② CONTENT / ② PROGRAM"), and the Program Deck's door asks for `program` by name.

**The rules are a pure module — `scripts/ui/content/EncoderModel.js` — and it is the ONLY place a number lives.** No Foundry globals, so `dev/tools/sims/test-encoder-model.mjs` (49 checks) drives the real functions. `ENCODER_DEFAULTS` is the shape; the world setting **`encoderConfig` stores ONLY what the GM changed** and `resolveEncoderConfig(stored)` layers it over the defaults (objects merge, **arrays replace**, so a deleted tier stays deleted) — which is why a default added in a later version reaches existing worlds **with no migration**. It also sanitises: an unknown botch rule / perk / pricing mode falls back, a negative price clamps, a nameless item entry is dropped, and there is **always exactly one fallback tier**.

- **The ladder is the upload arc's, not a second one.** `SLOPPY_BAND` mirrors `FORGE_SLOPPY_BAND` in `UploadFlow.js` and **both the sim and Phase 6 assert they match** — meet the DV = clean · miss by up to the band = sloppy (it writes, with a tell) · worse = rejected (nothing compiles). `encodeOutcome` / `ladderOdds` / `likelyRung` / `oddsClass`. Quality uses the same `50 + margin × 8` scale, so a player-made file reads to ANALYZE/SWEEP exactly like an uploaded forgery.
- **A chip can carry SEVERAL files, and a crowded chip is a harder chip.** `S.entries[]` holds them; `contentStackDV()` prices the lot: the **hardest** file sets the base (you are only as good as the fake that takes the most work), the craft-skill penalty is paid **once**, and every file past the first adds `cfg.content.extraEntryDV` (default 2, 0 turns it off). One encode roll covers the chip, so **one quality lands on every file**. How many fit at all is the tier's `capacity`. Corollaries the code enforces: `_needsRoll()` reads EVERY file (a note beside a forged dossier does not make it easier), `_eddiesLoad()` sums every cred drop on the chip, `_choices()` offers the trades for the HARDEST type, and the GM relay accepts a LIST — a player sending three files must not lose two.
- **ADDING a file and EDITING one are different doors, and the add door needs BOTH halves.** "Write another file" only sets the intent (`S.adding`) and opens the type row; **picking the type is what opens the editor** (`case 'type'` consumes the flag). The first cut stopped at the rail, where the button re-read as "Write another file" again — so the editor was unreachable for a second file and the only way in was the per-file pencil, which EDITS: every "new" file replaced the last one. Any unrelated click clears `adding`, so a later type pick can never surprise-open the editor. The slot a composer writes back to is **captured when it opens**, never read from the live `editIndex` at save time (a second composer would otherwise land its file on top of another one), and a second composer is refused outright — `PlayerEntryComposer` owns ONE window id, so two would fight over the same slot.
- **The startup wears the chip the player designed.** `_bootConfig` sets `iconMode:'image'` + `imageUrl` from the chosen art (a baked data URI works — the boot renders a plain `<img>`), falling back to a glyph only when there is no art. Without it the splash animated around an empty space.

- **A tier says how much the chip HOLDS.** `capacity` (entries; **0 = no limit**) is the fourth thing a tier buys, alongside price, botch rule and perk — defaults Scrap 1 / Standard 3 / Premium 8, so a better blank is worth buying for more than surviving a botch. `capacityOf()` / `capacityLeft()` are the readers. The encode stamps the tier's limit onto the shard as `config.capacity`, and **`DataShardService.addMessage` enforces it for every writer** — the Encoder, the GM composer, the Workshop, and a terminal burn — returning `{success:false, full:true}` with a sentence rather than failing silently. **An absent capacity resolves to 0/unlimited**, so every shard authored before this behaves exactly as it did. A burn onto a full chip now carries the reason out of `exfilToShard` (it counted successes and returned a bare `success:false`, which read as a broken button).

- **Blank tiers are GM-defined.** `tierForItem(cfg, {name, tierId})` takes a PLAIN DESCRIPTOR, never a Foundry Item (the model stays pure — the app's `_desc(item)` builds it). An explicit `tierId` stamped on a bought blank wins; else the GM's per-tier item lists by **space/punctuation-insensitive name** (the SkillService rule); else the fallback tier. `botchFor(tier, {nat1})` says what a rejection costs — a natural 1 is one step harsher. A tier perk (`craft+1`) is a **real modifier**: `SkillService.performCheck` gained an `options.modifier` that lands in the total and the result.
- **Program branch:** `FAMILY_ABILITIES` maps utility/execute → `PROGRAM_EFFECTS` keys. **Only verbs with a working applier are offered** — `wipe`/`corrupt` need target files picked at PUSH time and `logicBomb` has no inner-effect authoring, so all three are absent (the standing "a dead option is worse than no option" rule; the sim asserts the negatives). Rank in the gating skill both **unlocks** abilities and **buys charges**; the player then PICKS the craft skill (`craftChoices` — the recommended one free, another trade at +DV, some alts limited to certain verbs). `programDV` = ability DV + craft penalty + trojan cover. `programEfficiency(total, dv, rank)` is what the margin buys: clean = full charges / stealth DV 12+margin (capped 20) / run DV −2; sloppy = 1 charge / stealth DV 8 / run DV +2 / GLITCHY.

**The Content branch does NOT reimplement authoring — it opens the REAL composer.** `PlayerEntryComposer` (scripts/ui/ShardEncoder/) subclasses `DataShardComposer` for exactly two reasons a per-instance option cannot cover: `ADMIN_THEMED` is read as `this.constructor.ADMIN_THEMED` and this window is player-facing, and it needs its own window id so it can't collide with a composer the GM has open. The parent gained a **`playerMode`**: it **COLLECTS instead of persisting** (`onCollect(entryData)` — the Encoder keeps the entry, and only the encode roll decides whether it is ever written), its `_prepareContext` / `_onSaveEntry` isGM gates relax, the type picker is filtered to the GM's `allowedTypes`, and the template hides the GM-only apparatus (③ SECURITY & ACCESS, the template library) behind `{{#unless playerMode}}`. The inherited static actions still work because they are bound to the PARENT's methods by name and branch on the flag.
- **The roll is the forgery's quality, not a gate.** `contentDV` (the type's DV + the penalty for using the other trade) → `contentEfficiency` → `quality` on the same `50 + margin × 8` scale, and a **`scanDV` that mirrors `UploadFlow.stealthDVFromQuality` exactly** (the sim asserts the formula still matches), written to the entry as **`contentData.sniffDV`** — which is what ANALYZE rolls against. So a shard a player forged reads to ANALYZE and SWEEP like one they uploaded, and a sloppy fake really is easier to catch.
- **A type with no craft skill needs no roll at all** (`_needsRoll()`): a message, a note and a cred drop are not fakes, so the die never appears, the ladder is replaced with "nothing to fake, nothing to roll", and the blank is never at risk. Do not "fix" this by giving them a DV.
- The centre panel previews the finished file through `enrichContent` + the shared `content-body` partial, with the `--sp-*` tokens mapped onto the preview so a typed file looks the way it will on the chip.

**The LOOK is the player's, the SECURITY is the roll's.** The Blank stage's **Look** row sets the chip art and a cosmetic preset. Art defaults to the Cyberpunk RED compendium chip (`systems/cyberpunk-red-core/icons/compendium/gear/memory_chip.svg`, `DEFAULT_SHARD_IMG`) with five one-click alternatives from the same set and a FilePicker for anything else; it is written to the **item**, never into the shard config (`_lookConfig` stamps `__img` and `_shardConfig` strips it). A preset contributes **`theme` + `boot` ONLY** — several shipped `SHARD_PRESETS` carry Black ICE at DV 20, and a player must not inherit that by liking the artwork, so the Encoder passes explicit overrides and never hands `convertToDataShard` a preset KEY (which would apply `security` too). Security comes from the Lock stage, where it is rolled for.

**The roll follows what was WRITTEN, not what was picked.** The composer carries its own "Change type", so a player can start a message and finish a dossier. `_adoptEntryType(entry)` runs on collect AND again before the encode: an allowed type is adopted (with the craft skill re-synced, since Forgery is not Accounting), and anything the GM disallows is reverted with a reason rather than rolled at a DV that does not belong to it. Without it a rewritten message was forged at the message's nonexistent DV.

**The chip designer bakes an icon — `scripts/ui/ShardEncoder/ShardIconBuilder.js`.** A framework-free promise modal (the SecurityConsole / OperatorSelect family, mounted into `host` so it wears that window's palette) composing a shape, a colour, and a mark that is either a Font Awesome symbol or any image. The **chip shape is the Encoder core's own silhouette** — the square with the top-left and bottom-right corners cut in, mirroring `.ncm-fw-chip-core`'s `clip-path` on canvas — so the icon on the item is recognisably the thing the player watched compile. Colour is a `CT_COLORS` swatch **or any hex** from a native picker; `hexFor()` takes either, and dragging the picker repaints live without rebuilding the swatch row. The icon is baked onto **`#1b1f21`**, the flat near-black every Foundry item tile sits on — a transparent PNG shows the sheet through the chip and reads as a hole in the row. It resolves a **PNG data URI, not a path**: writing a real file needs upload permission a player usually lacks, while a data URI is a string on an item they already own. **The Font Awesome trick:** a class name carries no character — the glyph lives in the stylesheet's `::before { content }` — so a hidden probe element is mounted, `getComputedStyle(el, '::before').content` is read back, and THAT character is drawn in the FA family. `paintIcon` is shared by the preview, the two small previews and the bake, so what is approved is the pixels that land. A cross-origin image taints the canvas and `toDataURL` throws; that is caught and explained rather than handed back broken.

**A cred drop is money MOVED, not made — `_eddiesLoad()`.** An `eddies` entry needs no roll, so nothing stands between a player and minting eb from nothing; the old `ShardConversionFlow` debited the author's wealth and the Encoder must too. The amount is checked against wealth **before the roll** (together with a bought blank's price, so a player is never told halfway), debited **only once something is really written** (a rejected encode returns before the money moves — the blank is spent, the money is not), re-checked at the moment of writing in case wealth moved, and **refunded with the blank price if the write then fails**. It is stated in three places: the readout sentence, the artifact card, and the encode stage's locked-in list.

**The startup is the player's to write.** The Look row also sets what the shard SAYS when it opens: title, the line under it, one of the nine boot choreographies `ItemInboxApp._bootAnimations` actually implements (offering a tenth would be a dead option — the sim cross-checks the two lists), a speed, and a switch to skip the startup entirely. A preset seeds the animation and the placeholders; typing over them is an override, and `_bootConfig` writes ONLY fields the player filled, so an untouched shard keeps the preset's own words instead of being flattened to the generic defaults.

**Copying shards into the Items directory — Admin → Shards → "Copy Shards to Items".** The recurring question is where a player-made shard shows up for the GM, and the honest answer has two halves: an item **embedded in an actor cannot be foldered at all**, and moving it would take the shard off the player's sheet. So `DataShardService.archiveShardsToItems()` makes **reference copies** as world items, filed under **Player-Made Shards → the character**. Each copy keeps the source's `journalId`, so it is a **live window** on the player's real shard rather than a snapshot that drifts. `surveyShardArchive()` is the read-only census the dialog shows first (what would be copied, what already is, which copies have lost their shard). Re-running is idempotent — a source that already has a copy is skipped, and a copy is never itself copied.
- **The guard that makes this safe:** the admin Unconvert calls `removeDataShard(item, true)`, which deletes the linked journal. An archive shares that journal, so deleting a copy would gut the player's shard — `removeDataShard` now refuses to delete a journal when the item carries `shardArchive`. Never remove that check.

**Player-made shards are filed under their maker.** `MessageRepository.getSubfolderPath([...])` creates a nested journal-folder path, and `convertToDataShard` uses it when `configOverrides.playerMade.actorName` is set: the linked journal lands in **Data Shards / Player-Made / <character>** instead of the flat folder. Folder creation is a world write, so the helper is **GM-only and degrades** — a player gets the deepest folder that already exists and the journal simply stays put, rather than throwing. The **item** cannot be foldered at all (it is embedded in an actor), so the Admin → Shards row carries a **"Made by <character>" badge** instead (gold when the forgery was sloppy), which is also how a GM learns a dossier is a fake before the NPC it accuses does.

**The Agent encodes as the character it is OPEN as.** `MessageViewerApp` has `actorId`, NOT `actor` — the first cut passed `this.actor` (undefined), so the Encoder fell back to `resolveOperator()` and quietly encoded as the remembered character rather than the one whose Agent was on screen. The door now passes `game.actors.get(this.actorId)`, and the Encoder's Operator card shows on EVERY stage (naming the character even where nothing rolls) so the question can never be silent again.

**PERMISSIONS — three of the Encoder's writes are the player's own, and three are not.** Theirs: creating a bought blank on their actor, paying for it out of `system.wealth`, and renaming/restyling the item. Not theirs: the shard journal, the world settings, and the price — all relayed. `_permissionProblem()` checks the player-side ones **up front (on open) and again before the roll**, in one sentence each: no operator · an operator you do not OWN (both the buy and the payment write to that actor) · authoring switched off mid-session. `_createBlank` refuses loudly rather than returning a silent null, the cosmetic item writes are wrapped so a failure cannot cost a shard that was already rolled for, and `EncoderConfigApp.render` refuses for a non-GM at the door instead of failing at Save.

**The LOCK stage is a CEILING, never a check — and it is optional.** A lock roll cannot be failed: the total picks a rung in `cfg.lock.ceilings` (the table the old `ShardConversionFlow` used, now a GM setting), and the rung says the highest encryption DV you may set and which affordances open. A bad roll still locks the chip, it just cannot lock it hard. Two independent, optional rolls: **Cryptography** buys the encryption ceiling and Black ICE (which ALSO needs the GM's `lock.blackIce`), **Electronics/Security Tech** buys the bite-back failure mode (10+) and a key-item reader (20+). A password needs no skill and no roll at all — it is a secret you set.
- **`lock.allowed: false` removes the stage**, it does not grey it out: `_stages()` filters `STAGES`, and the spine, the footer count and the navigation all read that filtered list. Never index `STAGES` directly.
- **`_lockConfig()` writes the shard config's OWN long-standing field names** (`encrypted`/`encryptionType`/`encryptionDC`/`failureMode`, `requiresLogin`/`loginPassword`, `requiresKeyItem`/`keyItemName`…), so a player-locked shard is breached by exactly the same code as a GM-locked one. An untouched lock writes **nothing** — an open shard must not carry half a security block.

**MARKET — the player proposes, the GM disposes (`scripts/ui/ShardEncoder/ShardMarket.js`).** It renders only at the seal, because there is nothing to price until the thing exists. `cfg.pricing`: **off** (never rendered) · **propose** (the default and the dev's locked decision — the figure does NOT touch the item until the GM approves) · **free** · **formula**. The write is always the GM's: `system.price.market` is CPR's field on an item a player may not own, so `propose` relays through **`SHARD_PRICE_REQUEST`** and the GM's own client prompts and writes. **`applyShardPrice` refuses a non-GM caller**, so the mode is enforced where the write happens rather than in the UI. Three failure paths are handled out loud rather than silently: no GM online, a prompt closed without answering (= **deny**, never a silent yes), and no answer inside two minutes.

**`ShardEncoderApp` is hosted in the Malware Workshop FRAME.** Its root classes are `['ncm-app', 'ncm-malware-workshop', 'ncm-shard-encoder']`, so every `.ncm-fw-*` rule IS the real chrome and only `.ncm-enc-*` is new (`styles/components/shard-encoder.css`, imported **after** malware-workshop.css — the sim asserts the order). Build-once-and-patch like the Workshop: the PART is a bare root, `_mount()` builds it and every interaction patches the DOM, never `render()` — which is also what lets the stage transition (out-fold → handoff sweep → core morph → cascade in) animate on live nodes. Two Workshop rules needed a local override: `.ncm-fw-icecard__ic` is **red** there because it means Black ICE (a blank chip is not a threat), and `.ncm-fw-chip` is styled as a SPAN, so a `<button>` wearing it still gets Foundry's white default.

**It is NOT `ADMIN_THEMED`** (it is a player window; the GM config app IS) and the sim asserts both directions.

**Writes:** the player owns the blank item, but a shard journal is GM-owned, so conversion + the first entry ride the existing `SHARD_CONVERT_REQUEST` relay. **`_canPersist()` runs BEFORE the roll** (the sim asserts the ordering) — never after something irreversible. A bought blank debits wealth and **refunds on any failure**. A **bricked** blank is FLAGGED (`flags.<MODULE>.blankBricked` + a renamed item), not deleted — non-destructive, auditable, and `_candidates()` filters bricked chips out so it can never be re-used. The entry is built through **`programToEntry`** (the Workshop's own shape, so the Deck / upload / SWEEP need nothing) and stamped with `provenance.playerMade` + the forge quality; the shard config carries a `playerMade` block for the GM's audit, and `TraceService.logSuccess` writes the Security-tab row when `cfg.audit` is on.

**Three doors, one launcher — `game.nightcity.openEncoder({item?, stage?, family?, actor?})`** (registerReadyServices ready/115, refuses when the GM has not switched authoring on): the Agent's Shards tab **"Encode new"** action pill (`open-encoder`, gated on the context flag `canEncode`), the item right-click (`ShardSheetOverride._launchConversionFlow`, whose door-side gate is `ShardSheetOverride.canAuthor(actor)` → `canEncode`), and the **Program Deck's first empty cartridge** (`.ncm-pd-cart--new`). Every one of them, and the launcher itself, judges through `canEncode` — see the encoder-gate section.

**GM card: Admin → Shards → Player Authoring → `EncoderConfigApp`** (`ADMIN_THEMED`, admin vocabulary: display chrome, mono values, 2px radius, `.ncm-ct-row__check`). Five tabs — Basics (the master switch, pricing, lock, re-encode/copy, audit) · Blanks (tier cards with price / botch rules / perk / an item picker in the **burn-picker pattern**) · What they can make (the 18-type allow-list with craft skill + DV + alt) · Programs (families, gating skill, alts, per-ability DV + rank, charges, trojan cover) · Optional depth. **Nothing is written until Save** (`this.draft` is the working copy), and it builds-once-and-patches because a settings sheet full of live inputs must not lose focus to a re-render.

**ACCESSIBILITY — `scripts/utils/legibility.js` is the ONE place, and any FUI surface can adopt it.** Per-player (client setting `legibilityPrefs`), opened from the Encoder's footer **DISPLAY** button, applied live with no re-render. `applyLegibility(root, prefs)` stamps `--ncm-lg-text` plus `data-lg-motion|density|outlines|font` and writes the contrast palette inline via the shared `applyContrastToElement`. Seven knobs: **text size** (80–160), **contrast** (70–140), **motion** (full/calm/off), **density** (compact/roomy), **stronger box edges**, **plain font**, **always show the numbers** — plus five one-click presets (Default / Large text / High contrast / Calm / Maximum).
- **It sits ON TOP of the theme, it does not replace it.** Text size MULTIPLIES the player's Agent Text Size — the Encoder redefines `--ncm-text-scale: calc(var(--ncm-text-scale-base,1) * var(--ncm-lg-text,1))`, which is the shard-viewer composition trick and means the **borrowed Workshop classes scale too** (they are all `calc(Npx * var(--ncm-text-scale,1))`). Contrast is the same OKLCH tone-map as the Theme Customizer, and **100% removes the inline overrides** so an untouched window keeps following the theme live.
- **Motion can only ever be LOWERED.** `effectiveMotion` forces `off` when the OS asks for reduced motion or the module's animation pref is off; the player's choice can never raise it. Every beat of the encode sequence reads it (`off` = instant, `calm` = shorter with no looping decoration).
- **Plain font works by redefining the font slots** (`--ncm-font-display/title/mono/ui` → the body face) plus one `text-transform:none` sweep, so it reaches the borrowed chrome without touching a single component rule.

**First live run (2026-09-21) — four fixes worth keeping in mind.** (1) The blank list has a **search + filter chips**: the search filters the LIVE DOM (re-rendering the rail per keystroke steals focus), and the chips are **one per item TYPE the character actually carries** (Gear, Cyberware, Weapons…, labelled by `_typeLabel`) plus All and Blanks. They render whenever the character carries anything — the first cut only showed them when the GM had registered blank items, so a fresh world had no filter at all. (2) **The player composer must not demand an item** — a BOUGHT blank has none until the encode succeeds, and requiring one showed the GM-only "No shard selected" panel, so player mode renders and saves without one. (3) **Every type tile names its skill**, not just the selected one — otherwise you have to click all eleven to learn which trade each wants. (4) **A finished shard has to be findable**: the item directory, the actor sheet and the Agent SHARDS tab all cache their lists, so `_refreshShardViews()` repaints them, the seal's button becomes **Open it**, and the hint names whose gear it is in.

**Test setup:** `dev/tools/test-encoder-setup.macro.js` — paste into a Script macro as GM: switches player authoring on, puts one blank of each TIER on a carrier actor and registers them by name in their tiers, then prints a what-to-try list (the three doors, a forgery, a rejected/bricked blank, the program branch, the accessibility panel, the two-client relay test).

**Verification:** `node dev/tools/sims/test-encoder-model.mjs` (165 checks — config layering, tiers, the ladder, program gating/efficiency, the content branch (no-roll types, the scan-DV formula, the collect-not-persist contract), the lock ceilings (monotonic, never empty, the GM veto), the market (GM-only writes, deny-on-close, no-GM), the legibility clamps, and the wiring a window can get wrong: stylesheet order, template registration, class-prefix collisions, admin-theme flags, relay-before-roll). Phase 6 gained **6.14** (model + settings + ladder agreement + every offered verb has an applier) and **6.15** (legibility clamps and stamps). Visual: **`dev/mockups/shard-encoder-probe.html`** mounts the REAL app against the real cascade (`?stage=blank|content|program|lock|encode`, `?type=`, `?wrote=1`, `?rolled=`, `?sealed=clean|sloppy`, `?preset=large|contrast|calm|max`, `?display=1`, `?still=1`, `?h=`) and reports contrast / clipping / the stamped prefs in `<title>`. **`?still=1` matters**: headless advances JS timers but NOT CSS animations, so an entrance cascade captures frozen at opacity 0.

## Architecture: shards players don't own — the state relay, the editing rule, re-encode, Permissions (2026-10-21)

Tester report: "to modify a shard a player needs Owner rights, and Owner puts the shard in the Items sidebar before its reveal" + "we haven't done anything to update existing shards". Both were real; they are two different problems.

- **A shard that arrives as a message attachment is a WORLD item the player has no permission on, and every state write a player's hack caused went straight to `item.update`** — `_handleHackSuccess` (decrypted), `_updateActorSession` (attempts / lockouts / login / key item), `_decryptMessage` (a page on the GM-owned journal), `_destroyShard`. The roll succeeded, the write threw, the shard looked like it never unlocked — hence "needs Owner". **Now every one of them goes through `_canWriteItem(item)` (GM or `item.isOwner`) → direct, else `_relayState(op, item, payload)` → `SOCKET_OPS.SHARD_STATE_REQUEST`** (ops `decrypt` | `session {actorId, updates}` | `decryptPage {messageId}` | `destroy`; GM handler `handleStateRequest`, one GM lands it; no GM online → warns + returns false). A shard on the player's own sheet is still a direct write (they own the actor). **So a world shard needs NO ownership at all** — leave it at None, it stays out of the sidebar, and the player hacks it through the Agent. Don't reintroduce a bare `item.update` on a player-reachable path; the sim greps for it.
- **Per-shard editing rule — `config.playerEditing`: `locked` | `maker` | `qualified`** (Configure Shard → Security → "Player Editing"; `SHARD_EDIT_MODES` + the pure `resolveShardEditing(config)` in EncoderModel.js). **A missing value resolves by provenance: player-made (`playerMade.actorId`) → maker only, everything else → locked** — so every GM-made shard, and every pre-existing one, is read-only for players with no migration and nothing to remember. It governs WRITING only (add a file / re-encode); hacking, claiming, cracking and reading are play, not modification, and never consult it. **`canEditShard(item, actor)` (helpers.js) is the ONE door-side answer**: GM → ok; the shard's rule; then `canEncode`; then `encoderConfig.reencode.allowed`. Doors: the shard viewer's + button (`canPlayerEdit` → a player's `addEntry` opens the Encoder, never the GM composer), the item right-click "Encode More Onto It" (directory + inventory row), `_launchConversionFlow` on an already-converted item, and the Encoder itself (`_permissionProblem` re-judges before the roll). Admin → Shards rows wear an **Editable · maker/qualified** badge when the rule is open.
- **Re-encode is REAL now** — `encoderConfig.reencode` was a dead knob (the GM card ticked "Rewrite a sloppy shard" and nothing read it). The Encoder has a third source, **`srcMode: 'edit'`** ("Re-encode a shard": carried shards passing `canEditShard`; a shard handed to `openEncoder({item})` opens there).
