## Architecture: programs — Workshop → shard → machine (2.1, 2026-11-01)

Tester: description not saving, Custom became a Forgery, "carries no network program", no way from the library to a shard. Root cause of the last two: **network programs could not be built at all** (the Workshop offered no `node` verbs and the composer redirects malware to the Workshop), which `test-network-nodes-setup.macro.js` hid by hand-building them. Sim `dev/tools/sims/test-workshop-programs.mjs` goes through the real model.
- `abilitiesFor('malware')` includes the Network group; `isNodeVerb`, `programRunsOn(program)` ("Runs on" on the build rail, library cards and shard rows). Settings ride `uploadParams` (malware) or `effect.params` (payload): the appliers read there.
- **A verb always travels**: only a plant has no `uploadEffect`, Custom is `adjudicate` (read back by `payloadType === 'program'` for older entries). A program's own push roll is `uploadSkill` / `uploadDV`, separate from the run gate. `description` is one field for every verb, `coverScan` is what a failed ANALYZE reports. `normalizeProgram` upgrades library records (`params.__desc`) and `stripProgramUi` keeps window state out of them (a saved `saved:true` made the first Compile click do nothing).
- **Triggers**: "Waits for" stores the action name the trace funnel reports (`TRIGGER_ACTIONS`), "On a date" uses the CyberTimePicker and writes `atMs`; a blocked program will not compile.
- **Library → shard**: `_libInstall` (chip icon on a card) picks any shard in the world or in anyone's gear. Compile & save and Install report a refusal (a full shard).
- **Where it lands**: terminal Upload skips node verbs; any payload pushed onto a terminal RUNS there (`family: 'run'`), and a verb that writes goes to the GM (`PAYLOAD_EFFECT_REQUEST` kind `uploadRun` → `applyUploadRun`). `pickHostFiles` asks which files for Wipe / Corrupt when they run. Insert a shard's empty message names what they carry and why it won't run there.

## Architecture: Upload / Forge / Trace / Operator Gate / Security tab (2026-07-14→15)

The player→machine arc (backlog #4/#5 above, now BUILT — design doc `dev/design/UPLOAD-FORGE-TRACE.md` is the source of truth). All new, all UNCOMMITTED, verified via scratchpad sims + faithful headless renders. **Not yet live-tested in Foundry** — the dev breaks here.

**Trace subsystem — `scripts/services/TraceService.js`.** ONE funnel, two entry points: **`fireTrace(o)`** (a FAILURE — plays trace-fire + `showShardTrace`, bumps heat, GM-alerts, logs) and **`logSuccess(o)`** (a SUCCESS — logs with `success:true`, **zero heat**, so the Activity Log is a *full* feed the GM can audit, "no heat gained" shown explicitly). Both build a `_payload(o)` carrying `actor/operator`, `action`, `severity`, `targetKind` (terminal/network/shard/message/contact/account), `targetUuid`/`targetMessageId`/`targetContactId` (deep-link anchors), `outcome`, `roll`. `recordTrace` appends to the `traceLog` world setting (cap `LOG_CAP=250`) and applies `heatDelta` (`HEAT_BY_SEVERITY` minor:10/major:20/hostile:35; success=0). Heat lives in the `traceHeat` world setting keyed by `operator::objectId`; `getHeat/bumpHeat/setHeat`, decay `HEAT_DECAY_PER_HR=5` (poll-based, through the time provider), tiers `TIERS` 25/50/80 (`tierOf` static → cold/warm/hot/burned). `_heatChat` posts a GM-reason card on manual adjust; `_gmAlert` respects the `securityAlertLevel` client setting. Countdowns: `startCountdown/cancelCountdown/reapCountdowns` (the "corp found you" escalation timer). **GM-owned world writes → players relay via `SOCKET_OPS.TRACE_REQUEST`.** Every prior bare `showShardTrace` call site (31 of them) was routed through `fireTrace`.

**Upload / PLANT — `scripts/ui/content/UploadFlow.js` + `UploadConsole.js` (+ `styles/components/upload-console.css`).** The inverse of exfil: carry a forged typed-entry (from a shard "go-bag" or composed) to a terminal and leave it behind. `runUpload` opens the FUI picker (OperatorSelect pattern — framework-free promise modal appended into `host`), runs a **FORGE check**, and installs the content as a resident (below). `forgeQualityFromMargin(margin)` → a 0–100% quality; `stealthDVFromQuality` → the scan DV a later ANALYZE must beat (a botched forgery = low quality = easy to detect = "leaves tells").

**THE FORGE CHECK IS A LADDER, NOT PASS/FAIL** (`forgeOutcome(total, dv)`, `FORGE_SLOPPY_BAND = 4`): `margin >= 0` → **clean** · `-1..-4` → **sloppy** (it lands, but ANALYZE will flag it FORGED) · **worse than -4 → rejected, NOTHING installs**. The original model installed on any committed roll with no floor, so failing by 12 planted the same file as failing by 1. `runSecurityConsole` gained an optional **`verdictFor({ok,total,dv}) → {label, tone}`** hook for exactly this (a binary ok/fail can't express three rungs) plus an **`is-warn`** amber stage tone (a sloppy forge is a compromised success, so no shake). The console's intro spells the ladder out before the player commits. **Don't bother hiding the DV** — the shared `templates/chat/hack-result.hbs` prints "vs DV {dc}" for every check in the module, so hiding it in one console is cosmetic-only; it would need a `hideDV` flag threaded through `SkillService.performCheck` + that card (which every hack shares).

**Re-uploading REPLACES, it does not stack (`residentSlotKey` + `installResident`).** A resident carries a `slotKey` (`effectType::accountId::name`); installing one **replaces an existing ARMED resident in the same slot**, and only an armed one (a *fired* plant already landed, so a re-upload is genuinely a new file; slotless/legacy residents never dedupe). Without this, a player who missed the forge and retried left N armed duplicates and the GM's next login prompt fired **every one of them** — the reported "it uploads all the failed tries as well". Sim: scratchpad `test-forge-bands.mjs` (21/21, drives the real `installResident` via `prototype.call`). The COMPILING beat streams procedural code via **`HackFX.streamHackCode(el,{durationMs,subject,family,reduced,onDone})`** — family-aware pools (plant vs execute, with warning lines), reduced-motion-gated. **Composer** gained an uploadable fieldset (author the payload up front).

**Residents (triggered effects) — in `TerminalService`.** A planted file can be a **resident**: `getResidents/installResident/updateResident/removeResident`, lifecycle `_checkLoginResidents` (fires on next login) / `_proposeResidentFire` / `fireResident` / `reapResidents` / `checkActionResidents`. Stored in `TERMINAL_STATE.residents`. `applyMalwareEffect` is the shared effect applier. This is the "fires on next login" armed-plant mechanic surfaced in the Security tab's Planted & Resident card. **Only `plant` is implemented** in `fireResident`; `keylog`/`forgeAccount`/`logicBomb`/`deployICE` fall through to "GM to adjudicate" until thread #6.

**A trigger match PROPOSES — and the world setting `residentFireMode` decides.** `propose` (default) → the GM gets the prompt · `auto` → fires on trigger, GM is just told · `manual` → never prompts, waits for Admin → Security's Fire. **The pause exists because a plant firing may be the moment the table runs the NET** (design §5) — but that intent was completely invisible, so the prompt now says it in as many words. The prompt is **`scripts/ui/content/ResidentConsole.js` + `styles/components/resident-console.css`** (`runResidentConsole` → `'fire'|'defuse'|'later'`): the FUI family modal (framework-free promise, appended into `TerminalService._openViewerElement(item)` so it inherits *that machine's* preset; body-fallback), replacing a raw `Dialog` with inline styles. It shows what fired, who planted it, the target mailbox, the **forgery tell** (clean/passable/sloppy from `forgeQuality`), names the **closest NET action** for the effect (`NET_VERB`), and points at the setting for tables that don't play it that way. ESC/backdrop = "later" (never destructive). **Its markup is a template literal — keep backticks out of it** (one inside an HTML comment terminated the string and the modal silently never rendered). Preview: `dev/mockups/resident-console-preview.html` (imports the REAL module against the real cascade).

**Operator capability gate — `canOperate(actor, override)` (helpers.js) + `DEFAULTS.OPERATOR_GATE` (constants.js).** Restricts WHO can operate a terminal/run content actions: `mode` (everyone / only-who-qualifies), `roleLogic`, `roles[]`, `skill`+min-rank, **`itemGroups`** (grouped **OR-of-ANDs** — each group is an AND of required items, groups OR together; items are `{name,img}` so the gate UI shows item images), `actors[]`, `allowGM`. `nameOf` handles both string and `{name,img}`. ## Architecture: the program-effect registry (what a program can DO)

**`PROGRAM_EFFECTS` in `ContentRenderers.js` is the ONE source of truth for every effect a payload executes, a malware deploys, or a resident fires.** Accessors: **`programEffectInfo(key)`** (unknown/legacy → `adjudicate`) and **`programEffectOptions({mode, host, exclude})`** for pickers.

Before it (fixed 2026-07-26) the catalog was duplicated across **five** places that disagreed — the payload metadata map, a *second* hardcoded option list in `DataShardComposer._plContext`, the upload verb list, `_EXEC_DESC` in `TerminalViewerApp`, and the two appliers — and **7 of the 11 verbs had no label anywhere** (`wipe`/`corrupt`/`forgeAccount`/`plant`/`keylog`/`deployICE`/`logicBomb`), which is exactly why they never reached a picker and why **malware could not be authored with an ability at all**. `PAYLOAD_EFFECTS`, `payloadEffectInfo` and `_EXEC_DESC` are gone; don't reintroduce a local list.

Per entry: `label`/`icon`/`blurb` · **`modes`** — `'instant'` (applied by `SiphonFlow._applyNativeEffect`) and/or `'triggered'` (applied by `TerminalService._fireResidentEffect`) · `host` (`'terminal'` when it only means something on a machine) · `group` (picker grouping) · **`params`** (the fields the applier reads out of `effect.params`, so an authoring UI can render them — previously `effect.params` had NO authoring path anywhere).

- **The two appliers are the authority; the registry mirrors them.** A verb must never claim a `mode` whose applier has no `case` for it. The payload manifest's **`isNative` keys on `modes.includes('instant')`, NOT mere presence in the catalog** — with the catalog now holding triggered-only verbs, a presence check would let a payload claim native support it falls through to `adjudicate` on.
- **A verb whose params can't be authored yet stays OUT of its picker.** `logicBomb` is excluded from the upload verb list (`exclude: ['plant','adjudicate','logicBomb']`) because with no `inner` it installs and then no-ops (`'logic bomb had no payload'`) — a dead option is worse than no option.
- Sim: scratchpad `test-registry.mjs` (45/45) asserts **both** directions against the appliers' real case lists, including the negatives.

**Resident triggers ride the trace funnel.** `onLogin`/`onDate`/`onAction` were implemented with live reapers but only `onLogin` could ever be *produced*, and `onAction` had exactly ONE call site (exfil). Now **`TraceService._fireResidentTriggers`** (called from `recordTrace`) reaches every gated action, since they all already report there with an `action` tag + host — no per-site calls. Added **`onHeat`** (`TerminalService.checkHeatResidents`, threshold `trigger.atLeast`) off the heat that funnel already tracks. Rules: **`onAction` fires on SUCCESS only** (a failed attempt is the trace's business, not the bomb's); **`'exfil'` is deliberately EXCLUDED from the funnel path** because its own `EVENTS.TERMINAL_EXFIL` listener owns it *and* catches ungated exfils that never reach the funnel — running both would propose the same resident twice. `SecurityTab`'s resident rows only label `onDate`/`onLogin`; the two new kinds fall through to the raw kind string (cosmetic, unfixed).
