## Architecture: the ENVELOPE — mail vs file (#37)

Every entry used to wear an **email envelope** (from / subject / received) even when it was a camera feed. A terminal is a **machine**, and machines hold **files**. So an entry now carries **`envelope: 'mail' | 'file'`** (default `'mail'` — **every legacy entry is untouched, zero migration**).

- **`file`** = a machine artifact: **filename / path / owner-node / modified / size** instead of a sender. It also **suppresses every mail affordance**: no avatar, no Reply, no Add-to-contacts, **no threading**, **no delivery toast**, and **no master-contact auto-create** (a file's owner is a NODE — `SECCAM-B2`, `root`, `kowalski` — not an Agent).
- **`resolveEnvelope(entry)`** (ContentRenderers, the one source of truth for all three viewers + the composer) returns the file view-model, **deriving everything the GM didn't author**: `deriveFileSize` (12 frames → ~14 MB; a **live feed derives NO size — it's a stream, not a file**), `suggestFilename` (subject → slug + per-type extension via `FILE_TYPE_INFO`; a feed gets `.feed`, not `.img`), and the **type-aware 4th cell** (Channels / Rows / Lines / Subjects / Frames…). A live feed also **renames itself**: `typeLabel` is **CAMERA FEED**, not "Image Gallery" — the mode is its identity — with the broadcast icon and a green accent.
- **`isStream`** is load-bearing: a stream has **no size and no modified date ("LIVE")**, and it cannot be copied off the machine (see exfil).
- **Composer**: a **Show as MESSAGE / FILE** segmented control at the top of ② DELIVERY swaps the section's fields (DOM-only, so a flip-flop doesn't lose unsaved edits). `FILE_DEFAULT_TYPES` pre-picks FILE for the obviously-file types (feed gallery / syslog / malware / schematic / payload / spreadsheet / record / credentials / chatlog / avlog / document) — **a default, not a rule**; one click flips it.
- **Persistence — FOUR field-by-field spots, all four must carry it**: `TerminalService._buildMessageFlags`, `MessageRepository.createMessage`, `MessageRepository._pageToMessage`, **and `DataShardService.addMessage` + `_pageToShardMessage`** (a shard holds files too, and a burned file must stay a file). The edit-prefill openers (`TerminalViewerApp._onEditMessage`, `ItemInboxApp._onEditEntry`) must ALSO carry `envelope`/`file`/`exfil` — the edit path writes `entryData` straight to flags, so a missing key silently resets a FILE back to mail on the next save.
- **Page name**: a file titles its journal page `[FILE] <filename>` — the mail formatter would call it "Unknown".
- **Threading**: `resolveThreads` skips `envelope: 'file'` outright. Signal 4 (subject + shared counterparty) would otherwise merge two unrelated `dock-cam.feed` files from the same node into one "conversation".
- **AUDIT (same round)** — two more silently-dropped fields found in `_buildMessageFlags` and fixed: **`status.eddiesClaimed`/`eddiesClaimedAt`** (hardcoded false → a mirrored/exfil copy of an already-claimed eddies drop was **re-claimable**) and **`selfDestruct`** (hardcoded null). Same class of bug as the `spam`/`folder`/`recovered*` drops. **When adding a message field, grep all four builders.**

**Per-entry exfil override (#37).** `entry.exfil = { mode: 'inherit'|'custom', <action>: { state: 'inherit'|'allow'|'deny', dv? }, denyReason, hideDenied }`, resolved by **`TerminalService.resolveEntryExfil(item, entry)`** layered over `getExfilPolicy`. Rules:
- **`mode` is the control people expect and it MUST exist** (it was in the mock, got dropped in the first build, and its absence made the whole feature read as broken). `'inherit'` (default) = an untouched action follows the terminal's Exfil tab — so "set one action to ALLOW and hide the rest" changes **nothing visible**, because the rest are still inheriting an *allow*. **`'custom'`** = the entry is the whole story: anything not explicitly ALLOWed is **denied**. `custom` + `hideDenied` is the "allow only this one, lock everything else away" intent. The composer surfaces it as a **FOLLOW TERMINAL / ONLY WHAT I ALLOW** toggle with a live note explaining what INH means in the current mode, and `resolveEntryExfil` emits a `log.debug` of the resolved per-action outcome (debugMode) so "the override isn't doing anything" is diagnosable.
- **The terminal's `allowExfil` master is a HARD CEILING** — master off = nothing leaves, and no entry can widen it.
- **A live camera feed can never be copied** (`agent`/`shard`/`forward`/`sell`/`leak` are force-denied with reason **LIVE STREAM**, regardless of authoring — *you cannot download a stream*). **WIPE still works** (you can always pull the plug) and **SAVE FRAME is the escape hatch**. This is physics, so it's enforced in the resolver, not left to the GM to remember.
- **A denied action renders DEAD WITH ITS REASON, it does not vanish** (`.is-denied` + `.ncm-term__exfil-why`) — a missing button reads as a broken UI, a stated reason teaches the rule. `hideDenied` forces the silent hide for things whose existence is the secret.
- Composer UI: a per-action **INHERIT / ALLOW / DENY** tri-state grid in ③ SECURITY & ACCESS (it's an access policy, not envelope metadata), with per-action DV, denied-reason and hide-instead.

**SAVE FRAME (`TerminalService.exfilSaveFrame`).** You can't take the stream — you can take a **picture** of it. One channel's frame becomes a **single-image gallery** in the operator's Agent (Recovered), stamped with the cam id + the feed clock, carrying a **file envelope**. A **looped** cam captures its *frozen* time (loop a cam then save a frame and you've captured the loop — the correct, cruel outcome). GM writes directly; **players relay** via `TERMINAL_EXFIL_REQUEST` `dest: 'saveFrame'`. Deliberate simplification: the capture is the frame's **source image**, not a pixel-crop of the PTZ view — cropping would mean rasterizing to a data URI and stuffing hundreds of KB of base64 into world data on every capture; instead the **PTZ aim (pan/tilt/zoom) rides in the caption**. The lightbox button only renders when the host stamps `data-save-frame` on the thumb (`TerminalViewerApp._stampFrameCapture`) — ContentRenderers stays policy-free because it serves all three viewers.

**Sidebar (terminal)**: one **mixed list**, and **both row kinds share ONE hierarchy** — this is the rule, don't drift from it:
- **line 1 = the ANCHOR** (sender name / filename) — same size + weight in both, `text-primary`; mail uses the body font, a file uses mono (it's a machine name, not a person's). The priority dot ↔ the **content-type icon** swap here.
- **line 2 = what it is** — the subject, or a small **type chip** (+ size). Typed *mail* gets the same chip, so a spreadsheet reads the same whether it arrived as mail or sits there as a file.
- **line 3 = muted detail** — the body snippet, or the file's path.

The first cut anchored mail on a **14px bold subject** while a file anchored on its **11.5px filename**, so a mixed list read as **two competing lists** (dev: "the actual list of messages/files are confusing"). Unread files show **NEW** (a file has no urgency — it just wasn't there before); a live feed's date column reads **LIVE**. **ALL / MAIL / FILES** solo chips ride the gallery chip driver (`[data-env-act]`, document-delegated) and only render when the folder holds both kinds.

**The exfil folder's NAME is a setting, and every surface reads it.** The Agent folder that catches exfiltrated intel (downloaded mail, burned files, captured camera frames) defaults to **EXFIL**, not "Recovered". Two reasons the old name broke down: the player clicks **EXFILTRATE → To my Agent** and it landed in a folder with a *different* word (two vocabularies for one idea), and "recovered" implies something was lost and found — a **SAVE FRAME capture of a live feed was never lost**, it wasn't even a file until you made one. The label is the world setting **`exfilFolderName`** (GM-renameable — Salvage / Cache / Recovered / The Haul…), read through **`SettingsManager.getExfilFolderName()`**. **The folder tab, the per-message provenance chip, and every exfil toast (including the socket-relay ones) all read that one getter** — hardcoding the word in any of them makes them disagree the moment a GM renames it. The stored flag key stays `metadata.recovered` and the filter key stays `'recovered'`, so renaming is a pure label change with no data migration.

**Terminal motion (#38) — the terminal inherits the MessageViewer's motion vocabulary, it does not invent its own:** `cubic-bezier(.22,1,.36,1)` (expo-out), **0.3s** entrances / **0.18s** micro-interactions, **translate + fade only** (never scale-only, never bounce), all `prefers-reduced-motion` gated. Tokens live on `.ncm-terminal-viewer` (`--ncm-term-ease/fast/base`). What moves: message rows **cascade in** (`--ncm-i` stagger, capped at 9 so a full page can't become a wait), the **detail pane slides** when a different message is opened, the **sidebar collapse animates the grid column**, the **account-switcher dropdown unfolds** from its top edge, and the **login pick** holds the chosen card while the others fall away (`_playCardPick` — cards/roster/portraits; crt/lockscreen/keypad opt out by having no wrapper).

**A CSS transition cannot survive an AppV2 re-render — collapse/expand toggles must be DOM-ONLY.** `render()` **replaces** the element, so it is born in its final state and the transition has nothing to animate *from*: the panel snaps. Both collapse toggles (`TerminalViewerApp._onToggleSide`, `MessageViewerApp._toggleListPanel`) therefore flip the class on the **live node** and update the chevron by hand, and the template still stamps the class from state so it survives the next real render. This is why the terminal's collapse "wasn't working" — it was rendering, not transitioning. Same rule applies to any future animated toggle.

**The MessageViewer runs the same motion system** (row cascade, detail slide, animated list-panel collapse, refine-bar hover) — `MessageViewerApp._stampMotion` is the twin of the terminal's, with the list signature keyed on actor · filter · sort · page · search · env-solo · tab · message ids.

**THE trap, and the reason `_stampMotion` exists: the terminal re-renders on EVERY click.** An entrance animation tied to "a render happened" would make the list twitch every time you select a message. So `_stampMotion` compares a **signature of the list's CONTENTS** (account · folder · env-solo · page · message ids — deliberately **excluding the selection**) against the last render and only stamps `is-fresh` when the list actually changed; the detail's `is-fresh` keys on the selected id changing, so re-rendering the *same* message (claiming eddies, decrypting a frame) doesn't re-slide it. Rule: **motion on arrival and on state change, never on idle.** Sim: scratchpad `test-motion.mjs` (12/12, drives the real `_stampMotion`).

**Terminal sidebar collapses (`terminalToggleSide` → `_sideCollapsed`).** The mailbox folds to nothing so a spreadsheet / camera multiplex / schematic gets the machine's full width (the MessageViewer `--list-collapsed` precedent). Two details that matter: the pane is **`display:none`d, not just width:0** (its children carry min-widths and would spill into the detail pane), and the **toggle floats on the divider, outside the collapsing pane** — a toggle that collapses along with its panel can't bring it back.

**Filter chips that live in a re-rendering app must be APP STATE, not a CSS class.** The MAIL/FILES chips first shipped as the gallery's display-only `[data-*-act]` driver — but the message viewer and terminal **re-render on every click**, so the filter reset itself the instant you opened an item. They're now real `data-action`s backed by `_envFilter`, and the filter **narrows the message list array** rather than hiding rows with CSS (hiding leaves pagination counting things you can't see, and counts computed off the paginated *page* make the chips lie on page 2). Counts are taken from the whole folder BEFORE the solo applies; the solo is force-cleared when the folder isn't mixed, so a stale solo can't empty a folder that has no chips left to undo it. The gallery's chips stay display-only — correct there, since a gallery re-render is scoped to its own entry.

**Modal layer order (learned the hard way).** `.ncm-seccon-backdrop` (SecurityConsole) is **z-index 130**, above the gallery lightbox's **110** — every roll launched from the MONITOR rail (SAVE FRAME, LOOP, CUT, TAKE CONTROL) opens **while the lightbox is still on screen**, and at its old z-index 100 the console rendered *underneath* it ("save frame appears underneath the gallery pop up"). The console is the thing being interacted with, so it's always topmost; the lightbox deliberately stays open behind it (you see the frame you're capturing) and the flow closes it afterward. BankHeist (60) / OperatorSelect (90) never open over a lightbox, so they sit below it.

**The ACCESS-GRANTED badge scan rides `--ncm-primary`, not `--ncm-secondary`.** The secondary slot stays brand cyan in most presets, so on Arasaka (red primary) the verification scan swept **blue across a red card** and read as a foreign element. Primary = the machine's identity colour, so the scan always belongs to the card it's scanning. (Same reason the welcome line under ACCESS GRANTED uses `:has(+ .ncm-term__badge-welcome)` to drop the granted line's bottom padding — it stacked with the welcome's top margin into a dead 24px band.)

**Terminal chip/button sizing.** The sender-header chips (Add to contacts · Reply via Agent) and the whole **exfil rail** (`.ncm-term__btn`) are deliberately **small** (9.5px mono, 3–4px padding, 4px radius) — they were 11–12px with 6–9px padding and dominated the detail pane. There can be **seven** exfil chips at once (six actions + SAVE FRAME, several of them dead deny-chips), so they must stay chip-sized; the GM edit/delete/move controls match at 24px.

## Architecture: shared content renderers (shards + terminals)

Typed content (a SPREADSHEET / CALENDAR / SYSLOG / GALLERY / … vs. a plain message) renders through **one shared registry** so a file looks identical wherever it's opened — design doc §8c, §9b. The two halves live in `scripts/ui/content/ContentRenderers.js` + `templates/content/content-body.hbs` (`TEMPLATES.CONTENT_BODY`) and **must stay in lock-step**:

- **`CONTENT_TYPE_INFO`** — the single source of truth for per-type `{ label, icon, accent, indexIcon }`. **Moved here from `ItemInboxApp`** (it was a module-local const); the shard viewer now imports it. `ACCENT_HEX` (palette key → hex for chips/dots) lives here too.
- **`enrichContent(entry, { isGM, interactive })`** — turns a raw entry (`{ contentType, contentData, subject, from, body, timestamp, encrypted, decrypted, … }`) into the view-model the partial renders: `is<Type>` flags (generated from `CONTENT_TYPES`, so `avlog`→`isAvlog`), `formattedDate`, `contentTypeLabel`/`entryIcon`/`accentColor`, `isLocked` (`encrypted && !decrypted`), and per-type processed `contentData` (eddies/dossier/payload/avlog enrichers in `ENRICHERS`). `isGM`/`interactive` ride **on the enriched object** (not `../`) so the partial reads them directly.
- **`content-body.hbs`** renders ONLY the decrypted content body (the `{{#if isMessage}}…{{else if isEddies}}…` chain + fallback). The **caller owns** the corrupted/encrypted overlays and the entry header. Interactive affordances (claim/execute/goToScene) are gated on `interactive` — the shard passes `interactive:true`, read-only consumers pass `false`.

**Adding a content type = four touches, nothing else:** one `CONTENT_TYPES` entry · one `CONTENT_TYPE_INFO` row · (optional) one `ENRICHERS` fn · one `{{else if isX}}` branch in `content-body.hbs`. (CSS for a new type goes in `styles/components/content-types.css`, `.ncm-app`-scoped, **only `--ncm-*` tokens** so it renders in both viewers — never bare `--sp-*`.) A fifth touch to make it **authorable**: a `{{#if isX}}` fieldset + a `_collectX(data)` case in `DataShardComposer` (below).

**Authoring composer (`DataShardComposer`) is shared by shards AND terminals.** Generalized via a `target` descriptor `{ kind:'shard'|'terminal', item, accountId? }` (legacy `shardItem` still accepted = shard). `_item`/`_isTerminal`/`_service`/`_journal()` resolve the right side; `_persistEntry(entryData)` creates via `dataShardService.addMessage` or `terminalService.addAccountMessage`, and edits via a generic `page.update` (find page by `messageId` in `_journal()`). The form is read by **`_collectEntryData({validate})`** (one method, shared by Save and the **live preview**). **From + Timestamp live in ONE shared "Entry Header" fieldset** rendered for every type (the 18 per-type timestamp rows and the message-only From row were removed — the dev couldn't edit from/timestamp on typed entries without flipping back to Message; keep it single-instance, duplicate `name="timestamp"` inputs corrupt `FormDataExtended`). **From ↔ GM Master List:** the From input carries a `<datalist>` of every master-contact email (context `masterEmails`), and after a successful save `_syncFromToMasterList` runs the account link-or-create precedent — an email-shaped From (`includes('@')`, no spaces) not in the directory creates a master contact (name title-cased from the local part, provenance note naming the item) and toasts the GM; non-email Froms (SECCAM-B2) are system nodes and skip; failures never block the save. **Templates & Examples** (top of the form, `EntryTemplates.js`): per-type built-in **Load example** (`BUILTIN_EXAMPLES` — the macro seeds, timestamps stripped) + a GM **template library** (world setting `entryTemplates` `[{id,name,type,entry}]`; save-current-as / load / delete / JSON import-export, envelope `{ncmEntryTemplates:1}` — the spam-template pattern). Loading either sets `this.editData` **without an `entryId`** and re-renders — the whole edit-prefill machinery (list rows, selects, spreadsheet grid) reconstructs the form, and `_persistEntry`/`isEditing`/`get title()` all key on `editData?.entryId` (NOT bare `editData`) so a loaded template still saves as a NEW entry. Live preview: a pane (`.ncm-composer-preview-body`) that re-renders the real `content-body` partial (`enrichContent` → `renderTemplate(TEMPLATES.CONTENT_BODY)`) on every `input`/`change` (debounced in `_onRender`). Repeatable rows use a **generic list engine** — schema arrays (e.g. `BANK_TXN_FIELDS`) drive `_rowHtml`/`_onAddListRow`/`_onRemoveListRow`/`_collectList`; containers are `[data-list="<key>"]`, rows `.ncm-cl-row`, inputs named `<key>__<field>-<idx>` (prefix-matched on read). `TerminalViewerApp._onNewMessage`/`_onEditMessage` open this composer with a terminal target. **Built so far: Banking · Calendar · Syslog · Credentials · Gallery · Document · Chat Log · Records · Schematic · Note · Malware** (banking = lore/account/txn-list/siphon; most others are list-engine forms — calendar auto-builds the `categories` color map at save via `_calendarCategories`, preserving colors already assigned when editing; note/malware are scalar forms with textareas). The engine also supports `type:'date'` (native date input; ISO values sliced to `yyyy-mm-dd` on prefill) and select values never count toward the row's "has content" check (a default `<select>` isn't user intent — empty rows are dropped at collect). **`interactive` means "this consumer WIRES the content actions" — NOT "is a live viewer".** The terminal AND message viewers passed `interactive: false` while wiring every action, which silently hid the payload **RUN/KILL**, the disguise **REVEAL**, the schematic **SCOUT**, and the GM Go-to-Scene chips in both (the dev's "I've never seen the Run button"). **Operator identity — WHO a viewer acts as.** `resolveOperator()` (helpers.js) is the ONE source for the character every roll, siphon, eddies claim, and skill/stat read uses in the terminal + shard viewers: remembered pick (client setting `operatorActorId`, still owned) → `game.user.character` → the sole owned actor → null. **Never read `game.user.character` directly in a viewer** — that was invisible-and-wrong when a player owns several PCs (siphoned eddies landed on the wrong one). **Player content writes need a GM online — guard BEFORE anything irreversible.** Entries live in GM-owned journals, so a player's `persistContentData` RELAYS; with no GM connected the write evaporates and the player still gets the payoff (a claimed-eddies flow credited wealth, failed to persist `claimed`, and could be re-claimed forever; ANALYZE announced the hidden payload that never got marked `sniffed`). **`canPersistContent()`** (SiphonFlow) returns false + warns when `!isGM() && !game.users.activeGM`; `runEddiesClaim` / `runAnalyze` / `runMalwareDeploy` / `runContentUnlock` all check it as their FIRST statement. `persistContentData` warns + returns false in the same case rather than silently dropping. (This is also the answer to "declassify/decrypt/deploy do nothing" — no GM was online.)

**ANALYZE — the player-facing file scan (`runAnalyze`).** A magnifier chip on **EVERY typed file** in the terminal detail + shard entry header (deliberately type-agnostic — a button that only appeared on trojans would BE the tell). Rolls vs the file's `sniffDV`: a disguised payload is unmasked (persists `sniffed: true`, same write as the GM REVEAL), a clean file reports "no anomalies" — so scanning is a real, sometimes-wasted choice. A failed probe on a booby-trapped disguise (`traceOnFail`) fires the trace.
