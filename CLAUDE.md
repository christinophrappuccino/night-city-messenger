# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Night City Messenger (NCM)** — a Foundry VTT v12 module for the Cyberpunk RED tabletop RPG. Module ID `night-city-messenger`. Provides in-character messaging, contact management, data shard mechanics, network simulation, and GM tooling. The local working directory IS the live Foundry module install; there is no separate build artifact.

Repo: https://github.com/christinophrappuccino/night-city-messenger

**Module id renamed 2026-09-10: `cyberpunkred-messenger` → `night-city-messenger` (folder must match).** v1.0 shipped under the old id, and a module id is the flags namespace on every document, the settings namespace, the socket name and the compendium pack ids — so the rename is a breaking change carried by a one-time migration, `scripts/core/NamespaceMigration.js`: `migrateClientSettings` (preInit/1, every client, localStorage copy) + `runNamespaceMigration` (ready/1, GM only, MUST stay the first ready task because later services cache world state): scans for legacy world settings + document flags across `MIGRATION_SCOPES` (actors+items, items, journal+pages, scenes+notes+tokens, users, macros, folders, messages), prompts the GM (raw `Dialog.confirm` — it runs before the admin-dialog hook exists), copies world settings (registered keys only, never clobbers), then per document copies the flag block → **verifies the read-back** → deletes the legacy block only when verified (mismatches keep their legacy flags and are listed), stamps the hidden setting `namespaceMigrationDone`, and calls `SettingsConfig.reloadConfirm({world:true})`. Declining doesn't stamp (asked again next load; module runs empty meanwhile). Legacy Setting documents are left in place (inert, rollback-safe). **`LEGACY_MODULE_ID` in constants.js is the ONLY place the old id may appear in module code** — a stray literal is a bug (the 2026-09-10 sweep rewrote 253 files; the stylesheet entry is now `styles/night-city-messenger.css`). The macro packs embed the id (`flags.<id>.managed`, pack keys) — regenerated by `node dev/tools/gen-macros.cjs`. For USERS the rename means Foundry sees a different module: uninstall the old one, install the new, load the world, accept the prompt (backup first). Sim: `dev/tools/sims/test-namespace-migration.mjs`.

## Verification

Before presenting changes, syntax-check JS and balance-check Handlebars:

```bash
node dev/tools/check-syntax.mjs            # every .js/.mjs in scripts/ + dev/tools/, in MODULE context
node dev/tools/check-syntax.mjs scripts    # or just one tree
node dev/tools/run-checks.mjs              # EVERYTHING: syntax + exact-case paths + every sims/test-*.mjs (~25 s)
```

**CI runs `run-checks.mjs` before every dev build and every release** (`.github/workflows/checks.yml`, called by
`dev-build.yml` and `release.yml`; a failure publishes nothing). It runs on Linux with no Foundry install, so: a sim
that needs Foundry's Handlebars finds it through `dev/tools/sims/lib/foundryApp.mjs` (never a hard-coded
`C:/Program Files/…` path on its own), and every path the module loads must match the file's case exactly
(`dev/tools/check-paths.mjs` — Windows forgives a wrong case, The Forge's Linux servers do not). To run the sims the
way CI does: `NCM_FOUNDRY_APP=<folder with node_modules/handlebars@4.7.8> NCM_NO_LOCAL_FOUNDRY=1 node dev/tools/run-checks.mjs`.

**Live checks in a real Foundry — `node dev/tools/live-smoke.mjs --url <server> --user <offline user>`.** Joins a running world headless as an offline user (never one someone is logged in as), checks the startup report and the compat.js lookups, opens every admin tab / the composer / sound board / theme customizer / a v1 dialog / the name picker, and lists the warnings and errors NCM causes apart from everyone else's. **A Foundry v13 test install** (2026-11-05): the Node build in `dev/FoundryVTT-Node-13.351/` (gitignored, never committed), data in `%LOCALAPPDATA%/FoundryVTT-v13`, run with `node dev/FoundryVTT-Node-13.351/main.js --dataPath=<that> --port=30001`; world `ncm-v13-test` on Simple Worldbuilding (Cyberpunk RED has no v13 release yet). Put NCM in it with `node dev/tools/sync-test-install.cjs --data <v13 Data> --any-system` (a COPY, never a link; `--any-system` lifts the CPR requirement in the copy only). Re-run the sync after a change.

> **`node --check path/to/file.js` IS NOT ENOUGH — it passes files Foundry cannot load.**
> With no `package.json` type, node parses a `.js` file as CommonJS/sloppy script, and
> constructs that are fatal in module (strict) context survive that parse. This bit on
> 2026-09-22: a template literal containing `'…ELSE\\'S…'` (a double-escaped apostrophe)
> passed `node --check` on every run, then failed at import with *"missing ) after
> argument list"* — the Player Authoring window simply refused to open, with a full-file
> sweep reporting "all parse". The same bytes as `.mjs` are caught immediately, which is
> all `check-syntax.mjs` does: copy to a temp `.mjs`, then `--check`. It is parse-only on
> purpose — an `import()`-based check would EXECUTE the several `dev/tools/` files that run a
> CLI on load. The isolated one-liner repro does NOT reproduce it; it needs the
> surrounding code that lets the script-mode parse succeed, so trust the tool, not a
> hand-built snippet.

For `.hbs` templates, count block opens vs closes:

```bash
opens=$(grep -oP '\{\{~?#(if|unless|each|with)' path/to/file.hbs | wc -l)
closes=$(grep -oP '\{\{~?/(if|unless|each|with)' path/to/file.hbs | wc -l)
[ "$opens" = "$closes" ] && echo BALANCED || echo "MISMATCH ($opens/$closes)"
```

If the grep flags a mismatch, scan for block tags inside `{{!-- --}}` doc comments first — they're false positives.

To verify the macro packs after editing `dev/tools/gen-macros.cjs`, regenerate — the generator self-validates (every line round-trips as JSON; every `command` parses as the async function Foundry runs it as; ids unique/well-formed):

```bash
node dev/tools/gen-macros.cjs
```

When diffing a regenerated pack against a prior copy, key by `_id`, **never** by line order — Foundry's NeDB compaction reorders the on-disk `.db` on world load (see Compendium packs).

**In-Foundry verification suites** live in `scripts/tests/` — `game.nightcity.verify()` plus `verifyPhase2()`…`verifyPhase6()` (all auto-run under `debugMode`). **Phase 6** (`Phase6Verification.js`, registered in `registerTerminalSystem` postReady/33) smoke-covers the terminal era: TerminalService/TraceService/resident method contracts, the security-era settings, the 9 player→machine socket relays, the workshop/deck launchers + terminal macro API, `PROGRAM_EFFECTS` registry shape + adjudicate fallback, the forge ladder's three rungs, operator helpers, and template loads. ## Architecture: the rules the 2026-11 audit introduced

The audit remediation (`AUDIT-OPUS.md` / `AUDIT-FABLE.md` → `AUDIT-REMEDIATION-PLAN.md` → **`AUDIT-POST.md`**, all in the repo root, none shipped) left rules every new piece of code must keep. The full table, with the sim that guards each rule, is `AUDIT-POST.md` §2. In short:
- **A socket handler trusts its second argument** (the sender's id, which Foundry's server checks), never a field in the message. Use `isFromGM(sender)`, `userOwnsActor(sender, actorId)` and `isPrimaryGM()` (helpers.js). Every op has a class in `SOCKET_TRUST` (constants.js; `test-socket-identity` fails on a missing one). **A player request carries what they DID** (an intent); the GM re-reads the data and computes the change (`contentIntents.js`, the A3 relays), and re-runs a player's recipient checks on relayed mail (`checkRecipientsAsPlayer`).
- **One GM acts:** request handlers, reapers and migrations run on `isPrimaryGM()`.
- **A linked macro runs only through `runGmMacro`**, and only when a GM wrote the link.
- **Escape everything a player typed:** toasts through `ncmNotify` (notify.js); tooltips through `{{ncm-tip}}` / `tipText()`; picture urls through `cssUrl`; stored HTML cleaned when shown (richText.js).
- **Read-modify-write of one record goes through `serialize(key, fn)`** (serialize.js); a character's contacts use `contacts:<actorId>`. Never wait on the same key inside `fn`.
- **Message fields:** `createMessage` stores them one by one, so a new field goes there and in `_pageToMessage` (`test-persist-roundtrip`). `updateMessageFlags` writes only the changed leaf paths (`flagChangePaths`).
- **Startup:** everything synchronous registers inside `init` (`runPhaseNow`), and ready waits on `initDone`. Templates use two-argument comparison subexpressions only, not block helpers another module might replace. A failed startup step reaches the GM (`ModuleInitializer.reportFailures`).
- **Call privacy is masking on screen, not secrecy** (dev decision): module socket messages reach every client.

## Architecture: how startup works

**Single entry point**: `scripts/main.js` instantiates a `ModuleInitializer` (`scripts/core/ModuleInitializer.js`), then nine `register*` files in `scripts/init/` each push tasks into one of four phases: `preInit`, `init`, `ready`, `postReady`. Tasks have a numeric priority (lower runs first; conventionally increments of 10). Foundry hooks (`Hooks.once('init')`, `Hooks.once('ready')`) drain the phases.

This means: **to add a new service or hook, add a `register(phase, priority, name, fn)` call in the appropriate `init/register*.js` file.** Don't bolt new `Hooks.once` calls into `main.js`.

**Optional systems are FEATURES (`scripts/utils/features.js`, stage 2 step 14).** A feature = one world Boolean setting with `requiresReload: true`, an entry in `FEATURES` (`setting`, `default` — equal to the registered default, the answer when the setting reads unset — `label`, `requires`, optional `offReply`). Off means not installed: tag its ready/postReady steps `register(…, fn, { feature })` (skipped and listed in `startupReport.skipped`, never failed) and its socket ops `socketManager.register(op, fn, { feature })` (a stand-in answers instead: the primary GM sends `offReply`, everyone else drops). Its UI asks `isFeatureOn(name)` / `game.nightcity.features.isOn` — read once per load; never read the setting directly (`test-features`). A feature whose `requires` is off is off. On it: Conversations; Calls, and its three parts Payphones / Emergency lines / Overheard calls (each `requires: ['calls']`, step 15). The call services are always BUILT (numbers, booths and scripts stay editable); only their screens, hooks, timers and socket handlers are feature steps, and each service has `enabled` for its entry points. A **live** feature (`live: true`, step 16 — Trace consequences) is a rule gate: read every time, no `requiresReload`, never a step/socket tag, nothing may require it.

## Architecture: layers (stage 2, step 11)

**Pure rules live in `scripts/rules/`** (`encoder.js`, `integrity.js`, `contentTypes.js`) or `utils/` — never under `ui/`. They import only `utils/` and other rules. The old `ui/content/EncoderModel.js` / `IntegrityModel.js` / `ui/Calls/dictation.js` paths (and ContentRenderers' content-type names) re-export them, so UI imports did not change; **lower layers (rules, utils, data, core, services, integrations) import the new homes.** `helpers.js` imports NO UI file (the operator picker moved to `ui/content/OperatorSelect.js`). **What a service needs from the UI is handed to it, never imported** (R9b): `scripts/core/providers.js` names each piece (`PROVIDERS`: askRoll, rollReveal, dataDropOverlay, residentConsole, canPersistContent, persistContentData, migrateRecycleBin), the init step "UI providers" (`registerUIComponents.js`) provides them (lazy imports of the UI files), and a service calls `need('name')(…)`. Services / core / data / utils / rules import NO ui/ file; only the two wiring files (`SocketHandlers.js`, `ShardSheetOverride.js`) reach UI flows, lazily. `test-layering` enforces both and that every needed name is declared and provided. A sim that runs such a service registers the real functions with `_provideAll`.

## Architecture: the public API (v2)

`game.modules.get(id).api.v2` (`scripts/integrations/publicApi.js`, documented in **`docs/API.md`**, stage 2 step 18; 2.1.0 added the GM writes, calls and networks.set). Every method resolves `{ ok, data }` / `{ ok:false, code, error }` (codes `API_CODES`), never throws or toasts, takes ids and returns plain objects (never a document or a service), and calls the SAME service method the UI does (owner / GM checks for good errors; the relay checks for safety). Events: `events.on` only (no emit), names from `PUBLIC_EVENTS`. A new method: add it there + a row in docs/API.md (`test-public-api` fails on an undocumented method or code); a change of shape is a semver bump. v1 fields (`apiVersion` 1.2.0) stay for existing integrations.

## Architecture: services

Long-lived stateful objects in `scripts/services/` (MessageService, NetworkService, DataShardService, MasterContactService, SpamService, etc.) are constructed during the `ready` phase and exposed on the `game.nightcity` namespace (e.g. `game.nightcity.messageService`). UI code accesses them via `BaseApplication` getters (`this.messageService`, `this.networkService`, etc.). Cross-service communication goes through `EventBus` (`scripts/core/EventBus.js`) using event names from the frozen `EVENTS` enum in `scripts/utils/constants.js`.

**`scripts/core/serviceMap.js` records which service looks up which** (`SERVICE_MAP`: `uses` + plain-words `does`). Those links go through `game.nightcity`, so imports don't show them; the startup report uses the table to tell the GM what stopped working when a step fails (`game.nightcity.startupReport` = `{ failed, missing, affected }`). **A new service, or a new `game.nightcity.<service>` lookup inside one, goes in the table** — `test-service-map` re-derives every lookup from the source and fails when they disagree. Services look each other up at call time, never in their constructors (MasterContactService is built after several of its users).

**Rules by system (the short list — the file has the reasons):**

- **Messaging** — A message-viewer button = an entry in `VIEWER_ACTIONS` (after the class in MessageViewerApp.js,
  called with `this` = the viewer and `(target, messageId)`; step 12 — there is no click switch any more).
  `test-viewer-actions` fails on a template `data-action` with no entry. Every `MESSAGE_RECEIVED` emitter carries the display payload (`from`, `fromName`, `fromActorId`,
  `fromContactId`, `subject`, `preview`, `priority`); only the one listener toasts (`NotificationService`
  dedups by `messageId`). Eddies transfer once, at the recipient's Claim; never credit in the composer. Never add a
  second sent-copy writer (`_createSentCopy`). The composer's `_onSend` re-enables Send in `finally`. Anonymous
  masking lives in `MessageService` (`_maskAnonForRecipient`); the real sender exists only on the GM's `-sent` copy.
  Self-destruct always hard-deletes, and a GM never triggers it. `status.spam` must survive `createMessage`.
- **Contacts** — Members are keyed by ADDRESS, ids are hints (`participants.js`). `getPlayerCharacters()` is the one
  "players' characters" list; don't write another `user.character` loop. The directory beats the actor label
  (`resolveDisplayName`); the address decides which identity sent a message (`directoryEntryFor`). An alias never
  borrows its character's portrait. Send-As doors pass `fromContactId`.
- **Admin panel** — A tab's context is SPREAD into the panel context, never cherry-picked. Admin CSS uses `--ncm-*`
  tokens; coloured text uses the ink mix; a lock is violet, red is only for bad. New buttons use `tabAct`, not a new
  static delegator. A ScopePicker callback fires on open too: compare before acting. A new selection opens its group
  once, then the GM's fold wins. A tab's context and its template change in one step.
- **Networks** — The node scene rule is enforced in ONE place, `NetworkService.getAvailableNetworks`. **Simple
  network mode** (`networks` feature off, step 17) is answered inside NetworkService (`this.simple`: CitiNet, full
  signal, no dead zones / logins / restricted mail, every gate passes, nodes inert) — a new network answer honours it there, not in its callers. Node writers
  run through the queue (`NODE_WRITERS`); no writer calls another. Skill resolution goes through `SkillService`.
- **Shards** — Write entries only through `DataShardService.addMessage`. A player's state writes on a world shard go
  through `_canWriteItem` → relay. `canEncode` is the one encoder gate and `canEditShard` the one edit door. The
  shard palette is data (`buildShardThemePrefs`); `--sp-*` derive from `--ncm-*` in one place. A preset never hands a
  player its security block.
- **Content types** — Adding a type = `CONTENT_TYPES` + `CONTENT_TYPE_INFO` + optional `ENRICHERS` fn +
  a `content-body.hbs` branch (+ a composer fieldset). `interactive` means "this consumer wires the actions"; only the
  composer preview passes false. Locked data is removed in the enricher, never hidden with CSS. A new message field
  goes in all four flag builders (`_buildMessageFlags`, `createMessage`, `_pageToMessage`, `addMessage` +
  `_pageToShardMessage`) and the edit-prefill openers (`terminalEditData`).
- **Terminals** — A login lasts as long as the window (`_unlocked`); never call `requiresAuth` from a login path.
  Player session writes relay. Every terminal sound goes through `resolveTerminalSound`. A mailbox layout is a skin
  over one view-model and the same data-actions. Collapse/expand toggles are DOM-only (a CSS transition can't survive
  an AppV2 re-render). Content reads go through `_boxId()` / `_boxMessages()`.
- **Programs & security** — Every trace goes through `fireTrace` / `logSuccess`. Something that reacts to a trace
  listens for `EVENTS.TRACE_RECORDED` `{ row, heat }` (GM side) — residents do (`TerminalService.residentsOnTrace`);
  the trace spine calls no one. Heat, the GM alert and the player splash happen only while `consequencesOn`. `PROGRAM_EFFECTS` is the one effect
  catalogue; a verb never claims a mode its applier lacks. The forge check is a ladder (clean / sloppy / rejected);

- **Rolls** — `beatsDV` / `d10Odds` (`rolls.js`) are the one rule; a tie fails. A roll with no animation uses

  `cancelled`.
- **Access points** — One door, `game.nightcity.openAccess(ref)`. Themed dialogs open with
  `THEMED_DIALOG_CLASSES` (keep `'dialog'`). Never wrap a placeable's click handler; read the DOM event after release.
- **Phone / payphones** — A booth side is masked per recipient in `CallService._send`; masking is on screen, not
  secrecy. Emergency words are slots, never literals in `EmergencyHud`. Calls, Payphones, Emergency and Overheard are
  features (`isFeatureOn`); a new way into one of them checks its service's `enabled`.
- **Conversations** — Writes go through the one GM queue; lines are plain text; a pane paint replaces what is inside
  the host, never the host. Off = no hooks, no sockets, no UI.
- **Watch** — A window opts in with `static WATCHABLE`; `mountMirror` morphs in place; decorative animation carries
  `data-watch-ignore`.
- **UI shell** — UI sounds are centralised in `BaseApplication` (no hover sound, no manual `play('click')`).

## Architecture: UI apps

All NCM windows extend `BaseApplication` (`scripts/ui/BaseApplication.js`), which is `HandlebarsApplicationMixin(ApplicationV2)`. BaseApplication provides:

- `subscribe(event, callback)` — managed EventBus subscriptions auto-cleaned in `close()`
- `_debouncedRender()` — 150ms coalesced render for bursty event sources
- `_applyAtmosphere()` — sets `data-ncm-scanlines/neon/animation-level` attributes on the root
- `playSound(id)` / `playEffect(el, cls, ms)` — respect user prefs
- `_animationActive` flag — set by handlers during multi-step flag writes to suppress debounced re-renders mid-animation

**Always use `_onRender` for post-render DOM work.** Never override `render()`. ApplicationV2 template parts must have a single root element.

## Architecture: AdminPanel composition

`scripts/ui/AdminPanel/AdminPanelApp.js` is a thin shell (~1,000 lines). Tab logic lives in **7 separate files** under `scripts/ui/AdminPanel/tabs/`:

```
AdminPanel/
├── AdminPanelApp.js     ← lifecycle, services, action dispatchers, EventBus, keyboard
├── BaseTab.js           ← abstract: prepareContext / onRender / onClose + service proxies
└── tabs/
    ├── OverviewTab.js   ContactsTab.js   MessagesTab.js
    ├── NetworksTab.js   ShardsTab.js     SpamTab.js   ToolsTab.js
```

Tabs are **composed, not inherited** — `AdminPanelApp` holds instances in `this.tabs = { overview, messages, ... }` (lazy-init via getter). Tab classes own their own state (`this._search`, etc.), data gathering, DOM wire-up, and action-handler implementations.

**Why static action handlers stay on `AdminPanelApp`**: Foundry's ApplicationV2 binds the `static DEFAULT_OPTIONS.actions` map at class load. Static methods must remain on the parent. Each handler body is a **one-line delegator**:

```js
static _onContactFilter(event, target) {
  this.tabs.contacts.onFilter(event, target);
}
```

Inside the static method, `this` is the `AdminPanelApp` instance (Foundry binds it). Inside the tab method, `this` is the tab instance.

**Adding a new admin panel action:**
1. Add the action name → static handler in `DEFAULT_OPTIONS.actions`
2. Add a one-line static delegator method on `AdminPanelApp`
3. Implement `onXyz(event, target)` on the appropriate tab

**Cross-references from a tab to parent state/methods** go through `this.app.X`:
- `this.app._saveScroll()` — preserves admin-content scroll
- `this.app._activeTab` — currently active tab key
- `this.app._animationActive` — suppress debounced renders during multi-step writes
- `this.app._relativeTime(iso)`, `this.app._getRelativeTime(ts)` — formatters
- `this.app.constructor._findItem(id)` — static item lookup (used by ShardsTab, NetworksTab)

## Architecture: templates

All `.hbs` paths are constants in `TEMPLATES` (in `scripts/utils/constants.js`) and preloaded by `scripts/init/registerTemplates.js`. **A "Partial not found" error at render time means the file isn't in `TEMPLATES`** — add it there.

CSS is a single entry: `styles/night-city-messenger.css` `@import`s every other stylesheet. New stylesheets must be added there.

## Foundry v12 / ApplicationV2 gotchas

**Moved Foundry APIs go through `scripts/utils/compat.js`** (stage 2, step 10 — v13 readiness). `renderTemplate` /
`loadTemplates` / `getTemplate` (import them from compat; bare calls then reach the right one), `FilePickerClass()` /
`newFilePicker(opts)` / `browseFiles(…)`, `ImagePopoutClass()`, `DocumentOwnershipConfigClass()`,

Each tries the
v13 namespace first and falls back to the v12 global, so nothing prints a deprecation warning on v13 and v12 keeps
working. `dev/tools/check-deprecations.mjs` (in run-checks / CI) fails on a direct use outside compat.js, and holds a
count for what is still to move (v1 `Dialog`, `html.find`, `$(`) that may only go DOWN, and bans the old `renderChatMessage` hook and `controls.push(`. Verified live on v12 (build 343): no namespaced path exists
there yet, every lookup returns the real v12 class.

**Every NCM dialog is an `NcmDialog` (`scripts/utils/ncmDialog.js`) — Foundry's DialogV2 frame taking the v1 Dialog's settings** (stage 2, 2026-11-05; v1 is removed in v16). Open dialogs ONLY through the `adminTheme.js` wrappers (adminDialog / adminConfirm / adminPrompt / adminWait, the player* twins, themedConfirm / themedPrompt); `check-deprecations` bans a raw v1 `Dialog`. It keeps v1 semantics (button callback then `close` on every close; confirm Yes-default → true/false/null; prompt REJECTS on close; callbacks get jQuery `html`), renders v1's inner markup (`.dialog-content` / `.dialog-buttons` / `button.dialog-button[data-button]`) in a plain div, never a `<form>` (CPR styles `form .form-group label` dark), and namespaces button actions (`ncmb-<key>`: a button keyed `close` would replace the frame's close). The render hook is `renderNcmDialog`. Only frame differences go in `styles/components/dialog-v2.css`. Don't add an `autofocus` attribute to a default button: Foundry focuses `[autofocus]` after the render callbacks and steals a prompt field's focus. Sims use `dev/tools/sims/lib/dialogMock.mjs` (a DialogV2 stand-in the real NcmDialog runs on). Mock: `dev/mockups/dialog-v2-mock.html` (v1 beside V2, real cascade, `?core=13`, `?as=player&zoom=120`).

These have all bitten the project. Don't relearn them:

- `data-action` on `<select>` fires on **click** (dropdown opens), not on value change. Add a manual `addEventListener('change', ...)` for selects.
- Element-level `addEventListener` is unreliable in Foundry (DOM focus issues). Use `document.addEventListener` with an app containment guard, and remove it in a `close()` override.
- `item.update()` uses `mergeObject` on nested flag paths — for reliable resets, do `await item.unsetFlag(...)` then `await item.setFlag(...)`.
- `Dialog` callbacks don't return values to a Promise — use a mutable variable in the callback, read it after `close: () => resolve()`.
- `FormDataExtended` is unreliable with selects/checkboxes in ApplicationV2 — read DOM directly via `querySelector`.
- ApplicationV2 template parts must have a single root element.
- `render(true)` forces a template re-render; `render(false)` only repositions.
- `CONTACT_DECRYPTED` and similar EventBus events fire **synchronously** inside their producer methods. Use a guard flag (e.g. `_breachInProgress`) to prevent premature renders that detach animated DOM.
- `_onRender()` is the only safe post-render DOM manipulation point. Use a `_pendingReveal` flag pattern when you need to defer animation work to the next render.
- **Static methods aren't on the prototype.** `this.foo()` from inside another static method (where `this` is the bound instance) silently fails when `foo` is also `static` — `this.foo` returns `undefined`. If a method needs to be invoked via `this.x()` from a static context (such as ApplicationV2's static action handlers), it must be an instance method. This bit `ContactsTab._showShareDialog` and was a latent bug for an unknown amount of time.
- **A button's `disabled`/enabled state driven by a template variable won't update for live inputs that don't re-render.** Sliders, color pickers, `<select>`s, and text fields wired via `addEventListener` typically mutate working state without a `render()`, so a `{{#unless dirty}}disabled{{/unless}}` button stays stuck. Toggle the `disabled` attribute (and the disabled class) directly in the DOM from the change handler. This bit the Theme Customizer Save button — fixed via `_markDirty()`, which sets the flag *and* pokes the button.
- **`../` in a template counts BLOCKS, not object levels — and `{{#if}}` is a block.** Handlebars pushes a depth frame for every block it enters, so `{{#each ../list}}` inside two nested `{{#if}}`s (an `{{#if}}/{{else if}}` chain counts too) walks out past the root and resolves to **nothing** — no error, just an empty loop. That is what rendered the GM Contact Manager's detail-panel Share select as a "Players" heading with no one under it, while the identical top-bar select (same data, one frame shallower, no `../`) worked. **Reach for root data with `@root.x`**, which is depth-proof; keep `../` for stepping out of an `{{#each}}` you are actually inside. A bare name also works — it searches the current frame — but only until someone nests the block one deeper. Sim: `dev/tools/sims/test-gm-share-targets.mjs` compiles the REAL template through Handlebars and asserts each select lists the characters (it judges each select separately, since a whole-document search let the working one cover for the broken one).
- **A Font Awesome 6 glyph class alone renders NOTHING — it needs the FAMILY class too.** `<i class="fa-gun">` has a `::before` content rule but no font-family; only `fas`/`fa-solid` supplies it. `getRoleIcon` (designHelpers.js) returned bare `fa-x` for years, so every role chip on player contact cards / detail / list rows was an empty gap (tester 2026-10-21: "solo and netrunner icons don't appear"). It now returns the WHOLE class (`fas fa-crosshairs`), its built-in table mirrors the GM's role table (RoleManagerDialog `BUILT_IN_ROLES`) so a role looks the same on both sides, and GM custom roles resolve through `masterContactService.getCustomRoles()`. The Contact Manager's private `roleIcons` copy is gone. Sim: `dev/tools/sims/test-role-icons.mjs`. Rule: an icon string that reaches a template is a full class, never a bare glyph name.
- **A context FIELD named like a registered Handlebars HELPER never prints — `{{sub}}` CALLS the `sub` helper (subtraction) with no arguments and renders `NaN`** (the group tray's member line, tester 2026-10-21). Handlebars resolves a bare mustache as a helper first. registerTemplates.js registers `eq neq gt lt gte lte and or not add sub letter join lower upper truncate substring…`, so none of those is a safe field name. `dev/tools/sims/test-helper-collisions.mjs` reads the helper list and fails on any bare `{{name}}` / `{{#if name}}` use of one across every template.
- **Our Handlebars helpers named like Foundry's (`eq neq gt lt gte lte and or not`) REPLACE Foundry's for EVERY template in the game, core and system ones included — they must answer exactly like Foundry's.** A helper always receives Handlebars' options object as its last argument, block or subexpression; v2.0.7's `or`/`and` only dropped it for a block, so `(or a b)` counted an always-truthy object and core's token HUD rendered the elevation box `disabled` for everyone (testers 2026-11-03; fixed with `_isOptions` in registerTemplates.js, sim `dev/tools/sims/test-core-helpers.mjs` runs Foundry's real token-HUD line). A global helper or a scene-control `layer` shared with core is a change to OTHER modules' behaviour: the module's button group has its own `ncmControls` layer because core picks the first group on a shared layer (Grid Scaler opened instead of the messenger). To reproduce a "breaks something outside NCM" report, join the dev's running world as an offline player in headless Chrome over CDP (see memory `live-foundry-cdp`).
- **Script macros run with `speaker, actor, token, character, scope` predefined** as the macro function's parameters. Declaring a local `const actor`/`token`/`character` is a redeclaration error — use other names (`_who`, etc.). Foundry wraps the body in an **async** function, so top-level `await`/`return` are legal (validate macro source the same way — see Compendium packs).

## CSS specificity patterns

- Foundry's globals require `!important` on most `ncm-actlog__` and Network Manager rules.
- `border:` shorthand with `!important` kills inline `border-color` — split into `border-width` + `border-style`.
- `background:` shorthand with `!important` kills `background-image` SVG arrows on selects — split into `background-color` + `background-image`.
- CSS custom properties must be scoped to `:root` (not `.ncm-app`) for ThemeService overrides to apply.
- Foundry button reset must be element+class at specificity 0,2,1 — kill structural defaults only (height, min-height, appearance, box-shadow, margin, background-image), never visual properties.
- `overflow: hidden` vs `visible` is a tradeoff — `visible` fixes dropdowns but breaks flex scroll chains. Resolve by ensuring dropdowns open into a non-clipped area.
- **Foundry's global `.flexrow > *, .flexcol > * { flex: 1 }`** stretches every direct child of a flex row. Anything you inject into a Foundry sheet/sidebar (badges, wrap spans, custom widgets) needs `flex: 0 0 auto !important` or it will fill the row and push sibling content aside. The `.ncm-shard-thumb-wrap` span around inventory data-shard thumbnails is the canonical example.
- **`display: inline-block` on a flex item can render invisible.** When the wrap also has `line-height: 0` (or other line-box-collapsing styles), the element computes to zero size. Use `display: inline-flex` (with `align-items: center`) instead — it gives the element its own flex context and sizes reliably to its content.
- **CSS variable typos render as invisible, not error.** `var(--missing-name)` with no fallback resolves to the property's initial value (often `transparent` for backgrounds/borders, blank for colors). If a UI element looks empty/blank, grep `styles/base/variables.css` to confirm the var name. The actual NCM names are `--ncm-primary`, `--ncm-secondary`, `--ncm-accent` — there is **no** `--ncm-color-*` prefix. The blank shard preset's loading bar was invisible for this reason.
- **Standalone (non-admin) NCM windows still need explicit Foundry button/input resets.** A bare button (e.g. `.ncm-aip__row`) renders with Foundry's white default; scope rules as `.ncm-app button.<class> { … !important }` and reset `appearance` / `box-shadow` / `background` / `height`. This bit the ActorImportPickerApp.
- **A bare `<hr>` renders with the Cyberpunk RED system's gradient, not your border.** The CPR system styles `hr` with a gradient `background`/`border-image`; a divider rule that only sets `border-top` lets that gradient show through underneath. To force a flat line, raise specificity (`.ncm-app hr.<class>`) and add `background: none !important; border-image: none !important; height: 0`. This bit `.ncm-form-divider` (the "GM-ONLY FIELDS" divider in the contacts form).
- **Decorative gradient accents were deliberately flattened to solid lines** (per dev preference). Converted: the player Contacts app top accent (`.ncm-contacts-v5::before`), the date-range picker top accent (`.ncm-time-config-dialog::after` in `tab-tools.css`), and the GM Contact Manager top bar (`.ncm-gm-bar`) + top accent line (`.ncm-gm-contacts::before`). All use solid `var(--ncm-*)` now. If adding new chrome accents, prefer a flat line over a `linear-gradient`.
- **Foundry defaults `<button>` to `width: 100%`.** Converting an inline `<span>` badge/pill into a `<button>` (to make it clickable) makes it stretch full-width — and a flex-row parent stretches it further. Add `width: auto !important; flex: 0 0 auto !important`. This bit `.ncm-viewer__detail-thread` (the Thread pill) the moment it became a button.
- **Search fields: use the flex pattern, not an absolutely-positioned icon.** An `position:absolute` magnifier over a padded input overlaps the placeholder in Foundry. Instead use a bordered flex wrapper holding the `<i>` as a sibling beside a borderless, `padding:0` input — see `.ncm-net-config-search` / `.ncm-scene-ctl__search-wrap`.
- **Tooltips use Foundry's native `data-tooltip` (+ optional `data-tooltip-direction="UP|DOWN|LEFT|RIGHT"`), NOT CSS-pseudo tooltips.** Foundry renders `#tooltip` on `document.body`, so it escapes the window and auto-flips at edges. The old `data-ncm-tooltip` CSS-pseudo approach was clipped by `.window-content { overflow:hidden }` (pseudo-elements can't escape an overflow-hidden ancestor; the contrast `filter` + viewer `container-type` made fixed-escape impossible too — note the contrast `filter` has since been removed in favor of OKLCH palette tone-mapping, but `container-type` remains, so the native-tooltip decision stands). All usages were migrated; the dead `[data-ncm-tooltip]` rules linger inert in `styles/base/interactions.css`.
- **Text elements must declare `font-family: var(--ncm-font-*)` to follow themes.** A rule with no `font-family` silently inherits Foundry's default and won't respond to the Theme Customizer's font selection — it looks fine until a player switches fonts and that one element stays put. The slots are `--ncm-font-title`/`--ncm-font-ui` (Orbitron chrome), `--ncm-font-display`/`--ncm-font-body` (Rajdhani; use for prominent names/subjects), `--ncm-font-mono` (Share Tech Mono; technical values only). This bit `.ncm-viewer__detail-sender-name`, which had only `font-size`/`color` and ignored theme fonts.
- **`overflow-y: auto` with no explicit `overflow-x` spawns a phantom horizontal scrollbar.** Per the CSS overflow spec, setting one axis to a non-`visible` value computes the other (`visible`) axis as `auto` — so a 1px content overrun shows a horizontal scrollbar. Always pair them: add `overflow-x: hidden` next to any `overflow-y: auto`. This bit the date-range picker dialog content (`.ncm-time-config-dialog .window-content` in `tab-tools.css`).
- **Indentation comes from a section wrapper, not the row.** In the Theme Customizer, rows get their 16px horizontal inset from a padded `.ncm-tc__font-section` (`padding: 8px 16px`) / `.ncm-tc__slabel`/`.ncm-tc__name-hint` (`… 16px`), NOT from `.ncm-tc__srow` itself (which is `padding: 6px 0`). A `.ncm-tc__srow` placed directly in the panel (outside a section) sits flush-left and misaligns — wrap it in a section. This bit the Agent Name row.
- **Text is unselectable by default — Foundry core AND the CPR system both ship `* { user-select: none }` resets** (foundry2.css `@layer reset` and the CPR style.css Theme-V1 rules). Every player-readable surface must OPT IN, and because a directly-matched `* { none }` beats an *inherited* `text`, the opt-in must hit descendants directly: `.container, .container * { user-select: text }`, then re-disable on `button`/`[data-action]` so clicks don't smear selections. Blocks live in message-viewer.css (`.ncm-viewer__detail-body *`, the original), item-inbox.css (`.ncm-item-inbox *`), terminal.css (`.ncm-terminal-viewer *`, keypad excluded), and content-types.css (`.ncm-entry-body *` / `[class*="ncm-ct-"] *` — covers typed content everywhere incl. the composer preview). New windows that display copyable text need the same block ("all the text isn't selectable" was the 2026-07-11 bug report).
- **The `hidden` attribute loses to any author `display` rule.** `[hidden]`'s UA style is plain `display:none`, so a class like `.ncm-cfg-row { display:flex }` makes a `hidden` row render anyway. Pair toggle-by-`hidden` markup with `.<scope> [hidden] { display:none !important }` (see `.ncm-acct-editor` in terminal.css — the custom-clearance and datetime rows rendered visible without it).
- **A relative `url()` inside a CSS custom property resolves against the stylesheet that USES the `var()`, not the document base.** Setting `--x: url('worlds/img.webp')` via `setProperty` and consuming it in `styles/components/*.css` fetches `/modules/…/styles/components/worlds/img.webp` → silent 404 → "the image just doesn't show". Root the path first (`foundry.utils.getRoute`, typeof-guarded). This was the terminal-wallpaper bug.
- **A flat `position: relative` on a selector list can silently override a member's existing `position: absolute`** (equal specificity — later in the file wins), collapsing an `inset:0` overlay into normal flow ("the card jumped to the top"). Wrap positioning *defaults* in `:where(…)` (zero specificity) so they can never out-order a real scheme. Related: to slot a decorative pseudo UNDER an element's content without touching the children, give the host `isolation: isolate` and the pseudo `z-index: -1` — never blanket `> * { position:relative; z-index:1 }`, which also flattens any child's deliberate higher z-index (the login hero's dropdown).
- **AppV2 root classes are SAME-ELEMENT — `.ncm-app .ncm-<window>` descendant selectors are DEAD when `<window>` is an app root class.** `DEFAULT_OPTIONS.classes: ['ncm-app', 'ncm-data-shard-composer']` both land on the ONE application root, so the descendant form never matches; write `.ncm-app.ncm-data-shard-composer` (compound, no space). It works for OTHER windows only because their inner template root repeats the class (`.ncm-item-inbox`, `.ncm-admin-panel`, `.ncm-viewer` are template-root classes) — the composer's template root is `.ncm-composer-shell`, so its ENTIRE `.ncm-app .ncm-data-shard-composer` normalization block (checkbox 13px, input 22px, DV max-width, text-align:left — the #25b/#31 fixes) silently never shipped until 2026-07-13. Symptom: "fixed" sizing bugs the dev keeps reporting; headless repros pass because they hand-build nested divs.
- **The Foundry desktop app's Chromium handles CSS `zoom` differently from current Chrome.** `getScreenCTM()` and `getBoundingClientRect()` disagree inside a zoomed element there, so code mixing the two placed the payphone cord off the handset in the app, while it looked right in Chrome (2026-11-05). Measure both ends with ONE API (`PayphoneBooth.cordPoint` maps a rect into a viewBox). A "fine in Chrome, off in Foundry" report on zoomed UI is this.
- **A themed `<select>` in a body-mounted admin Dialog still has WHITE options unless you style `option` too.** Foundry core sets `select option { background: var(--color-select-option-bg) }` and that var is **`transparent`**, so Chromium paints the popup white while the options inherit the select's text colour → on the dark admin presets, white-on-white until hover (the Shards tab's Quick Create / Convert Item pickers, tester 2026-10-20; "fine on the light theme" because text-primary is dark there). AppV2 windows are covered by `.ncm-app select option` (contact-manager.css); dialogs are not — admin-theme.css now carries `.ncm-admin-dialog[data-ncm-admin-theme] .window-content select option`. Any NEW select host outside `.ncm-app` needs its own `option` rule.
- **A fixed-px `height` on a control whose `font-size` is `calc(Npx * --ncm-text-scale)` CLIPS when the player raises Text Size.** The font sweeps scaled the glyphs but left `height: 26px !important` boxes behind — Encoder inputs, the player entry composer's `.ncm-config-input`/number boxes, the schematic pin popover, the composer's net-search + encryption-DV inputs, the viewer's category-pill strip (tester: "text box is not sizing and cuts off text"). Rule: **size a scaled control's height with the same `calc()`** (`height: calc(26px * var(--ncm-text-scale, 1))`). Admin-tagged windows force the scale to 1, so GM sheets were never affected — test with the Theme Customizer slider or the Encoder's DISPLAY panel.
- **Browser password managers offer the player's FORGE login on an in-fiction login screen (tester, 2026-10-20).** A text field followed by a `type="password"` field is the shape every manager pattern-matches as a sign-in form for the current ORIGIN (forge-vtt.com), and `autocomplete="off"` is deliberately ignored for logins. Every secret field in the module (shard login, terminal manual/lock/keypad/net-join, the network auth dialog, the composer's credentials card) now carries **`autocomplete="new-password"`** (the one value Chrome/Edge/Firefox honour — no saved-credential fill), the extension opt-outs (`data-lpignore` / `data-1p-ignore` / `data-bwignore` / `data-form-type="other"`), and a field `name` that no longer says username/password/login (`ncm-shard-op`/`ncm-shard-key`, `ncm-term-op`/`ncm-term-key`/`ncm-term-netkey`, `ncm-net-key`) — the name is a heuristic on its own. **Second layer, because the attributes are only a hint:** `guardSecretInputs(root)` (helpers.js, called from the shard viewer's, terminal viewer's and network-auth dialog's `_onRender`) makes every secret field and handle **readonly until the first pointerdown/keydown** — no browser autofills a readonly field, and the guard lifts before the key's default action so the keystroke lands (focus alone does not lift it: an autofocused field would lift at render). `input.ncm-autofill-guard[readonly]` in interactions.css keeps it looking live. **Third layer, the one managers cannot see (dev, 2026-10-21: Chrome's manager AND NordPass still offered the Forge login after the attributes, the readonly guard AND a CSS-masked text field — Chromium's form parser treats a text field carrying `-webkit-text-security` as a password field, and NordPass keys on a "Username" label):** `shadowSecretInput(el)` (helpers.js, applied by `guardSecretInputs`) makes the field a **plain text input whose DISPLAYED value is bullets painted by the module**; the real text lives in script and is served through an instance override of the element's `value` property, so every reader (`input.value`) and writer (the keypad's `input.value = …`) works unchanged, and `beforeinput` keeps typing / backspace / paste in sync. Nothing on the element says password: no type, no CSS mask, no label (the shard login reads **Operator / Passcode** and the terminal prompt **OPERATOR** — after "Account" + a "handle" name + an "admin" placeholder still drew NordPass to the name field, nothing on that field may read as a username to a manager: label, `name`, placeholder (the name fields carry `data-ncm-login`, which is what the guard selects). **And then NordPass still attached to the plain text field whatever it was called**, so `shadowLoginInput(el)` replaces the name `<input>` with a **contenteditable element** dressed in the input's computed style, mirroring into the original input turned `type="hidden"` — readers that query `[name="ncm-shard-op"]` are untouched, Enter moves focus to the passcode, paste is flattened to one line. Managers attach to inputs; they do not attach to editable text. **The passcode got the same treatment next** (NordPass moved to the shadowed text input the moment the name field stopped being one): `shadowSecretInput` now also builds a contenteditable (`.ncm-secret-ce`) in front of the input turned `type="hidden"`, shows bullets, serves the real text through the hidden input's `value`, and **forwards keydown Enter to the hidden input** so the terminal / net-join / auth-dialog Enter listeners still fire. Net: a player login screen contains NO visible `<input>` at all). The auth dialog's eye calls `el.ncmSetMasked(false)`. **Never add `-webkit-text-security` or `type="password"` back to a player login field.** A new secret field = same three things + a `guardSecretInputs` call in its window's `_onRender`; `dev/tools/sims/test-login-autofill.mjs` fails on any `type="password"` without them, or any input on a player login screen whose name matches username|password|login (GM config sheets, where the GM types the password a shard will demand, are text fields on an admin window and are not in scope).
- **Foundry v12 checkboxes are `appearance:none` + FontAwesome `::before/::after` glyphs sized by `--checkbox-size` (default 20px).** Forcing only `width`/`height` leaves a 20px glyph overflowing the smaller box = "uncentered checkboxes". Set the VAR (`--checkbox-size: 13px`) — the glyph's width/height/font-size/line-height all read it. `accent-color` does nothing on these; the check color is `--checkbox-checked-color` (core defaults it amber — set it to `--ncm-secondary` for brand).
- **Foundry core `button > i { margin-right: .25rem }` shoves the glyph off-center on icon-ONLY buttons** (the AV ▶, remove ✕s, browse/dice chips). Fix with `button i:only-child { margin: 0 !important; line-height: 1 !important; }` scoped per surface (composer root + `.ncm-entry-body`/`[class*="ncm-ct-"]` for typed content) — icon+text buttons keep the core gap. Headless repros MUST include the real `foundry2.css` (+ FA css + CPR `main.css`, all file:///-loadable) or none of these core interactions reproduce.
- **Scrollbars are themed CENTRALLY in `styles/base/scrollbars.css` — never write scrollbar CSS in a component again.** Two Foundry traps made this necessary: (1) core ships `* { scrollbar-width: thin; scrollbar-color: … }`, and although `scrollbar-color` is an *inherited* property, a **directly-matched** declaration beats an inherited one — so core's `*` re-asserted its bar on every descendant and NCM's old `.ncm-app { scrollbar-color }` never reached anything inside the window (the exact `user-select: none` trap); (2) in Chromium, **specifying `scrollbar-color` DISABLES all `::-webkit-scrollbar-*` styling** for that element — so every webkit scrollbar rule in the module (26 files' worth) was dead code and had been for as long as they've existed. The fix matches descendants directly (`.ncm-app *`, plus the non-`.ncm-app` dialog roots and the body-mounted modals) and colors from `--ncm-*`; because custom properties resolve from the nearest ancestor, a **terminal automatically gets its preset's scrollbar** and the Admin Panel gets the admin theme's, with zero per-surface rules. Per-surface override: set `--ncm-scrollbar-thumb` / `--ncm-scrollbar-track` on the scroller or an ancestor. To hide one, `scrollbar-width: none` at specificity ≥ 0,2,0. Verified against the real core+CPR cascade (brand/terminal presets/admin/override all distinct, non-NCM panes untouched).
- **Never force `overflow: visible` on a Dialog's `.window-content` — it kills the only scroller a v1 Dialog has.** Foundry's `.app { max-height: 100% }` caps the frame at the viewport and `.window-app .window-content { overflow: hidden auto }` is what lets a tall body scroll; `overflow: visible` ALSO flips the content's flex `min-height` from 0 to its full height, so nothing shrinks and the frame's `overflow: hidden` silently eats the footer. Invisible at 100% Text Size (the body fits); at 120% the player-dialog zoom makes the breach dialog taller than the screen and the Execute/Abort buttons vanish with no scrollbar (tester 2026-10-22; Tab still reached them because focus scrolls a hidden-overflow box, and then nothing could scroll back). `.ncm-hack-dialog` and `.ncm-token-picker-dialog` now clip the frame + content, make `.dialog-content` the one scroller, and pin `.dialog-buttons` (`flex: 0 0 auto`). Probe: a static harness in the session scratchpad measured the real cascade at zoom 1/1.2/1.5. A `::-webkit-scrollbar { width: 0 }` on a dialog is dead under scrollbars.css anyway — don't add one.
- **In a modal that scrolls, make the CONTENT LIST the scroller — never the panel.** If the panel itself scrolls, its pinned furniture (a progress/verify strip, the footer buttons) scrolls out of view and the user picking an item near the top sees "nothing happen". Panel = `display:flex; flex-direction:column; overflow:hidden`; the list = `flex:1 1 auto; min-height:0; overflow-y:auto; overflow-x:hidden`; and the list's **children need `flex: 0 0 auto`** or they shrink and their contents overlap (the same shrink gotcha as the composer sections). This bit the OperatorSelect roster.
- **A CLASS-NAME COLLISION between two module stylesheets is the most expensive CSS bug here, because it presents as "a mystery framework rule".** `styles/` is one flat namespace: two files both scoped under `.ncm-app`/`.ncm-admin-panel` land at the SAME specificity (0,2,0), so the later `@import` wins **per declared property** and the newcomer **silently inherits every property it does not re-declare**. The Security tab shipped as `.ncm-sec-card`, colliding with security-overlays.css's `.ncm-app .ncm-sec-card` (the shard/network breach splash) — which meant the admin card inherited `max-width:400px; width:90%; text-align:center; max-height; overflow-y:auto`. That produced "the card is squished to half width and everything is centered", was **misdiagnosed as a Foundry core 400px cap on content children (there is NO such rule — core's only `max-width:400px` is `.tour-center-step`)**, and got band-aided with `width:100% !important; max-width:none !important` while the centering/max-height stayed. Rules: (1) **before naming a new component, `grep -rn "\.ncm-<prefix>" styles/`** — if the prefix is taken, the NEWCOMER renames (shipped code keeps the name); (2) the admin-panel twin of a taken prefix takes an `-admin-` infix — `ncm-term-*` (terminal viewer) → `ncm-term-admin-*`, `ncm-sec-*` (breach overlays) → **`ncm-sec-admin-*`** (this tab); (3) don't scope generic names (`.tk`, `.tier`, `.state`) to the whole panel — nest them under the component.
- **Two Foundry core resets that bite any new admin surface** (both proven on the Security tab): core ships a bare **`table { margin: 1rem }`**, so any table without `margin: 0` sits shifted 16px right and its last column disappears under a card's `overflow:hidden` (the "↗ / Purge button is cut off" bug); and the module's own **`.ncm-app label { text-transform: uppercase }`** (base/typography.css, a display-font micro-caption) hits EVERY `<label>` — a checkbox label that's a sentence must opt out with `text-transform:none; font-family:var(--ncm-font-body); font-weight:400` or it renders "GM ALWAYS HAS ACCESS". Also: a `.ncm-x-frow > label` field-key rule will match a `<label class="checkbox">` sibling too — exclude it (`> label:not(.ncm-x-check)`).
- **A header row of flex children SHRINKS before it wraps.** Foundry/CPR give no min-widths, so an overcrowded toolbar squeezes its title/badge/chips into 2-3 line stacks rather than moving anything to a second row. Fix by making nothing shrink (`> * { flex: none }` + `white-space: nowrap` on the text bits) and letting the row `flex-wrap: wrap`. **Size it against the SCROLLBAR-PRESENT width**: the admin panel is 820×600 and a long tab always has a vertical scrollbar, so the real content box is ~15px narrower than a preview whose frame is tall enough to avoid one — a header that fits in the preview wraps in the app. `admin-security-preview.html` forces `overflow-y:scroll` for this reason.
- **Measure, don't grep — but make the measurement honest.** A faithful headless preview + `getComputedStyle` is the only reliable way to find these; `admin-security-preview.html?diag=1` reports overflow, wrap, computed `text-align`, and an inheritance chain. Three traps that made the diagnostic itself lie, all fixed there: a rule-matcher must **recurse into `@layer`/`@media` (`r.cssRules`) AND `@import` (`r.styleSheet.cssRules`)** — `night-city-messenger.css` is 57 imports, so a flat top-level scan finds *zero* module rules and every real culprit reads as "no matching rule"; `clientHeight` **includes padding**, so a padded cell reads as "wrapping" unless you subtract it; and flex children are center-aligned, so counting distinct `offsetTop`s reports one row per child — count row *bands* instead.
- **`.ncm-app` is `position: fixed !important` (window-chrome.css) — a MOCK page that frames several windows must pin every frame back into flow.** A mock built from a real window root (`.ncm-app`, `.ncm-terminal-viewer`) inherits that rule, so on a scrolling page every frame piles up at the top, the first one follows the scroll, and the stack reads as "glitchy / half empty" (dev, 2026-10-25, both terminal mocks). A single-frame headless shot never shows it. Frame mocks with a plain `.mk-win` (never Foundry's `.application`, whose own absolute positioning + `max-height:100%` is a second trap) and declare `.mk-win, .mk-win .ncm-app { position: relative !important; inset: auto !important; transform: none !important; max-height: none !important }`. Render the WHOLE page once (`--window-size=1000,3000`) before handing a multi-frame mock over.
- **A preview that loads only the component's own CSS is worse than no preview** — it renders clean while the real app is broken, because every core/CPR reset above is absent. Always load the real stack: `foundry2.css` → CPR `main.css` → `night-city-messenger.css` → the component, and keep `.ncm-app` on the host. (`upload-console-preview.html` was component-only and was made faithful.)
- **A `:hover` transform that MOVES the element off the cursor causes hover flicker — and there are TWO tiers of fix (2026-08-14, took two rounds).** (1) An **isolated** mover (message/terminal rows' `translateX(2px)`, terminal `__btn`/`__chip` lift): keep the motion, add an invisible **`::after` hitbox guard** covering rest position + travel on the trailing edge — pseudo hits count as the element, so the hitbox never shrinks mid-move (rows verified stable under real CDP mouse events). (2) An element that **ANCHORS A DROPDOWN as a child across a gap** (the viewer's Dates/Sort/Filters buttons, `.ncm-sort-dropdown`/`.ncm-filter-dropdown` nested inside) must **NEVER translate on hover** — the transform moves the whole button+menu assembly, so crossing the 4px anchor gap creates an oscillating boundary NO guard can stabilize (CDP-measured 11 hover flips per traversal, with the message rows underneath hover-flashing through the gap slivers — the dev's "buttons glitch in and out / list flashes", reported twice because round 1 only applied fix 1). Dropdown anchors get color/border feedback only, **plus a `::before` gap bridge on the dropdown** (`top:-5px; height:5px` — the menus are static, so a bridge makes button→menu one continuous hover region; without it the gap still flashes the row beneath once per crossing). Same unguarded pattern remains on larger hover-movers (quickdial cards, workshop `pcard`, deck carts, terminal `__card`/`__rrow`/`__port`, claim/go buttons) — apply tier 1 if reported (check `::after` isn't already an effect). **Verify with real mouse events, not reasoning:** `dev/tools/sims/cdp-hover.mjs` drives headless Chrome via CDP over `dev/mockups/refine-bar-flicker-harness.html` (full core+CPR+module cascade) and counts hover enter/leave storms — static-style assertions and `elementFromPoint` probes both missed the traversal storm.
- **A hard `min-height` on a flex child in a clipping column makes it overflow onto its sibling.** `.ncm-composer__editor` had `min-height: 120px` while being `flex: 1` inside the `flex:1` editor-wrap of an `overflow:hidden` composer column. When the composer is short (a reply whose quoted-message card eats vertical space), the wrap shrinks below 120px but the editor refuses to, so its box paints **down over the top of the footer's Send button** — and because the editor is `cursor: text !important`, that strip swallows clicks (only the button's bottom edge works; "top of the button won't click, cursor looks like text-select"). Fix: `min-height: 0` so the editor shrinks with its wrap; `flex:1` still fills when there's room. Do **not** "fix" it with `overflow:hidden` on the wrap — that clips the absolutely-positioned `.ncm-composer__overflow` "More tools" menu anchored inside it. (Diagnosed with `document.elementFromPoint` over the button in a headless-Chrome repro.)

## Conventions

- Console logging: use `log.info/warn/error/debug` from `scripts/utils/helpers.js`, not raw `console.*`. The `debug` channel respects the `debugMode` setting.
- BEM: `ncm-component__element--modifier`. Class prefix is `ncm-`.
- Fonts: Orbitron (UI chrome/titles), Rajdhani (body/display), Share Tech Mono (technical data values only).
- Cyberpunk RED lore: **Blackwall = red**, not purple.
- **NCM is NOT localized — copy lives inline in JS/HBS, and `languages/en.json` holds ONLY the 6 keys Foundry resolves for us** (5 `NCM.SceneControls.*` tooltips + `NCM.ContactManager.Title`). To change any string, grep the JS/templates, never the locale file. Cleaned up 2026-07-26: the file was 104 keys of which **84 were dead** and **9 were requested-but-absent** — and because Foundry auto-localizes a setting's `name`/`hint`, three `config: true` settings (`dateFormat`, `timeFormat`, `timeProvider`) were rendering the **raw key text** (`NCM.Settings.DateFormat.Name`) as their label in the GM's Module Settings menu. **Rule: register settings with LITERAL name/hint strings, never i18n keys** — all 54 now do (it was 38 literal / 16 keyed, and the mixed pairs, a keyed `name` beside a literal `hint`, are exactly how the three raw keys shipped unnoticed). Guard: **`node dev/tools/audit-i18n.cjs`** cross-checks both directions (exit 1 on a requested-but-missing key, lists keys nothing asks for) and knows to check `settings.register` name/hint — run it after touching either side. `helpers.js` still exports an unused `localize()` as the entry point if real i18n is ever wanted.
- **A new visible setting (`config: true`) goes in a section of `SETTINGS_LAYOUT` (`scripts/ui/settingsLayout.js`, step 18).** Foundry lists a module's settings in registration order; a `renderSettingsConfig` hook moves NCM's rows under section headings (rows found by input `name`, v12 + v13). Unplaced = an "Other" section and a `test-settings-layout` failure. A setting's name drops a prefix its heading already says.
- **Mock before visual code, and make the mock load the REAL cascade.** Standing dev preference. A mock file lives in `dev/mockups/`, is built from the real class vocabulary inside the real app root, and links Foundry core → CPR `main.css` → `night-city-messenger.css` (+ `admin-theme.css` for panel surfaces) — a component-only preview renders clean while the real app is broken. **A mockup that imports a real module CANNOT be opened off disk — serve it.** Chrome gives every `file://` URL its own opaque origin, so a `file://` page's ES-module `import` is refused as cross-origin, and the page renders with the imported thing simply missing: no error on screen, just a backdrop (the dev's "all I see is agent"). `--allow-file-access-from-files` fixes it for a headless render and does nothing for a double-click. **`node dev/tools/serve-mockups.cjs`** (zero deps, localhost, read-only) serves the repo at `http://127.0.0.1:8123/` and fixes every preview at once, including the ones that `fetch` a real `.hbs`. Two rules for a preview that must work both ways: guard the import with a **dynamic** `await import()` in a try/catch that renders the fix on screen (a static import fails before any of your code runs, so there is nothing left to say it with), and pick the two out-of-repo stylesheets from `location.protocol` — `file:///…` off disk, the server's `/_vendor/…` mirror over http, because an http page may not load a `file://` stylesheet. Render it headless and *look at it* (`--headless --screenshot`, full `file:///` URL — a bare filename is treated as a hostname). Query params to switch states beat one static picture. **Four design lessons the malware-workshop rounds paid for, applicable to any new authoring surface:** (1) **card walls don't scale past ~6 options** in a 640px window — eleven 196px option cards ate the whole composer and pushed everything below the fold, the same mistake the 18-pill type wall made before it became a grouped dropdown; compact chips or a grouped `<select>` instead. (2) **A per-field hint belongs IN its field** (placeholder or a sub-line in the same cell), never stacked in a list under the grid where it orphans from what it describes. (3) **If every choice produces an identical screen, the surface reads as bland** — let a real property of the data drive the page (the workshop keys colour off the ability *family*, which also encodes what kind of harm it does). (4) **Don't default to dark-panel + one accent + a preview rail** — that's the shape of every other surface here and the generic AI-design default; find the structure in the subject (a malware program *lies*, so the page is the cover stacked on the payload).
- **In-world vocabulary belongs on PLAYER-FACING IMMERSIVE surfaces ONLY — GM/authoring UI uses plain language.** (Dev's rule, 2026-07-26.) A GM building content should never have to decode fiction: composer intros/labels/hints, config tabs, and admin panels stay in normal conventions ("a recovered chat transcript", not "a BabelChat scrape"). Setting-flavor words go where the *player* is in the fiction — a breach console, an action console, a rendered artifact. Exception worth knowing: a **placeholder or fallback that supplies in-world CONTENT** (the chatlog's "Chat app" field → `BabelChat`) is fine, because the authored value is what the player reads — but keep the placeholder and the enricher fallback identical or the field promises a name the render contradicts.
- **Canon vocabulary (setting flavor).** `dev/design/CANON-VOCAB-AND-IDEAS.md` is the adopt/consider/skip list, governed by [[ip-homebrew-constraint]] — **names and reworded concepts only, never verbatim descriptions/statblocks/tables**. Applied 2026-07-26 under the rule above: **Breacher** (the shard hack sequence's banner + status chip), **AltLink** (the exfil-to-Agent console intro), **BabelChat** (the chatlog `app` placeholder + enricher fallback). Available but **not** placed, for want of a player-facing home: **SAAI** (the Agent's assistant), ZPost/BangMe!/WatchBox. **Do NOT name the SAAI in the shared trace copy** — `NotificationService.showShardTrace` is the ONE toast for every trace source (shard/terminal/network/camera) and a SAAI belongs to an *Agent*, so it would misattribute 3 times in 4; doing it properly needs a `context` threaded through the trace payload the way `showShardBlackICE` already reads `data.context`. **Demon** is the right word for a *box's* automated defender if that ever gets built.
- All timestamps use UTC getters; stored ISO strings end in `Z`.
- **Simple Calendar's `currentDateTime()` returns `month` AND `day` as ZERO-BASED INDICES** (`getMonthAndDayIndex()` in its bundle). `Date.UTC`'s month is zero-based too but its day-of-month is 1-based, so `TimeService` passed the day index straight through and every NCM clock read **one day behind the calendar** in SC/Auto mode (tester 2026-10-20). The mapping is now the pure static `TimeService.scDateTimeToMs(dt)` (`day + 1`); sim `dev/tools/sims/test-simple-calendar-date.mjs`. Mail stamped before the fix keeps its stored (one-day-early) timestamp — cosmetic, no migration. A non-Gregorian custom SC calendar can't map onto a JS Date at all; known limit.
- **All countdowns/expiries go through the time provider, not raw `Date.now()`.** Use `game.nightcity.timeService.getCurrentTime()` / `getCurrentTimeMs()` so timers respect the configured mode (real-time / world-time / manual / disguised). This covers self-destruct, network-access lockout (`MessageAccessService`), security/shard-hack lockouts (`SecurityService` — its auto-expiry is a poll-and-reschedule, not a single real-time `setTimeout`, so a paused game clock doesn't clear early), ICE breach lockout (`ContactBreachService`), the trace countdown, and the message "X ago" display. Only record timestamps and real-time animation legitimately use `Date.now()`. **"… ago" labels too — measure a stamp on the clock that WROTE it** (2026-10-28, dev: mail sent at game time 11 Mar 2026 read "last mail · 231d ago" in Admin → Contacts). GAME clock: message `timestamp`, `status.readAt`, trace-log rows, recycle-bin rows, terminal login footprints, shard `lockoutUntil`, contact `breachLockoutUntil`. REAL clock: `deliveryFailures[].at`, held-mail `_queuedAt`, group `sharedFrom.at` / `lastUsedAt`, composer drafts `savedAt`, `claimedRealMs`, `revealedAt`, `logActivity` rows. `AdminPanelApp._relativeTime(iso, { real })` defaults to the game clock; pass `{ real: true }` only for a real-clock stamp. Sim `dev/tools/sims/test-game-clock.mjs`.
- **Display dates via `formatCyberDate(iso, opts)` (helpers.js), never hand-format.** It honors three world settings: `dateFormat` (order — `YMD`/`DMY`/`MDY`), `dateMonthStyle` (month as `number` 03 / `short` Mar / `long` March, composes with the order), and `timeFormat` (24h/12h). Options: `{ dateOnly }`, `{ timeOnly }`, `{ seconds }`. The message-viewer HUD clock uses the default (date + time) at a reduced font so it fits the header. **CyberTimePicker follows all three too** (2026-07-13): its preview and the `formatted` string handed to `onSet` **delegate to `formatCyberDate` directly** (the old hand-built string ignored `dateMonthStyle` and could drift), and a written month style swaps the month digit-box for a named `<select>` (Jan/January, numeric values 1–12 so `_readInputs` parses either widget; the input listener is `'input change'` — selects need change). Presets: Game Time / Real Now / +1 Hour / +1 Day / +1 Week.
- **Cyberpunk RED data is read through `scripts/utils/cpr.js` (stage 2, step 10b)** — roles (`roleItems`/`firstRole`/`roleName`/`roleRank`; CPR roles are actor items, not `actor.system.role`), money (`wealthBalance`/`wealthLedger`/`hasWealth`; writes go through `utils/wealth.js`), Luck, ICE ATK/class, `marketPrice`/`PRICE_PATH`, `itemTypes()`, and the type lists. Skills stay in `SkillService`. `test-cpr-adapter` fails on a direct read elsewhere, so when the system changes a shape the fix is one file.
- ICE actors: `isBlackIceActor` (type `blackIce`/`black-ice`, flag `isBlackICE`, or a name matching `/black\s*ice/i`).
- Contact avatars resolve via `PortraitService.resolvePortrait`: `contact.portrait` → linked-actor `img` (when `contact.actorId` set) → `contact.customImg` → initials. When creating a contact programmatically (e.g. "Add" from a message), pass the sender's `actorId` and/or a `portrait` — name+email alone yields initials. `ContactRepository.addContact(actorId, contactData)` is `(ownerActorId, data)`; the contact's own linked actor goes in `data.actorId`.
- **"Burned" contacts are retired from scope but only CSS-hidden, not removed.** The burn/restore logic still lives in `MasterContactService` / `ContactRepository` / the tab + GM handlers. The UI is hidden via two reversible blocks marked `Burned UI hidden` in `styles/components/admin-panel/tab-contacts.css` (stat, filter pill, row badge, batch-burn, per-contact burn) and `styles/components/gm-contact-manager.css` (burn/restore buttons + `.ncm-chip--burned`). Delete those blocks to restore the UI. Burned references in the message viewer / email / toasts were intentionally left visible.

## Data layout

Inboxes are Foundry journals identified by **flags**, not name: `flags.night-city-messenger.{ type: 'inbox', actorId }` (actor inbox) or `{ type: 'contactInbox', contactId }` (contact inbox). Current/migrated worlds use **human-readable names** like `"V — Inbox"` / `"Fixer — Mail"`; the legacy `NCM-Inbox-<id>` / `NCM-Inbox-Contact-<id>` names are only a fallback.

**To scan `game.journal` for inboxes, ALWAYS use `MessageRepository.identifyInbox(journal)`** → `{ isContact, ownerId } | null` (flag-first, legacy-name fallback, skips archived inboxes in the Deleted folder). **Never key on the `NCM-Inbox-` name prefix** — a prefix scan silently matches nothing on current worlds, which is what made the admin Message Activity feed (and several other scans) come up empty. Callers: MessagesTab, MessageService, ContactsTab, CharacterSelectApp, MessageAccessService, DocumentSyncBridge.

Each message is a journal page with flags under the `night-city-messenger` namespace (`messageId`, `subject`, `body`, `status.read/deleted/spam/eddiesClaimed`, `timestamp`, `eddies`, `selfDestruct`, `references[]`, etc.). Sent copies have IDs ending in `-sent`. The four-subfolder hierarchy (Inboxes / NPC Mail / Data Shards / Deleted) under "Night City Messenger" is built and kept in sync by the migration tool in `MessageRepository.migrateJournalOrganization()`.

**GM-only logs live in a GM-only journal, not world settings (stage 2, step 13).** A world setting is re-sent whole to every client on each write and loaded by every player at login; `scripts/data/gmLogStore.js` keeps the trace log and the network access log as pages of the hidden "NCM — GM logs" journal (ownership NONE: GM clients only). `readGmLog` / `updateGmLog` (serialized per log) / `writeGmLog`; migration v7 moved them (verifies the read-back before emptying the setting). Measure a world with `node dev/tools/measure-world-settings.cjs --data <Data folder>` (read-only: copies the settings DB). A new append-style GM log goes there too.

**Version-keyed migrations (2026-08-14): breaking flag-shape changes get an upgrade hook.** `scripts/core/MigrationRunner.js` + the hidden world setting `dataSchemaVersion` (default 0 = pre-versioning world) run at postReady/5, GM-only, no-op when current. To ship a breaking change: bump `DATA_SCHEMA_VERSION`, push `{to, label, run}` onto `MIGRATIONS` (idempotent — a crash mid-run reruns it; the version stamps after each successful step so later failures resume). Never renumber shipped entries. This exists because the alternative was permanent read-time back-compat or hand-run console snippets (the `uploadable:false` legacy-program episode). The two older shape-detecting migrations (`migrateJournalOrganization`, `MasterContactService._migrateContacts`) stay as they are — they key on detecting legacy data, not on a version.


It re-emits both packs (both formats), validates every line round-trips as JSON, and parses every `command` the way Foundry runs it (an **async** function with `speaker, actor, token, character, scope` predefined — so don't declare locals named `actor`/`token`/`character`; use `_who` etc.). Macro bodies use only double-quoted strings + concatenation (no backticks/template literals) so they JSON-encode cleanly.

**Icons:** each macro's `img` is a fixed path `assets/icons/macros/<icon>.svg` (player icons cyan, GM icons neon-red; `assets/icons/macros/README.md` is a generated macro→file map). The generator seeds a neon placeholder SVG there **only when the file is missing** — it never overwrites existing art, so custom icons (same filename) survive every regen. Replacing a file in place takes effect immediately: no regen, no reinstall, Foundry just loads whatever is at the path. Keep the `.svg` extension (baked into the docs); to switch to PNG/WebP, change the extension/`ICON_WEB_BASE` in the generator, rerun, and reinstall via Admin → Tools.

**NeDB gotcha:** Foundry rewrites the module's `.db` pack files on disk when a world loads (NeDB compaction reorders lines and may add fields). This is harmless — the source of truth is `gen-macros.cjs`, and the Import/Reinstall flow copies into independent world Macro documents — but it means a post-load `.db` will not be line-for-line what the generator emitted. Diff packs **keyed by `_id`**, never by line order.

The packs never auto-write to a world. **Admin Panel → Tools → "Import / Reinstall Macros"** (`ToolsTab.onImportMacros`) is the explicit installer: it creates missing macros in world folders `NCM — Player Tools` / `NCM — GM Tools`, resets `managed:true` macros to the shipped version, and never touches macros the GM authored or detached (matched by `sourceId`).
