FILE ENVELOPE · PER-ENTRY EXFIL · SAVE FRAME

The keystone: an entry gets an envelope — MAIL (today: from / subject / received) or FILE (filename / path / modified / size / owner-node). A camera feed is not mail and should stop pretending to be. Default stays MAIL, so every existing entry is untouched; the composer just pre-picks FILE for the types that are obviously files (feed gallery, payload, malware, schematic, syslog…). File mode also suppresses reply / add-to-contacts / threading / the "New message from Unknown" toast, and never auto-creates a master contact from a system node like SECCAM-B2. Size + extension auto-derive from the content (12 frames → 14.2 MB, .feed) — the GM types a name, not a spec sheet.

Mixed list, type icon leads. A MAIL row is unchanged (priority dot → sender → subject → body preview). A FILE row swaps the priority dot for the content-type icon (colored by CONTENT_TYPE_INFO), the sender line for the filename in mono, and the body preview for type · size · path. Unread files show NEW instead of a priority dot — a file has no urgency, it just wasn't there before.

The ALL / MAIL / FILES chips are the same display-only filter pattern as the gallery chips (document-delegated, zero per-app wiring). They only render when the mailbox actually holds both kinds.

A live feed's "date" reads LIVE, not a timestamp — it isn't from a moment, it's happening.

No avatar, no ADD, no REPLY, no "(no subject)". The header answers the questions you'd actually ask a filesystem: what is it, where does it live, who owns it, when did it change, how big.

Owner is a NODE, not an Agent (amber, mono). This is the field that must not run _syncFromToMasterList — SECCAM-B2 is a camera, not a person, and auto-creating a master contact for it would pollute the directory.

The 4th cell is type-aware (channels / rows / frames / lines / entries) — free texture from data we already have.

Files never thread. The resolver's subject+counterparty fallback would happily merge two unrelated dock-cam.feed files; file entries are excluded from threading outright.

You cannot download a stream. Rather than hide the buttons (which reads as "the UI is broken"), the denied actions render dashed and dead with a reason chip — LIVE STREAM. The player learns the rule. Hiding stays available per-entry (silent deny) for things whose very existence is the secret.

SAVE FRAME is the escape hatch and the whole point: you can't take the feed, but you can take a picture of it. It lands in your Agent's Recovered folder as a one-image gallery — evidence you can carry.

Denied reasons are authored strings: LIVE STREAM · COPY-PROTECTED · DRM · TOO LARGE · or free text.

Per-action INHERIT / ALLOW / DENY layered over the terminal's Exfil tab. The terminal's master switch is a hard ceiling — master off means nothing leaves, no entry can widen it. A feed pre-fills DENY on Agent/Shard + ALLOW on Save frame; one click to change.
Exfil override lives in ③ SECURITY & ACCESS, not Delivery — it's an access policy, not envelope metadata. The collapsed section chips summarize it (exfil: 4 of 6) so you can see it without opening.

Sensible per-type defaults, not hardcoded rules: picking FEED pre-selects the deny pair; picking MESSAGE leaves everything INHERIT. The GM can always override — nothing is locked by type.

In the monitor / PTZ view, SAVE FRAME grabs the current channel (and, on a PTZ cam, the current crop — what you're actually pointed at) and writes it to your Agent's Recovered folder as a one-image gallery, stamped with the cam id + the feed clock. Shutter flash + shard-compile → receive.

It's a normal exfil action, so it inherits the whole machinery: optional roll (DV), trace-on-fail, the no-GM-online guard (the write relays), and the per-entry override that can switch it off entirely.

This is what turns "you can't download the feed" from a wall into a heist beat.
